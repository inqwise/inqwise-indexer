# inqwise-indexer

Vert.x 5.x indexing library with this Maven reactor layout:

- `indexer-dependencies`: dependency-management BOM for shared dependency versions.
- `indexer-parent`: reusable build parent for compiler, test, plugin, dependency-management import, and common build conventions.
- `indexer-core`: stable indexing action payloads, runtime ports, document data-plane ports, action/provider/hot-routing contracts, command contracts/execution primitives, provisioning contracts/resource definitions/utilities, catalog ports, metadata contracts/models, and shared error primitives. It has no dependency on deployment services, node wiring, REST, gateway, or local adapter implementations.
- `indexer-events`: typed cross-module event publication contracts and local publisher implementations.
- `indexer-coordination`: keyed exclusive-flow coordination contracts and the local shared-promise implementation.
- `indexer-query`: provider-neutral report dispatch, trusted-scope enforcement, published multi-index planning, query-provider contracts, typed report helpers, and Vert.x `ReportsService` transport.
- `indexer-query-rest`: consumer-neutral OpenAPI delivery for report discovery and execution over the generic query services.
- `indexer`: command handlers/orchestration, action-routing implementations, hot-routing implementations, catalog implementations, provisioning orchestration, runtime implementations, service communication, node wiring, REST/gateway APIs, and default local adapters. It depends on `indexer-core`.
- `indexer-example-hacker-news-model`: shared consumer-owned stored-document model, schema validation, and JSON codec used by both HN ingestion and suitable reports. It has no indexing runtime, report engine, REST, or store-adapter dependency.
- `indexer-example-hacker-news-actions`: consumer-owned pre-routing action validation and canonicalization over the shared HN model. It contains no target selection, routing, queue, document-store, or report execution logic.
- `indexer-example-hacker-news-reports`: consumer-owned HN report contracts, codecs, catalog, typed facade, result transformation, and local in-memory query-provider adapter. It contains no polling runtime, launcher, or logging configuration.
- `indexer-web`: internal React operator console plus its Vert.x static-delivery and same-origin API-proxy boundary. Maven builds the SPA into the module classpath without depending on Indexer domain/runtime code or Gateway.
- `indexer-node-application`: deployable node boundary. It composes the Indexer node, web verticle, and optional local consumer report services, and owns the Vert.x application launcher, runtime logging implementation, Jib image definition, and container process arguments without adding a project-specific `main()` method or shaded application JAR.
- `indexer-example-hacker-news`: first concrete data-source project. It owns Hacker News change polling, current-item projection, source-side deduplication, and target-action batching. Its ingestion runtime runs as a separate clustered Vert.x application and submits to an Indexer node through the Target Action EventBus service without depending on report execution.
- `indexer-load`: load/reload orchestration, provider/runtime integration, durable workflow commands, and load-specific metadata around the core indexer primitives.
- Root `inqwise-indexer`: local aggregator POM only.

The approved provider-neutral scope includes the query/report boundary described below. Query execution in this scope uses only `InMemoryIndexerDocumentStore` and its consumer-specific local adapters. Elasticsearch, OpenSearch, and every other external document-store adapter are intentionally excluded: each provider will be designed and implemented independently in its own thread when its concrete client, query semantics, schema behavior, and operational requirements are selected. This scope does not introduce a speculative shared external-search adapter. Other remaining implementation starts only after selecting another concrete external contract or requirement: production persistence/resource adapters, deployment identity and audit sinks, distributed coordination, historical/live blend tracking, partitioned catch-up lanes, strict distributed queue-reset fencing, or classified and observable automatic runtime recovery. Repository splitting remains deferred until module contracts and release cadence are stable. The public gateway remains intentionally read-only; administration mutations, action submission, runtime recovery, and report exposure stay internal until a deployment supplies the required policy.

## Query and Reports

`indexer-query` is a provider-neutral query and report-execution module over the existing Publication-owned `PublishedIndexResolver`. Its generic `ReportsService` accepts only a report name plus user parameters, resolves an immutable typed report definition, obtains trusted execution scope from a server-injected `ReportCaller` and context resolver, intersects report, consumer, and user time/limit constraints, conjoins their filters, resolves active published physical indexes, partitions them by schema identity, invokes an injected document-query provider once per compatible group, and lets the report decode and encode its typed result. Empty effective periods or absent published indexes are successful empty executions passed to the report decoder.

Optional presentation is a separate capability from execution. A `PresentedReportDefinition` supplies a validated `ReportPresentation` containing only its stable report name, operator-facing title and description, and draft 2020-12 JSON Schemas for the user parameter object and encoded result object. `DefaultReportCatalog` verifies that presentation and execution names match and returns defensive copies. The read-only `ReportDiscoveryService` publishes only these presentations, sorted by stable name, on an independently configured EventBus address; it does not expose execution descriptors, logical targets, trusted scope, provider queries, schema compatibility, or physical index identities. The local node composes one discovery service beside its configured execution service. The separate `indexer-query-rest` module exposes neutral `GET /reports` discovery and `POST /reports/{report_name}/executions` delivery without depending on a consumer, runtime, node, or Gateway package.

`ReportExecutionRequest` cannot supply caller identity, trusted filters, logical targets, physical index names, or provider query objects. A deployment adapter constructs `ReportCaller` only after its own trust decision and injects it into the server-side `ReportsServiceImpl`; it is not a Vert.x data object and never crosses the generated service-proxy codec. `ConsumerReportExecutionContextResolver` maps that injected consumer identity to a server-owned maximum scope and rejects missing or unknown consumers. It does not associate consumers with targets: the report definition independently owns its logical target, static maximum scope, request codec and validation, query planning, supported schemas, result decoding, and transport encoding. Concrete typed report facades remain consumer-owned and delegate through the reusable typed report binding/executor over `ReportsService`; typed clients cannot choose caller identity. Full-document reports may reuse a consumer document codec, while projection, aggregation, and calculated reports may use specialized result codecs.

Published index resolution includes the active manifest schema name and version. Query execution rejects unsupported schemas before provider invocation and groups compatible indexes without deriving identity from physical names. Physical index identities are present only in `DocumentQueryExecution`, where the provider adapter needs them; report definitions receive schema identity and the provider result without index names or indexer/target ids. Request-codec validation is identified explicitly and maps malformed types, fractional numbers, and out-of-range integers to the service's invalid-request contract; unexpected report, provider, and stored-data failures remain internal errors rather than being attributed to the caller. Each current `ReportsFacade` owns one provider and a provider-homogeneous resolver, so provider identity is implicit in composition. Explicit provider/strategy identity is required before any future facade may resolve mixed-provider indexes. Concrete search clients, authentication and trusted-context construction, REST/Gateway exposure, consumer report catalogs, document ingestion validation, action hooks, exports, node wiring, and deployment topology remain outside `indexer-query`. The module does not depend on queue transport, load/reload, runtime workers, `Indexer`, node/application modules, consumers, or concrete document stores.

The dependency direction for this slice is one-way: `indexer-core` provides Publication and runtime contracts; `indexer-query` adds provider-neutral report execution; the shared HN model remains independent; HN actions and reports consume that model from separate write-side and read-side modules; and `indexer-node-application` alone composes the selected consumer capabilities with the local `indexer` adapters. The reports module depends on `indexer` only for its explicitly local `InMemoryIndexerDocumentStore` adapter. Neither `indexer-core`, `indexer-query`, nor `indexer` imports a concrete consumer.

## Hacker News Example

`indexer-example-hacker-news` is the first concrete source application over the provider-neutral indexing runtime. Its companion `indexer-example-hacker-news-reports` module is the first concrete consumer of `indexer-query`; keeping them separate lets deployment modules use HN report contracts without importing the polling launcher or its runtime resources. Both depend one-way on `indexer-example-hacker-news-model`, which owns the active stored-document schema rather than either write or read infrastructure. The source follows the official [Hacker News Firebase API](https://github.com/HackerNews/API): every poll reads `/v0/updates`, coalesces duplicate changed item ids, fetches the current `/v0/item/{id}` representation with bounded concurrency, and submits only projections whose content changed since their last accepted submission. It performs no historical backfill and stores no archive.

The consumer-owned `hacker-news.stories` report accepts a bounded time range, minimum score, requested limit, and optional opaque continuation cursor. Its report definition fixes the logical `hacker-news` target, requires the stored `source=hacker-news` and `type=story` semantics through typed consumer filters, caps results at 100, supports the current `default/v1` publication schema, and requests the `hacker-news.story-search` provider capability. `HackerNewsReports.stories(...)` is the concrete typed facade and delegates through `TypedReportExecutor` to the generic `ReportsService`; grouped provider results are deduplicated by item id and globally ordered by descending score, descending time, and ascending item id. A result includes `next_cursor` only when another page exists. The versioned cursor is bound to the user time range and minimum score but deliberately excludes page size, so a caller may change `limit` while continuing. It is a stateless position marker, not an authorization token: trusted consumer scope is independently reconstructed and enforced on every request.

The `hacker-news.story-authors` report validates a materially different result shape over the same in-memory boundary. It accepts the same time/minimum-score constraints plus an author-group limit and `order_by` selection of `total_score`, `story_count`, `max_score`, or `latest_story`. The local provider resolves duplicate story ids across selected indexes before grouping nonblank authors, then calculates story count, total score, maximum score, and latest story time. `HackerNewsReports.storyAuthors(...)` exposes the typed result. Consumer and user time/filter/limit intersection still occurs before the `hacker-news.author-summary` capability is invoked; deterministic author-name ordering breaks aggregate ties.

`HackerNewsDocument` and `HackerNewsDocumentCodec` form the shared active-document contract. Ingestion builds the immutable model and validates required ids, type, time, story title, numeric ranges, related ids, and source before encoding the JSON carried by `PutDocumentActionItem`. `LocalHackerNewsQueryProvider` decodes stored JSON through the same contract before filtering or projection, so malformed documents fail as stored-data errors instead of producing weakened results. Unknown extra fields are tolerated but not added to the base model, allowing a future store adapter to append provider-specific enrichment through its own wrapper without changing this consumer codec. Report projections remain separate from the stored model because aggregate and calculated reports do not necessarily return whole documents.

`TargetActionPreparer` is an optional consumer-side boundary invoked by `TargetActionService` after generic request validation and before hot routing. The deployment-owned `TargetActionPreparationRegistry` selects a preparer by target name; the preparer itself remains target-agnostic, and targets without a registration pass through unchanged. Preparation is batch-atomic and must preserve action count and action types. Consumer validation failures become invalid-request failures, while broken preparer contracts remain internal errors. `HackerNewsTargetActionPreparer` validates PUT and REMOVE ids, decodes PUT documents through the shared codec, requires the action uid to match the document id, and emits canonical base JSON. This protects direct Target Action producers as well as the HN ingestion application. Provider/store-specific appended fields remain downstream adapter responsibility and are intentionally removed from submitted base documents. The local node enables this registration explicitly through `hacker_news_actions`, whose deployment configuration owns `target_name`; application code keeps it disabled by default.

`LocalHackerNewsQueryProvider` is the concrete adapter for the current query scope over `InMemoryIndexerDocumentStore`. It reads defensive per-index snapshots, dispatches the story-search and author-summary capabilities, translates only the known HN source/story filters, and rejects every unknown filter rather than silently weakening trusted scope. Duplicate item ids prefer the later selected index when source timestamps are equal, which is required because HN item timestamps do not advance with score/content updates. `LocalHackerNewsReports.create(...)` composes that adapter, the HN catalog, a supplied Publication resolver, a supplied trusted-context resolver, and the fixed server-side `hacker-news-reports` caller into `ReportsService`. The ingestion verticle never deploys or calls it. The node application can deploy this local service explicitly through `hacker_news_reports`; it is disabled by default in application code and enabled only by the local development configuration. The same configuration deploys the neutral discovery service on `discovery_address`; the HN definitions contribute their user-parameter/result schemas without exposing HN classes to a discovery client. The local execution service currently maps its fixed consumer identity to an unbounded development scope. The consumer module also owns optional OpenAPI REST adapters over its typed facade. They remain separate from `indexer-query` and Gateway and delegate caller-free requests to the configured EventBus `ReportsService` address rather than duplicating report execution. External document stores, deployment-selected authentication/context policy, and public query exposure remain outside the example.

HN item ids are stable document uids. Live items produce idempotent PUT actions containing the current structured item fields; items marked `dead` or `deleted` produce idempotent REMOVE actions. The source application does not construct or start `IndexerNode`. It obtains `TargetActionService` from `TargetActionServices.proxy(vertx)` and sends batches to the cluster-visible `indexer.service.target-action` address. The separately deployed Indexer node owns target resolution, auto-provisioning, routing, queue transport, runtime processing, and document storage.

Both processes are started by the Vert.x 5 application launcher; neither module creates Vert.x in a project-specific `main()` method. The two launchers must use the same cluster manager and discovery configuration. Both launcher modules include the Hazelcast cluster manager on their runtime classpaths, while launcher arguments and deployment configuration decide whether each process actually starts clustered.

Install the reactor artifacts first:

```sh
mvn -pl indexer-dependencies,indexer-parent,indexer-node-application,indexer-example-hacker-news -am install -DskipTests
```

Start the Indexer node with the clustered container deployment described under Local Deployment. When the container advertises Hazelcast at `${INDEXER_NODE_HOST}:5702`, start the HN source application on the Docker host with the same cluster name, the shared TCP discovery configuration, and that advertised endpoint as its seed:

```sh
./run-hacker-news-local.sh
```

The script defaults to node host `192.168.6.171`, Hazelcast public port `5702`, and cluster name `inqwise-indexer-local`. Override them with `INDEXER_NODE_HOST`, `INDEXER_HAZELCAST_PUBLIC_PORT`, and `INDEXER_CLUSTER_NAME`. The host-side example binds its Hazelcast member to `${INDEXER_NODE_HOST}:5701`; the container member remains reachable at `${INDEXER_NODE_HOST}:${INDEXER_HAZELCAST_PUBLIC_PORT}`. Do not use the nonexistent `local-cluster` Maven profile or omit the Hazelcast system properties: either starts an isolated default cluster. A source warning containing `No handlers for address indexer.service.target-action` means the HN launcher cannot see the clustered Indexer node; verify that both Hazelcast member logs report a cluster size of two.

`deployment/local/indexer-node.json` defines the non-periodic `hacker-news` target with auto-provision-on-write. The HN source configuration lives separately under `hacker_news`: `base_uri`, `poll_interval_ms`, `max_changes_per_poll`, `request_concurrency`, `request_idle_timeout_ms`, and `action_batch_size`. Defaults are a five-second poll, at most 100 changed ids, eight concurrent item requests with a ten-second idle timeout, and 100 actions per submission. One poll is allowed in flight; a timer tick during a slow poll is skipped rather than creating unbounded work. Fingerprints are retained only for the selected update window, so source-side deduplication memory stays bounded.

This remains a development example. Its fingerprint memory is process-local and is lost on restart. Restarting may replay the current update window, which is safe because document mutations use stable ids. The source exposes no document query API and has no access to the node's document adapter. In the local profile, cluster members can call the report service at `indexer.query.reports`, but every request receives the server-injected `hacker-news-reports` caller and cannot select another consumer through its payload; the host can call the consumer-specific REST adapter through loopback port `8085`. That fixed consumer currently receives a deliberately unbounded scope because the profile has no authenticated identity boundary, so neither transport must be treated as public or production-safe. Production evolution requires source leadership, a durable deduplication/checkpoint store, durable command/queue and document providers, retry/backoff plus API observability, and an authenticated caller/context policy. Each future document-store query implementation remains an independent provider scope rather than a continuation of the in-memory example. LLM-derived product-pain enrichment is the next consumer layer, not part of source ingestion or Indexer runtime state.

## Internal Web Console

`indexer-web` is the internal operator interface for the local Indexer deployment. It is a separate logical Maven module containing a static React SPA and a narrow Vert.x delivery wrapper. It depends only on Vert.x Web/HTTP Proxy and the existing internal HTTP envelopes; it does not depend on Java domain packages, Vert.x EventBus services, or the public Gateway. `indexer-node-application` packages and deploys it beside the Indexer node in the same Vert.x JVM and container.

The console displays node readiness, runtime attachment, targets, indexers, provisioning state, and publication state. Target and indexer catalogs support local search/status filters and accessible entity detail drawers without introducing additional read API calls. Live monitoring offers paused, 15-second, 30-second, and 60-second refresh intervals; requests are serialized, polling pauses while the tab is hidden, stale data is identified from the last successful update, and desired-runtime/local-attachment drift is highlighted. Readiness, target catalog, indexer catalog, and runtime requests report independent health and last-success age; a failed envelope retains its last good data without hiding successful results from the others. Catalog navigation uses deterministic sorting, 10/25/50-row limits, pagination, and clear-filter controls; sort, limit, page, filters, polling preference, selected entity, and active section persist in the URL. A compact metrics view projects bounded action intake, indexing outcomes, runtime convergence, and lifecycle-operation signals from the same-origin Prometheus proxy; raw series and arbitrary labels stay outside the UI. Bounded operations expose indexer activate/deactivate, failed target-provisioning recovery, manual local-runtime reconciliation, explicitly confirmed single-indexer queue reset, and typed-name-confirmed single-indexer deletion from their detail drawers. Catalog mutations send the selected catalog `version` as `expected_version`; reconciliation only asks the current node to reload durable state and converge its local runtime. Queue reset advances future writes to a new versioned queue and schedules asynchronous cleanup of the retired queue; it does not claim synchronous fencing of old in-flight items. Deletion returns after fencing the indexer and accepting durable cleanup, not after physical cleanup completes. Every operation disables conflicting submission while pending, reports controlled errors, and reloads durable catalog/runtime state after success or failure. Bulk destructive operations remain outside the frontend.

The Reports view discovers presentations and executes reports through the
consumer-neutral API. It generates forms only for closed object schemas with
flat scalar parameters and renders only bounded scalar or table results. Unknown
keywords, remote references, deep structures, incompatible result payloads,
unsafe link schemes, and results beyond the display cap are rejected or bounded.
The frontend imports no consumer module or consumer-owned OpenAPI contract.

In development, Vite provides hot reload and forwards the same paths that the
Vert.x wrapper owns in packaged/runtime use:

- `/api/admin` proxies the Admin REST service on port `8080`.
- `/api/actions` proxies the Target Action REST service on port `8081`.
- `/api/runtime` proxies the Runtime REST service on port `8083`.
- `/api/health` proxies the deployment health service on port `8084`.
- `/api/metrics` proxies the read-only Prometheus endpoint on port `9090`.
- `/api/reports` proxies the consumer-neutral Reports REST service on port `8086`.

Run the local node first, then start the hot-reload frontend:

```sh
cd indexer-web/src/main/frontend
npm run dev
```

Vite listens on `http://localhost:3001` so it can run beside the packaged
console exposed by the node container on port `3000`.

To exercise the packaged delivery boundary, build and run the node application:

```sh
./run-local.sh
```

The React/Vite workspace lives under `indexer-web/src/main/frontend`. Admin, Runtime, and neutral Reports response/error schemas are concrete OpenAPI contracts; the frontend build regenerates TypeScript path and component types from those source contracts and uses `openapi-fetch` for type-safe same-origin requests. The Maven lifecycle installs a pinned Node/npm toolchain, runs `npm ci`, generates the API types, creates the Vite production bundle, and copies it to the classpath `webroot` served by `IndexerWebVerticle`. The Vert.x wrapper strips the UI-only `/api/{service}` prefix and forwards requests to the corresponding internal REST port. It is a delivery adapter, not a second business API or a replacement Gateway.

The console is an internal development and operations surface. Excluding Gateway also excludes public exposure, production identity, and authorization from this scope. A deployment-owned authenticated boundary must be approved before the console is exposed outside a trusted internal environment.

## Local Deployment

The first runnable deployment uses the existing `IndexerNode` composition with in-memory metadata, queue, and document-store adapters. It enables the internal Admin, Target Action, and Runtime REST envelopes, keeps the public Gateway disabled, and loads local `customers` and `hacker-news` target definitions with cold-write auto-provisioning from `deployment/local/indexer-node.json`. It explicitly registers HN action preparation for the `hacker-news` target, and enables one HN `ReportsService` instance at the cluster-visible `indexer.query.reports` EventBus address, sharing the exact metadata repository and in-memory document store created for the node. The neutral adapter exposes discovery/execution on port `8086` for the same-origin console proxy. A consumer-specific REST adapter remains available on loopback port `8085` for typed HN acceptance checks. The application integration contract verifies malformed direct actions are rejected before routing and verifies the document and aggregate read paths with a published target/indexer/manifest and a stored HN document resolved and returned through typed EventBus and HTTP boundaries. Action-preparer selection and report adapters are owned by the application rather than `Indexer`; report components are removed during application shutdown or startup rollback, while the read-side report service remains available during runtime recovery-only mode for already-published data. This profile is for inspection and development only: the endpoints are not Gateway routes, have no caller authentication, use unbounded trusted scope, and all state is discarded when the process stops.

Prerequisites are Java 21 or newer, Maven, a running Docker-compatible daemon with Compose support, and free loopback ports `3000`, `8080`, `8081`, `8083`, `8084`, `8085`, and `9090`. Build the layered image with Jib and start it from the repository root:

```sh
./run-local.sh
```

The script installs the dependent reactor modules, builds `inqwise/indexer-node:0.1.0-SNAPSHOT` into the local Docker daemon with Jib, and starts `compose.yaml`. Jib launches `IndexerNodeApplicationVerticle` through `io.vertx.launcher.application.VertxApplication`; that application verticle starts the Indexer node first and then deploys `IndexerWebVerticle` in the same JVM. The project has no deployment-specific `main()` method and does not build an uber JAR. The Java 21 base image is pinned to an approved multi-platform OCI digest; dependency maintenance must update that digest explicitly. Compose mounts the combined node configuration read-only and checks Indexer readiness on port `8084`; the console is exposed from the same container on port `3000`.

Query the local HN stories report with its typed JSON contract:

```sh
curl --request POST http://127.0.0.1:8085/reports/hacker-news/stories \
	--header 'content-type: application/json' \
	--data '{"from_inclusive":"2026-08-01T00:00:00Z","to_exclusive":"2026-08-10T00:00:00Z","minimum_score":20,"limit":25}'
```

The time range is required, `minimum_score` must be non-negative, and `limit` must be positive. The report definition further caps the effective result limit at 100. When the response contains `next_cursor`, repeat the same request criteria with that value in the optional `cursor` field; changing the time range or minimum score is rejected, while changing the page limit is allowed. Pagination uses the current in-memory index contents and does not promise a frozen snapshot when documents change between pages. Cursor semantics remain HN report/provider behavior and do not add a generic pagination model to `indexer-query`. The OpenAPI contract is in `indexer-example-hacker-news-reports/src/main/resources/openapi/hacker-news-reports.yaml`.

Query grouped author summaries through the second consumer-owned operation:

```sh
curl --request POST http://127.0.0.1:8085/reports/hacker-news/story-authors \
	--header 'content-type: application/json' \
	--data '{"from_inclusive":"2026-08-01T00:00:00Z","to_exclusive":"2026-08-10T00:00:00Z","minimum_score":20,"limit":10,"order_by":"total_score"}'
```

For the complete two-process acceptance check, start the clustered node and
then the source in separate terminals:

```sh
INDEXER_CLUSTERED=true ./run-local.sh
```

```sh
./run-hacker-news-local.sh
```

The Hazelcast logs in both terminals must show two members. After the source
logs an accepted action batch, verify the catalog view owned by the node:

```sh
curl -fsS http://127.0.0.1:8084/health/ready
curl -fsS http://127.0.0.1:8080/admin/targets
curl -fsS http://127.0.0.1:8080/admin/indexers
```

The expected state is one active/ready `hacker-news` target and one
available/ready/active `LIVE_WRITER` whose `publication_state` is `PUBLISHED`
and whose `mutation_state` is `WRITABLE`. Query story search with a small
limit, then send the returned `next_cursor` with otherwise identical criteria;
the second response must continue after the first page without repeating its
last story. Query `story-authors` and confirm that it returns the requested
ordering and limit.

Finally, stop only `run-hacker-news-local.sh`, start it again, and wait for a
new accepted action batch. Re-read the target and indexer catalogs. The same
target and physical indexer identities must remain, no second writer may be
created, publication must remain `PUBLISHED`, and both reports must remain
queryable. Because source fingerprints are intentionally process-local, this
restart can replay the current update window; stable document ids make those
PUTs idempotent.

The same image supports an opt-in clustered launch:

```sh
INDEXER_CLUSTERED=true ./run-local.sh
```

Clustered mode adds `compose.cluster.yaml`. It starts the Vert.x launcher with `--cluster`, fixes the EventBus cluster port, and mounts `deployment/local/hazelcast.xml`. Hazelcast multicast and automatic discovery are disabled; TCP discovery uses members supplied through deployment configuration. The default forms a one-member cluster over the Compose network and does not start or package the Hacker News application. A git-ignored root `.env` can persist `INDEXER_CLUSTERED`, `COMPOSE_FILE`, and the machine-specific cluster addresses for every agent working in the same checkout, so both `./run-local.sh` and plain `docker compose up` preserve the local clustered deployment. Explicit shell variables still take precedence; `INDEXER_CLUSTERED=false ./run-local.sh` explicitly selects standalone `compose.yaml`.

Cluster settings are deployment variables:

- `INDEXER_CLUSTER_NAME` identifies the Hazelcast cluster.
- `INDEXER_CLUSTER_MEMBERS` supplies comma-separated Hazelcast TCP discovery members and defaults to `indexer-node:5701`.
- `INDEXER_CLUSTER_HOST` and `INDEXER_CLUSTER_PORT` select the EventBus bind address and port.
- `INDEXER_CLUSTER_PUBLIC_HOST` and `INDEXER_CLUSTER_PUBLIC_PORT` select the EventBus address advertised to peers.
- `INDEXER_CLUSTER_FORWARD_HOST` and `INDEXER_CLUSTER_FORWARD_PORT` select the Docker host endpoint forwarded to the EventBus bind port.
- `INDEXER_HAZELCAST_HOST` selects the Hazelcast member bind address inside the container.
- `INDEXER_HAZELCAST_PUBLIC_ADDRESS` maps directly to `-Dhazelcast.local.publicAddress` and selects the complete `host:port` member address advertised to peers.
- `INDEXER_HAZELCAST_FORWARD_HOST` and `INDEXER_HAZELCAST_FORWARD_PORT` select the Docker host endpoint forwarded to container port `5701`.

Local defaults publish Hazelcast on `127.0.0.1:5701` and the clustered EventBus on `127.0.0.1:15701`, with those same loopback addresses advertised to a peer running on the Docker host. A peer must use the same cluster name and seed Hazelcast with `127.0.0.1:5701`; Hazelcast discovery then supplies the EventBus public address.

Deployments that cross a Docker host or network boundary must set both forwarding hosts to a reachable host interface, set both public hosts to the externally reachable address, provide explicit discovery members, and secure the published ports. Cluster mode does not make the local repository, queue, document store, or command engine durable, so this profile must not be treated as approval for multiple state-owning Indexer replicas.

## Monitoring

The node application includes `vertx-micrometer-metrics` with the Prometheus registry backend. Metrics are enabled when the Vert.x application launcher creates the runtime, before `IndexerNodeApplicationVerticle` is deployed. `Indexer`, command orchestration, persistence, queue adapters, and distributed workflow state do not own or initialize the metrics backend.

The launcher reads `deployment/local/vertx-options.json` through `--options`. Its Micrometer provider starts a dedicated embedded HTTP server on container port `9090` and exposes Prometheus data at `/metrics`. Local Compose publishes that port only on `127.0.0.1`, so the development endpoint is:

```text
http://127.0.0.1:9090/metrics
```

The endpoint exposes Vert.x infrastructure metrics plus application-owned,
bounded project-logic meters:

- `inqwise_indexer_runtime_events_total`: runtime event count labeled by the bounded `event` and indexer `role` enums.
- `inqwise_indexer_runtime_active`: node-local active runtime gauge labeled by indexer `role`.
- `inqwise_indexer_action_intake_total`: accepted or rejected target actions labeled by bounded action type and outcome.
- `inqwise_indexer_action_processing_seconds`: action-item processing timer labeled by bounded action type, `succeeded` or `failed` processing outcome, and indexer `role`.
- `inqwise_indexer_runtime_convergence`: desired, attached, and drift gauges updated after full runtime synchronization.
- `inqwise_indexer_lifecycle_pending`: in-flight lifecycle operation gauges.
- `inqwise_indexer_lifecycle_operations_total`: completed lifecycle outcomes for provision, publish, reconcile, reset-queue, and delete operations.

`MicrometerIndexerEventPublisher` is composed by `indexer-node-application`
over the existing provider-neutral `IndexerEventPublisher` port and the neutral
`IndexerOperationalMonitor` reporting contract. Service decorators own action
intake and lifecycle observation, while the runtime reconciler reports
convergence after a successful full synchronization. The default node
composition accepts these ports without depending on Micrometer, and
applications without an active registry retain no-op implementations. Metrics
recording never replaces service or runtime outcomes. Processing samples use
object identity only for node-local in-flight correlation; indexer identity,
action uid, target, queue, and index name are not exported as tags. A processing
timer stops at `ACTION_ITEM_PROCESSING_COMPLETED`, before queue commit; a later
commit/resume failure increments the failed runtime-event counter but does not
rewrite the already completed processing duration.

Further command, routing, and invalidation meters should use
application-composed adapters around their existing boundaries. They must use
bounded labels such as operation, outcome, role, or classified failure kind.
Document ids, request ids, physical queue/index names, concrete target ids, raw
EventBus addresses, and exception messages must not become labels because their
cardinality is unbounded or deployment-specific.

Production deployment must decide how Prometheus reaches the endpoint and apply network policy or an authenticated monitoring proxy. The embedded endpoint has no application-level authentication and must not be exposed as a public Gateway route.

## Domain Boundary Direction

Domain boundaries are derived from functions, commands, durable state ownership, invariants, and external-resource coordination. Current service classes are implementation candidates and API facades; they are not treated as final domain boundaries by name alone.

The accepted candidate boundaries are:

- Target Catalog: target identity, target period resolution, target status, target provisioning state, target lookup, creation, and failed-provisioning recovery.
- Indexer Catalog: indexer identity, immutable routing fields, desired runtime state, mutation state, provisioning state, lookup, creation/provisioning coordination, activation/deactivation, deletion fencing, and operational queue identity reset when retained.
- Publication: publication readiness, publish/retire/replace rules, resource verification before publication, and the invariant that a target has at most one published indexer.
- Action Routing: hot and cold route resolution, logical-to-concrete action expansion, destination validation, receiver preparation through capability interfaces, and publishing concrete actions to indexer queues.
- Indexer Runtime: local-node reconciliation, queue consumer lifecycle, action item processing, commits, runtime events, and runtime recovery. Runtime workers do not own distributed workflow state.
- Resource Provisioning: queue and document-index ensure/delete capabilities. These are external-resource capabilities used by catalog, publication, and cleanup workflows, not automatically public business services.
- Deletion/Cleanup Workflow: idempotent destructive cleanup across metadata records, queues, document indexes, and load records. Missing resources are expected cleanup misses; provider failures remain retryable failures.
- Load/Reload: historical load lifecycle, load metadata, provider start/stop, lazy live-writer attachment, completion markers, catch-up barriers, review, publication handoff, failure, cancellation, and cleanup.
- Command Transport / Workflow Engine: infrastructure for durable command acceptance, partition routing, retry/redelivery, failure classification, and handler dispatch. Command messages may carry domain workflow requests, but their domain ownership remains with the appropriate boundary above.

Important service-envelope distinctions:

- `AdminService`, REST verticles, gateway verticles, and `IndexerNode` are API/deployment/composition envelopes, not domain boundaries.
- `SubmitIndexActionsCommand` belongs to Action Routing. It may ask domain/plugin capabilities to prepare receivers, such as load/reload lazy live-writer creation, but it must not own load/reload rules directly.
- Load/reload behavior stays behind `IndexerActionReceiveCapability` and plugin APIs so cold action routing can collaborate with load-specific preparation without depending on load internals.

The preferred migration order is:

1. Separate local adapters from domain implementations.
2. Move runtime implementation out of the root package.
3. Separate action-routing implementation from generic command infrastructure.
4. Move durable delete/cleanup workflow commands and handlers out of generic command infrastructure.
5. Separate lifecycle wake-up implementation from the root package.
6. Review publication/provisioning ownership before any deeper behavioral moves.
7. Keep service, REST, gateway, and node packages as outer envelopes.

The local-adapter passes moved the in-memory command engine, queue, document-store, lifecycle event-bus, metadata repository, target-invalidation registry, invalid-route cache, and static definition providers into `com.inqwise.indexer.adapters.local`. Core invalid-route cache/signature/invalidation contracts live under Action Routing, and `InvalidRouteInvalidation.matches(...)` lets adapters apply invalidations without owning routing behavior. Hot request signature construction remains in `hot`; cold command signature construction is routing-local, removing the former routing/hot package cycle.

The runtime implementation pass moved `Indexer`, `IndexerRuntime`, `IndexerRuntimeReconciler`, `IndexerRuntimeReconcilerOptions`, `IndexerProcessorVerticle`, and `VerticleIndexerProcessor` into `com.inqwise.indexer.runtime`. `IndexerSnapshot` is a public core status contract because runtime snapshots cross the runtime/core package boundary; production construction uses its validated public builder while its constructor remains private.

The runtime port pass moved queue transport ports, processor ports, and runtime event contracts into `com.inqwise.indexer.runtime` in `indexer-core`. This keeps consumer lifecycle, queue publishing, action processing, and runtime event emission together while leaving queue resource ensure/delete under provisioning ownership.

The runtime contract pass moved `IndexerOptions` and `IndexerSnapshot` into `com.inqwise.indexer.runtime`. Runtime configuration and local status snapshots sit with runtime transport/processing ports. `IndexerMarkerHandler` now lives in `com.inqwise.indexer.providers` because plugins select the model-scoped marker behavior and runtime only invokes the selected capability. This keeps the dependency one-way from runtime implementation to provider extension contracts.

The catalog model pass moved `IndexerModel`, `IndexerRole`, `IndexerRuntimeState`, `IndexerType`, `IndexResourceOwnership`, `IndexerStatus`, `IndexerProvisioningState`, and `MutationState` into `com.inqwise.indexer.catalog.indexers`. Indexer identity, availability, provisioning, role, desired runtime state, mutation/deletion fencing, type, and physical resource ownership sit with Indexer Catalog contracts. `IndexerCatalogQuery` and `IndexerCatalogEntry` provide the persistence-independent read boundary; `MetadataIndexerCatalogReader` converts records and deliberately supplies no Publication filter. The mixed `IndexerMetadataQuery` remains persistence-owned because other internal consumers still combine Indexer Catalog and Publication filters. Publication operations return `PublicationReadinessResult` or `IndexPublicationResult`; metadata records remain internal to metadata-backed implementations, and architecture guards reject metadata imports from core catalog/publication contracts. `ManifestStatus` belongs to Resource Provisioning because it identifies which persisted physical-resource definition snapshot is active; manifest records and repository mutations remain metadata-owned. A separate configuration-manifest boundary is deferred until promotion, supersession, or version-selection behavior exists outside repository operations.

The document data-plane port pass moved `IndexerDocumentStore` into `com.inqwise.indexer.documents`. This port owns document mutation execution (`put`, `remove`, `drop`) and stays separate from metadata persistence (`metadata`) and physical index ensure/delete capabilities (`provisioning`).

The action-routing implementation pass moved the cold submit handler, metadata-backed action router, routed queue publisher, `SubmitIndexActionsCommand`, `RoutedIndexActions`, and `ActionDestination` into `com.inqwise.indexer.routing`. These contracts remain in `indexer-core` for reuse by hot fallback and load integration, but their package ownership follows the Action Routing domain. Generic command infrastructure knows only the `Command` contract and registered partition resolver SPI.

`InitialPublicationMode` lives under `com.inqwise.indexer.catalog.targets` because it is used only by Target Catalog's nested indexer-creation workflow. `READY` and `PUBLISH` describe which publication operation that workflow invokes after provisioning; Publication Lifecycle does not consume this orchestration option. This function-based placement keeps core dependencies one-way from Publication Lifecycle to Target Catalog invariants.

The action-provider registry pass moved `Actions` into `com.inqwise.indexer.actions`. It is service-loader infrastructure for action providers used by runtime processing, hot routing, cold routing, and load writers; it is not a root-package facade. The repository-split readiness pass moved this helper into `indexer-core` so load/reload production code can normalize actions without depending on the deployment-facing `indexer` module.

The core action-payload pass moved `IndexerActionType`, `IndexerActionItem`, `IndexerActionItems`, `PutDocumentActionItem`, `RemoveDocumentActionItem`, `CompleteIndexActionItem`, and `CatchUpBarrierActionItem` into `com.inqwise.indexer.actions`. Queue, runtime, event, marker, provider, and command ports remain in their existing ownership packages and import action payload contracts explicitly.

The catalog package pass moved target catalog contracts/implementation into `com.inqwise.indexer.catalog.targets` and indexer catalog contracts/implementation into `com.inqwise.indexer.catalog.indexers`. `TargetManagementService` returns the catalog-owned `TargetManagementResult`; `TargetCatalogReader` returns persistence-independent `TargetCatalogEntry` values for list/get operations, and `MetadataTargetCatalogReader` performs record conversion inside the metadata adapter boundary. Architecture guards reject metadata imports from both core Target and Indexer Catalog packages. `CreateIndexerOperation` lives under `com.inqwise.indexer.metadata` because it directly inserts and reloads persistence records for load metadata adapters. Keeping that helper in `indexer-core` still lets `indexer-load` production code avoid the deployment-facing `indexer` module without misclassifying persistence behavior as catalog ownership. The `IndexerProvisioningService` contract remains in Resource Provisioning because it coordinates catalog records with document-index and queue resource ensure; its metadata/resource-backed implementation is `MetadataIndexerProvisioningService`. `MetadataTargetManagementService` receives application-scoped provisioning and publication contracts rather than constructing or referencing peer implementations; application composition supplies those shared collaborators to the dedicated service envelope. Queue reset remains under `operations.queues` as an operational troubleshooting boundary, not indexer catalog.

Target Catalog reports a missing configured definition through `TargetDefinitionNotFoundException`; it does not emit `CommandFailure`. The admin/service boundary maps that catalog failure to `NotFound`, while cold Action Routing independently classifies its missing-definition condition as `STABLE_INVALID` for command retry/cache behavior. This keeps request/reply catalog operations independent of command transport semantics.

The resource-provisioning contract pass moved `IndexerQueueResourceManager` into `com.inqwise.indexer.provisioning`, next to the document-index resource manager. Queue transport clients remain runtime/buffer ports; queue resource ensure/delete remains provisioning capability code. Cold Action Routing receives an application-composed `IndexerProvisioningService` for auto-provision-on-write; routing retains the target lock and routing decision but does not construct Resource Provisioning from repository, definition, or resource-manager dependencies. `IndexerProvisioningService` returns the provisioning-owned `ProvisionedIndexer` identity/version result rather than a metadata persistence record. Admin, Target Catalog, and Action Routing reload metadata through their own repository dependency only when they need persistence fields. The architecture guard rejects metadata imports from core provisioning contracts.

Indexer provisioning always creates the catalog indexer as `WRITABLE` and `UNPUBLISHED`, with its publication record as `PENDING`. `CreateIndexerProvisioningRequest` and admin creation DTOs therefore do not expose `mutationState` or `publicationState`; accepting `READ_ONLY`, `DELETING`, or `PUBLISHED` during provisioning would bypass lifecycle invariants or contradict the pending readiness record. Mutation changes belong to Indexer Catalog lifecycle operations, and publication changes must go through `IndexPublicationService`. Nested target creation may select `InitialPublicationMode.READY` or `PUBLISH`, which runs only after provisioning has established the writable/unpublished/pending baseline. Core provisioning contracts must not import Publication Lifecycle types.

The operational queue-reset pass moved `IndexerQueueManagementService`, `ResetIndexerQueueRequest`, and `MetadataIndexerQueueManagementService` into `com.inqwise.indexer.operations.queues`. Queue reset remains troubleshooting orchestration: it advances queue metadata, provisions the replacement queue through the provisioning capability, emits lifecycle wake-up, and submits durable cleanup for the retired queue.

The runtime test package pass moved runtime lifecycle, queue-flow, and reconciliation tests into `com.inqwise.indexer.runtime`. Root-package tests should now be limited to cross-boundary composition helpers or flows that have not yet been assigned a clearer domain package.

The root test cleanup pass moved action registry/provider tests into `com.inqwise.indexer.actions`, in-memory lifecycle provider tests into `com.inqwise.indexer.lifecycle`, and local resource-manager adapter tests into `com.inqwise.indexer.adapters.local`. Remaining root-package tests should be reviewed as explicit shared command contracts or cross-boundary helpers before staying there.

The submit-action routing test pass moved the metadata-backed `SubmitIndexActionsCommandHandler` integration tests into `com.inqwise.indexer.routing`. The deployment-module root test package should now contain only shared test helpers unless a new cross-boundary composition test is deliberately accepted there.

The test-support package pass moved shared deployment-module test helpers into `com.inqwise.indexer.testing`. The deployment-module root test package is now empty; new tests should either live under a domain/envelope package or, for reusable helpers only, under `testing`.

Core `commands` owns only the command engine SPI, dispatch, retry/failure primitives, and generic partition routing. Cleanup, Action Routing, and Load each register their own partition resolvers with the generic router, keeping command infrastructure independent of domain workflows. The concrete inline engine lives in `adapters.local`, matching the future placement of resource-backed engine adapters.

`DeploymentPackageDependencyDirectionTest` enforces the outer-envelope and adapter-direction rules for the deployment module. ## Build And Repository Direction

The root `pom.xml` remains the local reactor aggregator for this repository. Reusable build infrastructure is split from the aggregator:

- `indexer-dependencies`: dependency-management BOM only, with no source code.
- `indexer-parent`: reusable build parent for compiler, test, plugin, and common build conventions.
- root aggregator: lists modules for this repository and should not become the parent external repositories inherit from.

Future repository splits should happen only after module contracts, dependency direction, and release cadence justify the extra cost. The likely staged direction is:

- keep one repository while domain packages and modules stabilize;
- keep `indexer-parent` and `indexer-dependencies` as reusable build infrastructure that can later move to a dedicated build repository when publishing across repositories becomes useful;
- keep `indexer-core`, `indexer-events`, and `indexer-coordination` as stable contract/support artifacts;

- delay separate repositories for runtime, control-plane, routing, adapters, and deployable applications until their contracts stop co-evolving heavily.

## Indexer Behavior

Most remaining root core types retain the `com.inqwise.indexer` package while Maven module dependencies enforce ownership: `indexer` may depend on `indexer-core`, while `indexer-core` must not import deployment or adapter code from `indexer`. The current extraction owns stable action payloads under `com.inqwise.indexer.actions`, lifecycle wake-up contracts under `com.inqwise.indexer.lifecycle`, runtime transport/processing/event/configuration contracts under `com.inqwise.indexer.runtime`, document data-plane ports under `com.inqwise.indexer.documents`, queue/document resource managers and physical resource-definition contracts under `com.inqwise.indexer.provisioning`, action/provider/hot-routing contracts, command engine SPI, command envelope/partition/retry/failure primitives, durable cleanup command payloads, provisioning utilities, catalog ports, metadata contracts/models, and shared error primitives. Runtime implementations now live under `com.inqwise.indexer.runtime` in the deployment-facing module, while in-memory adapters, metadata-backed provider composition, command handlers, cleanup handlers, catalog implementations, node wiring, service facades, and hot-routing services/listeners/local caches remain in `indexer`.

`inqwise-indexer` provides a controlled transport pipeline for gently moving structured actions into a targeted document store:

- `Indexer`: front object for one internal indexer. It owns producer-side submission into the indexer queue, validates concrete action identity, delegates action-specific document writes to `IndexerAction`, and delegates consumer lifecycle to an `IndexerProcessor` when one is provided.
- `IndexerRole`: declares the indexer responsibility. `LIVE_WRITER` handles ongoing action streams. `LOAD_WRITER` handles finite historical loads.
- `IndexResourceOwnership`: declares whether an indexer owns the physical document index resource. Cleanup deletes a document index only for an `OWNER`; `ATTACHED` writers may share the same `indexName` without owning deletion.
- `IndexerProcessor`: consumer-side runtime abstraction. `VerticleIndexerProcessor` deploys an `IndexerProcessorVerticle` and hides the Vert.x deployment id.
- `IndexerProcessorVerticle`: owns queue consumption for one indexer, including pause, process, commit, and resume. It receives only an `ActionItemProcessHandler`, not the whole `Indexer`.
- `IndexerQueueClient`: buffer client abstraction for publisher and consumer handles. Production implementations can use Kafka or another durable transport. `InMemoryIndexerQueue` is a simple local/test implementation.
- `IndexerQueueResourceManager`: admin-side abstraction for ensuring and deleting queue resources. Queue provisioning and deletion are not part of the shared runtime queue client surface. Provisioning may receive provider-owned `QueueDefinition` settings; implementations should make `ensure` idempotent for compatible existing resources and fail when an existing resource is incompatible. `delete(queueName)` acts only on the exact queue identity, treats missing or already-deleting resources as successful cleanup misses, and completes after the provider has durably accepted deletion; physical disappearance may remain asynchronous. Provider authorization, connectivity, timeout, and rejection failures propagate for command retry. Runtime clients must not auto-create missing queues because stale producers must not recreate a deleted queue. Every indexer owns its queue; `IndexResourceOwnership` controls document-index cleanup only. `IndexerQueueResourceManagerContract` provides shared missing, repeated, and exact-name deletion checks. Immediate recreation after delete remains an in-memory/provider-specific test because production deletion may settle asynchronously.
- `IndexerQueueConsumer`: consumer side of the queue. It owns bulk/portion delivery policy, exposes `pause`, `resume`, `commit`, and `close`, and calls the configured item handler.
- `IndexerActionItem`: abstract action payload. Logical `PutDocumentActionItem` and `RemoveDocumentActionItem` public builder APIs expose document data only; `targetName` and timestamp belong to the submission envelope. Routing creates concrete queue payloads through `IndexerActionItems` with mandatory `targetId`, `indexerId`, and `indexName`; only package-private builder operations used by that routing factory can set those fields. Runtime indexers reject logical or partially routed document actions. `CompleteIndexActionItem` is an internal marker for historical load completion; `CatchUpBarrierActionItem` is an internal marker proving a live writer consumed earlier queued catch-up actions.
- `IndexerActionProvider`: action-owned extension point for processing and route normalization. It lives with `Actions` and the action contracts rather than in a generic SPI package. Document action providers create concrete queue payloads through `IndexerActionItems`.
- `TargetActionPreparer`: optional consumer-owned validation/canonicalization before hot routing. Deployment composition selects it by target through `TargetActionPreparationRegistry`; it is separate from generic `IndexerActionProvider` route/runtime processing and cannot own target-name management. This submission contract provides pre-routing preparation only; runtime lifecycle hooks use the separate contracts below.
- `DocumentActionRuntimeHooks`: separately injected runtime capability over immutable `DocumentActionExecutionContext`. `beforeAction` runs before a PUT/REMOVE reaches the document store. `afterWriteBeforeCommit` runs after a successful idempotent write but before queue commit; failure leaves the item uncommitted for transport recovery/redelivery, so the write and hook must tolerate repetition. `afterCommit` is an observer invoked only after commit/acknowledgement. Its failure emits `ACTION_ITEM_AFTER_COMMIT_OBSERVER_FAILED`, is logged, and cannot undo the write, mark the action uncommitted, or prevent consumer resume. Marker actions do not invoke document hooks. Context document JSON is defensively copied, and hooks cannot transform the action or mutate target id, indexer id, physical index name, document uid, or routing destination.
- `IndexerProvider`: indexer-type extension point for loading and composing indexer views. `ResolvedIndexer` exposes the catalog-level `IndexerModel` plus optional `HotIndexerCapability`, while metadata lifecycle records remain inside metadata-backed implementations. The default metadata-backed provider exposes that capability only for eligible live writers.
- `IndexerDocumentStore`: target document-store abstraction. The default document store is in-memory and also implements `IndexerDocumentIndexResourceManager` for test/local provisioning. Document-index `ensure` is idempotent for the same `IndexDefinition`, and fails when an existing index has a different definition. Resource deletion accepts only one concrete physical index identity; wildcard, `_all`, and comma-separated identities are rejected. Missing and repeated deletion are idempotent success, while real provider failures propagate for command retry. Production document clients must not auto-create missing indexes. `IndexerDocumentIndexResourceManagerContract` supplies shared deletion checks; immediate recreation remains provider-specific because durable deletion may settle asynchronously.
- `DocumentStoreMetadataRepository`: id-first metadata abstraction for targets, indexers, publications, manifests, and mutation state. The default repository is in-memory.
- `CommandService`: narrow producer-facing command submission API.
- `CommandEngine`: pluggable runtime SPI that combines command submission, handler registration, and engine lifecycle. Concrete engines own transport-specific consumption, acknowledgement, and retry mechanics. `CommandHandlerRegistry` resolves handlers independently of transport. `CommandProcessor` executes exactly one handler attempt and returns an explicit succeeded or classified failed outcome while preserving the original throwable. `adapters.local.InMemoryCommandEngine` maps that outcome back to its inline `Future<Void>` contract for local composition and tests.
- `DocumentStoreCommandHandlers`: cleanup-package assembly helper for registering the standard document-store lifecycle and provisioning command handlers with any `CommandEngine` while keeping repository, provider, resource-manager, and event-bus dependencies explicit.
- `TargetManagementService`: accepted typed request/reply boundary for creating a concrete target from catalog-owned `TargetDefinition` data supplied by a provider adapter. It can optionally compose indexer provisioning and marks the target `READY` only after requested indexer readiness or publication succeeds.
- `IndexerProvisioningService`: core typed request/reply provisioning contract returning `ProvisionedIndexer` identity and optimistic version. `MetadataIndexerProvisioningService` inserts durable indexer metadata as `PROVISIONING`, ensures document-index and queue resources, inserts manifest/publication metadata, and marks the indexer `READY` or `FAILED`.
- `TargetManagementService.recoverProvisioning(...)`: request/reply function for reopening an `ACTIVE` concrete target whose provisioning state is `FAILED`. It moves the target back to `READY` with expected-version protection so normal explicit indexer creation or cold first-writer provisioning can be retried.
- `ReplacePublishedIndexer`: metadata primitive for atomically retiring the old published indexer for a target and publishing a replacement indexer.

### Node Envelope And Service Facades

The node envelope is the local Vert.x composition layer for one running indexer node. It owns service deployment and local runtime lifecycle, while keeping dependency assembly in composition factories and durable workflow decisions inside command handlers and metadata/repository layers.

- `IndexerNode`: programmatic lifecycle root. It receives `IndexerNodeOptions` and `IndexerNodeComponents`, then starts listeners and deploys enabled internal service verticles. Its convenience `create(...)` method delegates default dependency assembly to `DefaultIndexerNodeComponentsFactory`.
- `DefaultIndexerNodeComponentsFactory`: local default composition root. It assembles the in-memory repository and resource adapters, definitions, command handlers, hot routing, invalidation listeners, Vert.x lifecycle event bus, runtime, and reconciler without adding construction ownership to `IndexerNode`. Its explicit overload accepts deployment-composed `DocumentActionRuntimeHooks`; defaults remain no-op and hooks are not JSON-configured workflow state.
- `IndexerNodeVerticle`: Vert.x parent verticle wrapper for deploying a node through normal Vert.x deployment APIs. Child service verticles are deployed under this parent deployment scope.
- `IndexerNodeOptions`: declares which internal services, service-level REST APIs, and external gateway are enabled and how many verticle instances each service should deploy. Instance counts must be at least one when a service is enabled. Runtime service, REST APIs, and the gateway are intentionally singleton per node. REST APIs and the gateway are disabled by default and must be enabled explicitly with service options plus their host/port option blocks. Target invalidation configuration selects a `VERTX_SHARED_DATA` backend by default, with `IN_MEMORY` available explicitly for single-instance tests/local use, plus namespace, polling interval, retention factor, and target bound. Node workflows and pollers always use the registry service proxy. One local registry service is enabled by default, starts before its clients, and uses a namespace-derived address; deployments that consume a remote registry service disable the local service explicitly. Multiple local service instances require the shared-data backend.
- `IndexerNodeComponents`: explicit dependency container for node-local runtime services. Production bootstraps can replace in-memory repositories, queues, stores, event buses, command service wiring, invalid-route cache wiring, and definition providers without changing service APIs.

Plugin-enabled workflows are composed at the application/component layer, not through `IndexerNodeOptions` JSON. A load-enabled application should construct the shared core metadata repository, load repository, metadata-backed `LazyLiveWriterCatalog`, `LoadIndexerPlugin`, `IndexerPlugins`, and `SubmitIndexActionsCommandHandler` in the same bootstrap scope, then pass the resulting services through `IndexerNodeComponents`. Production lazy-live composition passes the catalog port, shared `CommandService`, and application `EventPublisher` to `LoadIndexerPlugin`. The shorter constructor creates a local exclusive-flow coordinator and uses the no-op lifecycle event bus, while the full constructor accepts application-provided coordinator and lifecycle dependencies. This keeps core node configuration free of module-specific class names and keeps metadata-adapter construction in application composition.

`CommandEngine` and `IndexerOperations` are application-scoped dependencies exposed through `IndexerNodeComponents`. Composition creates one metadata-backed operations instance and one command engine, registers cleanup before delete initiation, registers remaining core and plugin handlers, and injects the engine's `CommandService` surface into admin paths. `IndexerNode` starts the command engine before listeners and service deployments and stops it after service undeployment. `DocumentStoreCommandHandlers.register(commandEngine, config)` is the canonical core registration helper; the command-unaware `create(config)` helper is removed because it cannot compose complete chained workflows. `IndexerOperations` is the core indexer-entity lifecycle port; `MetadataIndexerOperations` is the default metadata/event implementation. It is distinct from runtime `Indexer`, provisioning operations, `IndexerDocumentIndexResourceManager`, and `IndexerQueueResourceManager`; no general physical `IndexOperations` abstraction is introduced.

Current project scope ends at provider-neutral contracts, workflows, local/in-memory adapters, composition boundaries, and conformance tests. The query implementation is specifically bounded to `InMemoryIndexerDocumentStore`; Elasticsearch, OpenSearch, and other store adapters are separate future provider scopes and are not completion criteria for this thread. Production repository implementations and durable/Kafka-backed `CommandEngine` implementations are also external integrations. Their atomicity, ordering, retry, and compatibility requirements remain documented, but implementing those adapters is not a project completion criterion.

Runtime hooks are synchronous lifecycle gates/observers around one document action; they are not a distributed side-effect transaction. A required post-action side effect must use a durable, idempotent follow-up command. If the document write and follow-up publication must be atomically handed across different durable systems, a provider-specific outbox or equivalent design must be approved rather than treating `afterWriteBeforeCommit` as an atomicity guarantee. No such command or outbox is introduced without a concrete side effect.

Command transport is reserved for work that needs durable asynchronous acceptance, partition ordering, or retry after the initiating request has completed. Request/reply services own caller-visible validation, optimistic conflicts, and returned resource state. The accepted command review classifies the current models as follows:

| Classification | Current models | Direction |
| --- | --- | --- |
| Durable action transport | `SubmitIndexActionsCommand` | Keep. Target/indexer routing and queue publication continue after producer-side acceptance. |
| Durable internal workflow | `DeleteIndexerCommand`, `PublishLoadCommand` | Keep for asynchronous cross-resource continuation. Admin delete may initiate through the service operation, while load cleanup and abandoned-candidate cleanup submit durable delete. |
| Durable cleanup | `CleanupDeletingIndexerCommand`, `CleanupResetIndexerQueueCommand`, `CleanupLoadCommand` | Keep. These commands are idempotent, reload durable state where needed, and tolerate missing resources. |
| Request/reply core operation | Target creation/recovery, indexer creation/runtime state, and queue-reset initiation are migrated | Keep these functions outside command transport; queue reset retains durable old-queue cleanup. |
| Internal core operation | Publication mark-ready, publish, and retire are migrated to `IndexPublicationService` | Keep these functions outside command transport while their final names and placement remain under review. |
| Request/reply load operation | `LoadManagementService.create`, `LoadManagementService.start`, `LoadManagementService.approvePublication`, `LoadManagementService.cancel` | Typed service operations own caller-visible load lifecycle changes. Start invokes the selected provider directly; approval and cancellation receive durable publish or cleanup acceptance before returning success. |

The request/reply command migration is complete for the reviewed groups. Remaining command models are intentional durable action, workflow, or cleanup transports. Durable follow-up submission must be confirmed before a request/reply operation reports success; handler execution completion must never be inferred from generic `CommandService.submit(...)`, whose future confirms producer-side acceptance only.

`IndexPublicationService` is the first draft request/reply boundary produced by this review. It owns typed mark-ready, publish, and retire requests, exact-version replay checks, readiness validation, provider definition resolution, and concrete index/queue resource verification. `MetadataIndexPublicationService` is the initial local implementation. A later boundary review accepted this provider-neutral grouping as correct for now; production at-most-one-published enforcement remains a repository/adapter concern rather than a reason to split the service. Missing publication/indexer state uses `IndexPublicationNotFoundException`, which preserves whether lookup used publication identity, indexer identity, or publication-by-indexer identity. Version and lifecycle incompatibilities use `IndexPublicationConflictException` with publication or indexer resource identity. Service boundaries map these domain-owned types to stable `404`/`409` tickets without inspecting messages; repository mutation races remain retryable and provider/resource failures retain their owning error. No EventBus service proxy or deployment topology is introduced in this scope because no independent remote Publication Lifecycle consumer has been approved. The service name, method names, and remote placement remain provisional before external exposure. The former publication command models, handlers, registrations, and partition resolvers are removed; tests call the service directly.

Target creation does not belong to `IndexPublicationService`. `TargetManagementService` exposes typed request/reply target creation and failed-provisioning recovery. `MetadataTargetManagementService` is the initial local implementation: it resolves target definitions and periods, creates concrete target metadata, owns target `READY`/`FAILED` transitions, returns `TargetManagementResult`, and calls provisioning/publication services only for optional nested indexer creation, readiness, and initial publishing. This Target Catalog grouping is accepted and must not be merged into publication or provisioning. Missing managed targets use `TargetCatalogNotFoundException`; incompatible lifecycle state, duplicate identity, and expected-version mismatch use `TargetCatalogConflictException`. The service boundary maps these domain-owned types to stable `404` and `409` tickets without inspecting messages. Repository mutation races remain retryable stale-state failures. The dedicated generated `TargetCatalogService` EventBus proxy combines catalog-owned list/get reads with create/recovery operations; `TargetCatalogRestVerticle` exposes the internal `/targets` OpenAPI contract and calls only a configured proxy address. Create input exposes target intent and optional `InitialPublicationMode`; the service envelope generates nested indexer resource names rather than exposing physical names to HTTP callers. The mixed `AdminService` target methods remain temporarily for compatibility while callers migrate, but new Target Catalog consumers should use the dedicated envelope. Neither envelope is approved for the public gateway. The former create-target and target-recovery command models, handlers, registrations, and partition resolvers remain removed.

`IndexerManagementService` is an accepted request/reply boundary for activate/deactivate lifecycle operations. It returns `IndexerRuntimeStateResult`, containing catalog-owned identity, desired state, and optimistic version rather than a metadata persistence record. Its metadata-backed implementation owns desired runtime-state metadata, expected-version checks, exact retry recognition, deletion fencing, metadata mutation, and lifecycle wake-ups. Missing managed indexers use `IndexerCatalogNotFoundException`; incompatible lifecycle state and expected-version mismatch use `IndexerCatalogConflictException`. The service boundary maps these domain-owned types to stable `404` and `409` tickets without inspecting messages. Repository mutation races remain retryable stale-state failures. The dedicated generated `IndexerCatalogService` EventBus proxy combines catalog-owned list/get reads with activate/deactivate; `IndexerCatalogRestVerticle` exposes the internal `/indexers` OpenAPI contract and calls only a configured proxy address. Its query and result models intentionally omit Publication state. Standalone physical creation stays in `IndexerProvisioningService`; deletion initiation stays in Cleanup Workflow; queue reset stays in Operational Queue Reset. The mixed `AdminService` indexer methods remain temporarily for compatibility while callers migrate, but new Indexer Catalog consumers should use the dedicated envelope. Neither envelope is approved for the public gateway. The former activate/deactivate and create-indexer command layers remain removed.

`IndexerQueueManagementService` is the request/reply boundary for troubleshooting queue-reset initiation under `com.inqwise.indexer.operations.queues`. Its current grouping is accepted as operational orchestration separate from indexer catalog lifecycle, runtime execution, generic provisioning, and generic command transport. `MetadataIndexerQueueManagementService` preserves expected queue/version validation, deterministic generation naming, one metadata read per attempt, exact retry behavior, lifecycle wake-up, and confirmed durable submission of `CleanupResetIndexerQueueCommand`. Admin and reset tests call the service directly. The former reset initiation command model, handler, resolver, and registration are removed; durable cleanup remains a command by design. The service name, reset method name, and remote envelope remain provisional before external exposure.

- `ServiceProxyVerticle`: shared base for Vert.x Service Proxy service verticles. It centralizes start/stop registration lifecycle while concrete services create their generated proxy handlers explicitly.
- `AdminService`: internal administration facade for metadata inspection and narrow management operations. The first slices expose target/indexer list/get operations, target creation, standalone indexer creation, failed target-provisioning recovery, indexer activation/deactivation, metadata indexer delete, and indexer queue reset through admin DTOs that hide repository-only fields such as metadata prefixes.

It uses catalog-owned read and management contracts, supports namespace-derived addresses, and does not expose metadata records or caller-selected physical indexer resource names.

Service APIs use Vert.x Service Proxy over the event bus, with typed data objects rather than raw `JsonObject` in concrete contracts. Mutating admin operations will be added one use case at a time after deciding whether each operation should return a concrete result or durable command acceptance.

The first target/action REST contract is stored under `indexer/src/main/resources/openapi/target-action.yaml` and exposes `POST /targets/{target_name}/actions`. The gateway contract is stored under `openapi/gateway.yaml` and currently exposes `GET /gateway/status`, `GET /gateway/admin/targets`, and `GET /gateway/admin/indexers`. `GatewayExposurePolicyTest` treats that method/path/operation-id set as an exact public allowlist and requires every operation to declare success plus the safe default error response; adding a route therefore requires deliberate public-policy review. The admin read routes proxy to internal admin REST, preserve the query string, forward successful upstream response bodies/content types, and use the configured admin REST base URI plus request timeout. Upstream error bodies never cross the public boundary: `400`/`422`, `404`, and `409` become safe gateway-owned invalid-request, not-found, and conflict tickets, while every other upstream failure becomes a generic `502` response. `GatewayProxyOperations` keeps upstream validation and response forwarding separate from gateway verticle lifecycle.

Deployment security is expressed through narrow `GatewayAuthenticator`, `GatewayAuthorizer`, `GatewayRateLimiter`, and `GatewayAuditSink` contracts composed by `GatewayRequestHooks`. Authentication produces an immutable `GatewayPrincipal`; authorization and rate limiting receive that principal plus immutable request metadata. Gateway generates an `x-request-id`, captures operation, method, path, and remote address, and passes the same metadata into a builder-created `GatewayAuditEvent`. Failure audit events contain a stable gateway error code rather than the original exception or credential. The audit sink returns a `Future`; failed requests are not written until that audit attempt completes, while audit-sink failure is logged and never replaces the request's public result. `IndexerNode.create(vertx, options, gatewayRequestHooks)` and the corresponding constructor let deployment composition supply the concrete policy; omitting it preserves the option-based built-in API-key/rate-limit behavior. Successful proxy responses may already be committed before completion audit finishes, so this first read-only contract is not a durable mutation-audit guarantee. Public mutations require a selected durable audit policy, including whether intent must be persisted before execution.

When `GatewayRestOptions.apiKey` is configured, `GatewayBuiltInRequestHooks` requires the matching API key header, defaulting to `x-api-key`, and produces an authenticated API-key principal; the secret is read from JSON config but intentionally omitted from `toJson()`. When `rateLimitRequests` is greater than zero, the same built-in hooks apply a per-operation/per-remote-address fixed-window in-memory rate limit using `rateLimitWindowMs`, returning a typed `RateLimited` error when exceeded. Gateway-owned failures are normalized through the shared `ErrorTicket` JSON contract so raw internal exception messages, metadata ids, physical index/queue identities, storage details, and credentials are not returned to callers. Concrete deployment identity providers, authorization policy, and durable audit sinks remain adapter choices. Target/action submission is not planned for gateway exposure unless a concrete external use case is approved.

### Document Store Publishing Model

Document-store publishing separates public target routing from physical index execution:

- `TargetDefinition` is a Target Catalog contract backed by application/static provider data, not repository metadata. It is resolved by `targetName` and controls period strategy plus whether public writes may auto-create/provision concrete targets through `autoProvisionOnWrite` and publish auto-provisioned writers through `autoPublishOnWrite`. When `autoPublishOnWrite` is omitted, it defaults to the value of `autoProvisionOnWrite`, so auto-provision-on-write targets publish generated writers by default. Target naming validation, concrete target keys, and UTC period strategy/resolution also live under `catalog.targets`; metadata repositories consume those catalog values. Physical index, queue, and indexer resource definitions live under `provisioning.definitions` and must not be imported directly by Catalog.
- Target and indexer definitions are immutable for the lifetime of a node. Definition changes require rebuilding/restarting the owning node composition; they do not emit metadata invalidation events or mutate existing hot-target composition in place.
- `TargetRecord` is the concrete target used internally for one period bucket, or the single concrete target when the period strategy is `NONE`.
- `targetName` is the public route identity and logical business target name, such as `customers`.
- concrete period target names are encoded as `{baseTargetName}--{periodKey}`, such as `customers--2026-05`.
- supported period strategies are `NONE`, `MONTHLY`, `HALF_YEARLY`, and `YEARLY`.
- period routing uses UTC.
- `indexName` is the concrete physical document-store index, such as `customers-2024-01J...`.
- the indexer id or uid identifies one durable physical index version.
- `PUBLISHED` means queryable; it does not mean immutable.
- publication state and mutation state are separate, so a valid physical index can be `PUBLISHED` and `WRITABLE`.
- multiple indexers may share one physical `indexName` when their roles and ownership make that relationship explicit, for example a `LOAD_WRITER` owner plus an attached `LIVE_WRITER`.

Repository access for document-store metadata is id-first. Identity lookup uses concrete metadata `id` or `uid`, and relationship lookup uses foreign ids such as concrete `targetId` and `indexerId`. Target definitions are resolved through `TargetDefinitionProvider`, so the repository stores concrete targets by `targetName` plus `periodKey` rather than a target-definition foreign key.

Public write requests route by `targetName` plus a timestamp when the target definition uses period routing. Command orchestration resolves the target definition from `TargetDefinitionProvider`, resolves the UTC period, loads the concrete `TargetRecord`, resolves or provisions a writable indexer for that concrete target, expands logical mutations to concrete `IndexerActionItem` payloads, and publishes those concrete actions to each resolved indexer queue. Runtime action items execute by concrete `targetId`, `indexerId`, and `indexName`.

If `autoProvisionOnWrite` is disabled and the concrete target or writable indexer is missing, the cold command fails as a stable invalid route and does not create resources. If it is enabled and the concrete target is missing, the command creates the concrete target for the resolved period. If the concrete target has no writable indexer, the command path attempts to provision the first writable indexer through `IndexerProvisioningService`. The cold path generates the physical index/queue names, resolves index and queue definitions from `provisioning.definitions.IndexerDefinitionProvider`, ensures document-index and queue resources, inserts manifest/publication metadata, and moves the concrete target through `PROVISIONING` and back to `READY`. If `autoPublishOnWrite` is enabled for that target definition, the generated writer is marked publication-ready and published through `IndexPublicationService` before the document action is published to the writer queue. Provisioning failure marks the target `FAILED`, so later writes fail fast instead of repeatedly creating indexers. Explicit target creation uses `TargetManagementService`; when a nested indexer is requested, `initialPublicationMode` is mandatory and can prepare the indexer publication as `READY` or publish it immediately.

Target creation validates its public `targetName` with the Target Catalog canonical-name rules at the core request boundary. Invalid names therefore fail before definition lookup, period resolution, metadata insertion, or optional resource generation and are not misclassified as missing definitions.

Provisioning currently creates only the concrete `INDEX` indexer type. Creation contracts do not expose `IndexerType` as a caller-selected option while it has only that one implementation. The type remains persisted catalog metadata and remains available to provider selection, queries, and views; adding another type requires its own concrete behavior and an explicit review of creation policy before widening the provisioning contract.

Target Catalog and standalone admin creation derive an owning, inactive `LIVE_WRITER`; their request DTOs do not expose role, resource ownership, or runtime state as caller-selected values. The lower `CreateIndexerProvisioningRequest` requires all three inputs explicitly because Action Routing creates active owning live writers and load workflows create load writers or attached live writers. It does not default missing workflow policy to standalone-admin behavior. New creation combinations belong in a domain workflow that establishes their invariants, not in generic admin input.

The persistence mutations `InsertTarget` and `InsertIndexer` require their complete identities and lifecycle state through validated builders. `InsertIndexer` additionally requires explicit resource names, type, role, resource ownership, publication state, and mutation state. Repository adapters must not infer classification or lifecycle from missing fields; the workflow or provisioning layer establishes it before insertion. Module-local `TestMetadataRecords` factories keep concise ready/available fixtures in `indexer` and `indexer-load` without adding production defaults to the mutation contracts.

Indexer provisioning accepts the concrete `targetId` as its only target identity. The metadata adapter reloads the canonical target before definition lookup or indexer insertion and propagates the stored target name into indexer, manifest, and publication metadata. Standalone admin creation likewise does not transport a duplicate target name. A missing target fails before indexer metadata or physical resources are created.

New provisioning requires explicit physical `indexName` and `queueName` values. It does not infer queue identity from the index name because document indexes and transport queues are separate resources with separate ownership and cleanup behavior. Nullable queue-name fallbacks remain only where historical persisted runtime models still require compatibility.

Creation contracts reject blank physical identities and apply the provisioning-owned concrete document-index guard before target or indexer insertion; wildcard, multi-index, and `_all` identities are not valid provisioning destinations. Queue-provider naming syntax remains adapter-owned, so the shared contract enforces only a nonblank queue identity.

Provisioning also requires an explicit metadata `prefix`. Unlike the canonical target name, the prefix is not redundant target identity: it groups related indexer, manifest, and publication records, and load composition may intentionally reuse it for an owning load writer and attached live writer. Creation workflows choose that family identity; provisioning rejects a missing prefix before repository or resource work.

Concrete target creation does not accept a metadata prefix. The metadata-backed Target Catalog adapter privately generates that repository identity when it inserts the target, so neither the core target contract, admin transport, nor Resource Provisioning utility exposes target persistence naming. This differs from the indexer family prefix above, whose intentional sharing is a workflow decision.

The lower persistence mutations `InsertTarget`, `InsertIndexer`, `InsertManifest`, and `InsertPublication` require an explicit non-null prefix and do not synthesize a test or production identity. Their builders require the identity and lifecycle fields owned by each mutation; `InsertIndexer` additionally requires its resource and classification state. Test fixtures state their fixture prefix explicitly and use module-local factories for common ready/available records; production workflows supply the target or shared indexer-family identity they own.

Publication-owned query routing uses `PublishedIndexQuery`, `PublishedIndex`, and `PublishedIndexResolver` under `com.inqwise.indexer.publication`. The metadata-owned `RepositoryPublishedIndexResolver` adapter loads active/ready concrete targets once, keeps only periods that overlap the half-open `fromInclusive`/`toExclusive` range, then loads available/ready/published indexers in one query. Missing concrete periods and targets with no published index return no indexes rather than failing the whole range. Results are ordered by target period and indexer id, and duplicate physical `indexName` values are collapsed so attached indexers sharing one physical index do not query it twice. Unperiodized targets match every valid range. Published writable and read-only indexes are queryable; deleting or incompletely provisioned metadata is excluded.

A target may have zero published indexes during first build and multiple writable indexes during rebuild, but metadata publication still allows at most one `PUBLISHED` indexer per concrete target. More than one published indexer for one concrete target is an invariant failure.

Hot routing keeps an in-memory view of operational targets and indexers for the action-item flow. `HotMetadataView` loads a full immutable `HotTarget` snapshot from repository target records and `IndexerProvider` results, indexes it by target name, target uid, concrete target id, and indexer id, and invalidates the whole snapshot rather than patching child indexers in place. The default view uses only active, ready concrete targets and hot-capable live writers.

`HotTarget` owns target-level routing. It resolves the request timestamp to the configured UTC target period, selects the concrete target snapshot, and routes each action to every hot live writer under that concrete target. Hot routing is batch-atomic: either every action is accepted by at least one hot indexer and grouped into `RoutedIndexActions`, or the original request falls back unchanged to `SubmitIndexActionsCommand`.

Provider-owned `HotIndexerCapability` defines final per-indexer acceptance and concrete action expansion. The provider-side `MetadataHotIndexer` implementation delegates action-specific normalization to `IndexerActionProvider.router()`. Hot metadata views consume this capability through `ResolvedIndexer`; providers do not import hot view or cache types. Candidate routing skips non-matching indexers; direct routing throws on conflicting concrete fields. This keeps action-specific rules out of the target cache and lets future providers add indexer-specific composition without changing the cache.

`HotIndexActionsService` is the hot-path entry point. It first tries a target-envelope route by `targetName` plus timestamp, then tries direct concrete routing for actions that carry an `indexerId`, and otherwise submits the original request to the command service. `RoutedIndexActionPublisher` is shared by hot routing and the cold command path for queue publication. Hot invalidation polling consumes the lifecycle-owned `TargetInvalidationRegistry`; only polling configuration and provider selection remain hot-owned.

Hot routing support also includes two guard components. `InvalidRouteCache` stores expiring invalid route signatures for stable cold failures such as missing target definitions, missing concrete targets/indexers, or missing writable indexers. `HotIndexActionsService` checks this cache before falling back to `SubmitIndexActionsCommand`; cached invalid routes fail fast instead of repeatedly entering cold submit. Retryable provisioning states and operator-recovery failures are not cached. Successful cold submission invalidates matching route signatures, so a route that becomes valid through explicit command submission or auto provisioning can clear stale cache entries before the TTL expires. `InvalidRouteMetadataChangeListener` subscribes to indexer and target metadata events. Indexer events invalidate direct target-id and indexer-id cache entries from the event, then reload the changed indexer only for target-envelope cache invalidation. Target events carry their target envelope and invalidate matching target-envelope and target-id cache entries without repository lookup, which covers explicit target creation and target-provisioning recovery.

`TargetInvalidationRegistry` is the missed-event recovery path for hot target snapshots. Its API is asynchronous so a distributed provider does not block Vert.x event loops. `MetadataChangeNotifier` is called by metadata mutation workflows after durable state is confirmed; it awaits the owning concrete target's registry mark before emitting a best-effort indexer or target metadata wake-up. Registry failure therefore fails the workflow attempt, while wake-up delivery does not delay or fail it. Idempotent already-applied paths re-mark the target so retries refresh recovery state. `TargetInvalidationMetadataChangeListener` only invalidates the node-local hot snapshot when indexer or target events arrive. `TargetInvalidationPoller` performs an initial read during node startup, then non-overlapping periodic reads. It compares the full observed entry (`version` and `expiresAt`), which detects both normal increments and version reset after an expired entry is recreated. Changed entries invalidate the owning `HotTarget`; entries no longer returned are removed from local observation state. A truncated registry result invalidates the entire hot view and clears local observations because the omitted target identities are unknown. Registry TTL is derived from poll interval times a retention factor of at least two, and the configured maximum target count must be positive.

`TargetInvalidationRegistryProvider` owns registry construction from `TargetInvalidationRegistryConfig`. The common configuration supplies a mandatory deployment namespace and the polling/retention options; backend endpoints, credentials, clients, and lifecycle remain application/provider concerns. Repeated construction for one namespace must observe the same logical registry, while different namespaces must be isolated. A distributed implementation must atomically increment one concrete target version while refreshing its TTL, may restart the version after expiry, and must set `truncated` whenever `listInvalidations(maxTargets)` omits entries. Provider selection is explicit in node composition rather than discovered through `ServiceLoader`. The default node uses `VertxSharedDataTargetInvalidationRegistryProvider`, which stores namespaced TTL entries in an asynchronous shared map and serializes each target increment with a namespaced shared lock. Regular Vert.x instances keep the data local; clustered Vert.x deployments make the same map and locks cluster-wide through the deployment's cluster manager. `InMemoryTargetInvalidationRegistryProvider` remains available for explicit single-instance tests and local composition. When the map size exceeds the requested bound, reads return an empty truncated result so pollers invalidate the complete hot view without loading an oversized entry set.

`TargetInvalidationRegistryServiceVerticle` and `TargetInvalidationRegistryServices` expose the existing registry contract as an internal EventBus request/reply service without adding another domain interface. The proxy implements `TargetInvalidationRegistry`; callers therefore use the same API for direct local injection and remote production access. Domain records are encoded only at the transport boundary, keeping Vert.x Service Proxy DTO requirements out of `indexer-core`. Service addresses include the registry namespace. Production metadata workflows await `markInvalidated(targetId)` until the backing provider confirms the version/TTL update, while pollers call bounded `listInvalidations(maxTargets)`. The reply confirms registry mutation, not that every node has reloaded. Repeated marks remain safe, and multiple service replicas are valid when the distributed provider supplies atomic updates.

Broader metadata inspection belongs to an administration layer that can load targets and indexers with wider status/state filters. Repository query-object methods such as `listTargets(TargetCatalogQuery)` and `listIndexers(IndexerMetadataQuery)` and the generic `IndexerProvider` read APIs support both hot routing and administration without baking hot-routing filters into the repository itself.

### Index Flow

Indexing uses two paths:

- Hot path: callers submit a `HotIndexActionsRequest` to `HotIndexActionsService`. A normal live-write request carries `targetName`, a timestamp, and logical document mutation items. If the cached target/indexer snapshot proves the route, the service expands the items to concrete `targetId`, `indexerId`, and `indexName` payloads and publishes them through `RoutedIndexActionPublisher`.
- Cold/unknown path: callers submit `SubmitIndexActionsCommand`, either directly or through hot-path fallback. The command supports only two routing schemas. Target-envelope mode carries `targetName`, optional timestamp, and logical document mutation actions with no concrete destination fields. Concrete mode carries no target envelope or timestamp, and every action must include a concrete `targetId` or `indexerId`; internal actions such as complete and catch-up barrier require `indexerId`. The command handler resolves writable metadata indexers by concrete `targetId`, verifies each destination, expands logical actions to concrete `indexerId`/`indexName` payloads, publishes metadata-change wake-ups only for real metadata changes such as auto-provisioned indexers, then publishes the concrete actions through the shared `RoutedIndexActionPublisher`.

Cold routing supports indexer preparation through `IndexerActionReceiveCapability`. Core asks capabilities whether a non-live candidate can receive an action with `YES`, `REQUIRES_PREPARE`, or `NO`. `YES` means the candidate is a receiver, `REQUIRES_PREPARE` lets the plugin prepare and return actual receiver indexers, and `NO` skips the candidate. Core remains responsible for forwarding the original action items to the prepared receivers.

`IndexerPlugin` is the core SPI for peer indexer functionality. The plugin surface exposes action-receive and model-scoped marker-handling capabilities through `IndexerPlugins`; application composition constructs plugins explicitly because implementations may need repositories or other runtime dependencies. Provider contracts do not depend on runtime implementations or hot-routing views.

Applications that enable load behavior should pass their plugin aggregator into `SubmitIndexActionsCommandHandler`; the plugin receives a `MetadataLazyLiveWriterCatalog` constructed from the shared metadata repository. Core defaults use `IndexerPlugins.empty()`.

Command completion means that the submitted actions were handed to the indexer queue, not that the documents were already indexed. Runtime processing remains asynchronous.

The cold path fails closed. If the command sees an unexpected indexer state or action mismatch, it must not publish actions. Expected/idempotent cases include resolving a writable, available, provisioned, runtime-active metadata indexer and waking runtime consumers that may not be hot yet.

Cold command failures use typed `CommandFailure` classification where the command layer needs retry decisions. Concurrent provisioning states, including target provisioning already in progress and target provisioning lock/version conflicts, are `RETRYABLE`. Stable invalid routes, including missing target definitions, missing concrete targets/indexers, and missing writable indexers, are `STABLE_INVALID` and may be written to `InvalidRouteCache`. Target provisioning marked `FAILED` is final for the submit command and requires explicit `TargetManagementService.recoverProvisioning(...)` before the same route should be retried.

The current fail-closed guards are:

- an unavailable or deleting indexer cannot receive new actions;
- an indexer whose provisioning state is not `READY` cannot receive new actions;
- a runtime-`NON_ACTIVE` indexer cannot receive new actions;
- cold concrete-target routing requires either target-envelope document mutations or concrete route fields so writable live writers can be resolved; load writers are not live-submit destinations;
- concrete actions with `indexerId` and `indexName` must match the resolved metadata indexer.

Routing identity fields are immutable by definition for normal lifecycle: `targetId`, `targetName`, `indexName`, `queueName`, `role`, and `type`. If these values are wrong, create a replacement indexer instead of mutating the existing record. `IndexerQueueManagementService.reset(...)` remains a narrow troubleshooting exception and must not be used as a normal reload/live-writer swap mechanism.

Failed indexer provisioning cleanup reuses the normal generic delete workflow. `DeleteIndexerCommand` moves a persisted `FAILED` indexer into deleting/non-active state, and `CleanupDeletingIndexerCommand` idempotently removes any queue or owned document index that was created before the failure, then finalizes metadata deletion. Recovery creates a replacement indexer through normal provisioning rather than mutating immutable routing identity.

Index publication is fail-closed on both metadata and external resources. `MetadataIndexPublicationService` first validates publication readiness and indexer state, resolves the provider-owned `IndexerDefinition`, and idempotently ensures the exact document index and queue definitions before changing publication metadata. Definition lookup or resource compatibility/provider failures leave the indexer unpublished for caller retry. Repeating the same request is accepted only when the indexer is `PUBLISHED` at exactly `expectedVersion + 1`; resources are checked again and metadata is not advanced. Any later version or state remains a conflict.

### Load And Reload Workflow

Durable load/reload orchestration is split between the core `indexer` module and the `indexer-load` module. Core owns indexer roles, resource ownership, runtime marker processing hooks, and generic indexer commands. `indexer-load` owns load workflow metadata, external loader contracts, and marker handlers.

- `LOAD_WRITER`: finite historical load writer for a target and physical `indexName`.
- `LIVE_WRITER`: ongoing writer. During reload, a new live writer may be linked to the load workflow and write to the same `indexName` as the load writer.
- `IndexerLoadRecord`: load-plugin metadata keyed by the core `indexerId` of the load writer. It tracks target id, load state, optional linked live writer id, persisted live-writer policy, timestamp replay window, review requirement and approval, barrier progress, and failure details. The load repository enforces one active load per target.
- `LiveWriterPolicy`: live writer creation is explicit and durable. A load may create no live writer, create one immediately, or create one lazily on the first live action when the policy allows it.

`CompleteIndexActionItem` and `CatchUpBarrierActionItem` are internal actions. External loaders should use loader-facing helpers such as `LoadWriter.submit(...)` and `LoadWriter.complete(...)` rather than constructing marker items directly. `QueueLoadWriter.submit(...)` accepts document mutations, normalizes them to the load writer's concrete `targetId`, `indexerId`, and `indexName`, and rejects mismatched concrete identities. `QueueLoadWriter.complete(...)` publishes the internal completion marker only while the load is `HISTORICAL_LOADING`; duplicate or late completion callbacks after completion, cancellation, failure, or publication are ignored. `LoadIndexerMarkerHandler` requires `CommandService` because barrier dispatch and publication are durable orchestration and must not be silently omitted.

After provider start is accepted, provider-owned source/load failures should be reported through `LoadWriter.fail(...)`. The queue-backed writer marks active loads `FAILED` with the reported reason. Late failures after the load is already `CANCELLED`, `PUBLISHED`, or `FAILED` are ignored so provider callbacks cannot overwrite terminal workflow decisions.

`LoadManagementService.create` is the request/reply load entry point. It requires an existing active, ready target identified by concrete `targetId`; it does not create or recover targets. Target creation or recovery belongs to target-management orchestration before load creation. The creation request carries provider, policy, timing, and source metadata only. Target readiness, generated load writer metadata, and optional immediate linked `LIVE_WRITER` creation go through the load-owned `LoadCreationCatalog` port, currently backed by `MetadataLoadCreationCatalog`. The port exchanges `LoadCreationTarget` and `LoadCreatedIndexer` views instead of exposing core metadata records to load workflow orchestration. The linked live writer shares the load writer's index and uses the load queue plus a `--live` suffix. The service stores the provider id and load source fields (`sourceFrom`, `sourceTo`, `sourceQuery`, `sourcePlaybookId`) in `IndexerLoadRecord`, publishes metadata-change wake-ups, and persists the load as `CREATED`. It does not start the provider.

`LoadManagementService.start` owns provider acceptance. It moves `CREATED` to `STARTING`, resolves the application-level `LoadProvider` from `LoadProviderRegistry`, asks `LoadCreationCatalog` to build the provider start context from durable target/load/indexer metadata, calls `LoadProvider.start(...)`, and moves the load to `HISTORICAL_LOADING` only after the provider accepts the asynchronous job. The `LoadRequest` includes both source fields and concrete callback identities such as `targetId`, `indexerId`, optional `liveIndexerId`, `providerId`, `indexName`, and `queueName`. `LoadProvider.start(...)` must mean accepted asynchronous work, not historical load completion. Retrying start for a load already in `STARTING` is allowed; providers must treat `LoadRequest.indexerId` as the start idempotency key and accept/resume repeated start calls for that same load. An exact retry after the load already reached `HISTORICAL_LOADING` returns the current successful state instead of invoking the provider again.

`LoadWriterActionReceiveCapability` is the cold-submit integration for lazy live writers. A `LOAD_WRITER` returns `REQUIRES_PREPARE` for live document actions only while an active load has `LiveWriterPolicy.CREATE_ON_FIRST_LIVE_ACTION` and no linked live writer. `prepareToReceive(...)` is the lazy-live preparation workflow boundary: it creates or reuses the linked `LIVE_WRITER`, attaches it to the load, returns that writer as the actual receiver, and the core submit command publishes the original live action items to it. The core action-receive SPI exchanges `IndexerModel` routing/catalog views after metadata validation and no longer exposes `TargetRecord` or `IndexerRecord` to plugins. Lazy live-writer metadata access goes through the load-owned `LazyLiveWriterCatalog` port, currently backed by `MetadataLazyLiveWriterCatalog`, which maps metadata records to `IndexerModel` at the adapter boundary. The durable safety primitive for production is an atomic attach-if-absent operation on the load record's existing `liveIndexerId` and version; no extra lock, claim, or session field belongs in load metadata. After the live writer is linked, the same `LOAD_WRITER` returns `NO` for live actions and is never a live action receiver.

When a lazy-live candidate loses atomic attachment or is abandoned after a stale-version retry, load orchestration submits the generic `DeleteIndexerCommand` with the candidate version and emits `LAZY_LIVE_WRITER_PREPARATION_CONFLICT` through `indexer-events`. Cleanup is best-effort and never blocks routing to a valid winner or changes the stale-state retry result. `cleanupSubmitted=true` means the command transport accepted cleanup and `cleanupSucceeded` remains null because distributed deletion has not completed. Rejected cleanup submission emits `CLEANUP_FAILED` with `cleanupSubmitted=false` and `cleanupSucceeded=false`. The cold command id is propagated as the event correlation id.

`LoadIndexerPlugin` exposes load-module peer behavior through the core `IndexerPlugin` SPI. It contributes `LoadWriterActionReceiveCapability` and model-scoped runtime marker handling for `LOAD_WRITER` and `LIVE_WRITER` roles while keeping load metadata and workflow dependencies in `indexer-load`. The plugin depends on the load-owned `LazyLiveWriterCatalog`; application composition selects `MetadataLazyLiveWriterCatalog` rather than allowing runtime integration to construct a metadata adapter. `IndexerRuntime` resolves marker handling through application-supplied `IndexerPlugins`; zero matching plugins retain the explicit failing handler, and multiple matching handlers are rejected as ambiguous.

Load-enabled applications assemble the module explicitly. The application constructs `MetadataLoadPublicationRepository` from the core metadata repository and supplies it as the `LoadPublicationRepository` and `LoadCleanupRepository` ports in `LoadCommandHandlers.Config`; `LoadCommandHandlers.register(...)` then registers publish and cleanup handlers against the shared `CommandEngine` without constructing metadata adapters. The application constructs `MetadataLoadCreationCatalog` from the metadata repository and supplies that load-owned port with the load repository, queue client, provider registry, lifecycle event bus, and command service to `DefaultLoadManagementService`. It also constructs `MetadataLazyLiveWriterCatalog` from that metadata repository and supplies the catalog with the remaining load dependencies to `LoadIndexerPlugin`; the plugin is then passed to runtime and cold-submit composition through `IndexerPlugins`. Core node JSON options and default node wiring remain load-free.

Load entry-point ownership and its internal transport envelope are accepted. Create, start, recover-created, approve-publication, and cancel are caller-visible request/reply functions exposed through the load-owned generated `LoadService` EventBus proxy and `LoadServiceVerticle`. `LoadRestVerticle` owns the OpenAPI-backed internal REST adapter and calls only the configured EventBus proxy address. `POST /loads` and grouped `POST /admin/loads` return `201`; start, recover-created, and approval return `200` with the resulting load view; cancellation returns `202` only after `LoadManagementService.cancel` has persisted cancellation and received durable cleanup acceptance. The grouped `/admin/loads` paths are aliases owned by the load REST contract so load state and workflow control do not move into the core `AdminService`. Service DTOs map to the domain API and return a controlled load view rather than `IndexerLoadRecord`. The REST API is internal and is not part of the public gateway allowlist. `PublishLoadCommand` and `CleanupLoadCommand` remain durable internal workflow commands.

The migration also closes current retry gaps. Creation performs multiple non-atomic inserts and cannot be safely redelivered through command transport because a partial attempt can duplicate composition; request/reply creation therefore fails to the caller. The `CREATED` load is the explicit start/recovery point. `LoadManagementService.recoverCreated` requires its indexer id and exact load version, verifies that the load remains `CREATED`, and delegates to `start`; it never recreates composition. Blindly repeating creation is invalid because an active load already exists. Approval recognizes an exact retry only when the load is `APPROVED` at the requested version plus one and all approval fields match; it resubmits publication without another mutation and rejects later or conflicting versions. Cancellation recognizes an exact retry only when the load is `CANCELLED` at the requested version plus one; it does not stop the provider again and resubmits cleanup without another mutation. Cancellation reason is provider-stop context rather than persisted retry identity. Cleanup atomically replaces the active load record with a minimal `IndexerLoadCompletion` tombstone containing terminal state, terminal version, and completion time. This lets an exact cancellation retry succeed after cleanup while unknown ids and mismatched completions still fail. Tombstone retention is repository policy; the production adapter must persist finalization and tombstone insertion in one transaction. `IndexerLoadRepositoryCompletionContract` provides reusable adapter conformance tests for terminal cleanup finalization, stale-version rollback, retained completion identity, and target reuse after cleanup.

Publication and cleanup orchestration receive a narrow `LoadIndexerReference` containing only indexer id, target id, and optimistic version. Physical index names and the rest of the indexer persistence record remain inside the metadata adapter because neither orchestration flow consumes them.

Historical-only loads publish the `LOAD_WRITER` after successful completion unless review is required; publication converts that indexer role to `LIVE_WRITER` while preserving physical index ownership. Reviewed historical-only loads move to `WAITING_FOR_REVIEW`. For a load with a linked live writer, completion atomically persists a generated barrier id and timestamp with `CATCH_UP_BARRIER_REQUESTED` before submitting a concrete `CatchUpBarrierActionItem` through the generic action command. A completion-command retry reloads and resubmits the same persisted marker identity. The live writer's ordered queue makes consuming that marker proof that earlier catch-up items were consumed; the timestamp is informational and does not depend on synchronized node clocks. Repository barrier completion accepts only the requested id and timestamp, then moves to `CATCH_UP_READY` or `WAITING_FOR_REVIEW`. Missing active load metadata for a late duplicate marker is an idempotent cleanup miss.

Loads with live support publish the linked `LIVE_WRITER` after historical completion, catch-up barrier processing, and optional review. `PublishLoadCommand` validates the load state, candidate writer state, optional approval, and catch-up barrier before calling the atomic metadata replace primitive. When a linked live writer is published, ownership moves from the load writer to the linked live writer and the old published writer is retired.

Direct lifecycle operations use exact optimistic-concurrency replay rules. Publication accepts an already-published record only at `expectedVersion + 1`, revalidates readiness and resources, and does not advance metadata again. Retirement likewise accepts only a `RETIRED` record at `expectedVersion + 1` as its own completed retry. Activate and deactivate commands currently require an expected indexer version and recognize only the corresponding runtime state at `expectedVersion + 1` on a non-deleting indexer; this prevents deactivation from claiming a deletion transition that produced the same runtime state. Exact replay republishes the metadata wake-up without another mutation. Mark-ready recognizes an exact retry only when the publication is `READY` at `expectedVersion + 1` and its persisted reason equals the request reason. Any later version remains a conflict even when a record has returned to the requested state, so stale requests cannot claim an unrelated transition.

Core command redelivery follows these explicit contracts:

| Command group | Redelivery contract |
| --- | --- |
| Publish, retire, activate, deactivate, mark-ready, target recovery | Recognize only the exact resulting state at the expected next version; later versions conflict. Wake-up-producing commands reissue the wake-up without another mutation. |
| Target/indexer creation | Provisioning owns durable identity and concurrent-create resolution; command retry reloads or reuses the persisted resource. |
| Indexer deletion | An existing `DELETING` record re-confirms invalidation and resubmits cleanup regardless of the initiating version. A missing record is completed cleanup. |
| Queue reset | Exact resulting queue identity and next version resubmit wake-up and old-queue cleanup without creating another generation. |
| Physical cleanup | Missing queue, index, or metadata records are successful cleanup misses; real provider failures remain retryable failures. |

Target provisioning recovery follows the exact contract: `ACTIVE`, `READY`, and `expectedVersion + 1` identify its completed result. Exact request retry republishes target invalidation without advancing metadata, while every later version conflicts even if the target later returns to `READY`.

`LoadManagementService.approvePublication` is accepted only for a review-required load in `WAITING_FOR_REVIEW`. It records `approvedAt`, `approvedBy`, and `approvalReason`, moves the load to `APPROVED`, and submits `PublishLoadCommand`. This prevents early approval from replacing historical or catch-up progress state. Marker handling auto-publishes non-reviewed loads when a command service is supplied: historical-only loads publish after the completion marker, and linked live loads publish after the catch-up barrier marker.

`LoadManagementService.cancel` marks the load `CANCELLED` and submits durable cleanup for the load writer and optional linked live writer. A `CREATED` load has not been accepted by a provider yet, so cancel skips provider stop. `STARTING` and later active states resolve the stored provider id from `IndexerLoadRecord` and stop that provider before cancellation. Published loads are not cancellable through this operation.

`LoadAwareIndexerEventPublisher` is the load-side runtime failure bridge. It observes `ACTION_ITEM_FAILED` events, finds an active load for the failing indexer id, marks the load `FAILED`, attempts to stop the stored provider, and then delegates the original event. Runtime processing stays generic; load workflow state remains in `indexer-load`.

Cross-module event publication uses the separate `indexer-events` module under `com.inqwise.events`. Its initial API consists of typed `EventChannel<T>` metadata (`name` and `payloadType`), `EventEnvelope<T>` (`eventId`, `eventType`, `occurredAt`, `source`, optional `correlationId`, and payload), and an `EventPublisher` whose generic `publish(channel, envelope)` returns `Future<Void>`. Publisher completion means that the configured transport accepted the event; it does not mean consumers processed it. Event ids and timestamps are assigned before publication so retries can reuse the same identity. The initial module supplies no-op and recording in-memory publishers; subscriber APIs and distributed transport implementations are added only with concrete consumers. Domain modules continue to own payloads, channel constants, consumers, and channel-specific delivery requirements. Lifecycle invalidation, runtime processing events, and load operational conflicts may therefore share transport infrastructure without becoming one event stream or adopting the same reliability policy. Load operational conflicts are the first consumer; migration of the existing lifecycle event bus is a separate follow-up scope.

Shared exclusive-flow coordination is implemented in the separate `indexer-coordination` module under `com.inqwise.coordination`. Its generic execution API accepts a flow key, concrete result `Class<T>`, and `Handler<Promise<T>>`; `LocalExclusiveFlowCoordinator` creates one shared promise, invokes only the first caller's handler for an active key, and returns that promise's future to the owner and local waiters. Success values and the original `Throwable` failure are shared, the key is released after either outcome, different keys remain independent, and an active-key call with a different result class fails immediately. Lazy-live integration wraps only `prepareToReceive(...)` under `load-live-writer:{indexerId}` and shares `PreparedIndexers`; action publication remains outside coordination so every cold submit forwards its own action items exactly once. A distributed implementation will encode successful results through a general extensible value-codec registry. At the current stage, the concrete result class is the codec identity and only one codec is allowed per concrete type; raw generic result types are unsupported. Explicit codec ids, format versions, and portable failure encoding are deferred until a distributed provider is implemented. Coordination reduces duplicate work but never replaces atomic repository correctness or abandoned-candidate cleanup for cross-node races.

Final indexer deletion is generic command orchestration, not runtime-node or load-plugin resource ownership. `DeleteIndexerCommand` first persists `DELETING` and `NON_ACTIVE`, publishes metadata invalidation, and asynchronously submits `CleanupDeletingIndexerCommand`. `IndexerOperations.markDeleting(...)` returns the catalog-owned `IndexerDeletionResult`, including the resulting fence state and optimistic version rather than a persistence record. Admin reloads the marked record before command submission because a local command engine may complete physical cleanup synchronously. Runtime reconciliation closes only its local producer and consumer handles. The cleanup command reloads and validates the deleting indexer, idempotently deletes its queue, and deletes the document index only for `IndexResourceOwnership.OWNER`. After physical cleanup, one atomic repository `finalizeIndexerDeletion(indexerId, expectedVersion)` operation verifies `DELETING`, deletes publication and all manifest metadata for the indexer, and deletes the core indexer record in one metadata transaction. Repeating finalization after the record is absent succeeds idempotently. Publication and manifest rows are operational metadata; durable history belongs in audit/operational events. Missing resources and records are successful cleanup misses, while real storage failures fail for command retry. The initial workflow fences routing but does not wait for closure acknowledgement from every runtime node; strict in-flight consumer acknowledgement is deferred. Plugin-owned load metadata is finalized separately.

Document-index ownership transfer must complete before deletion starts. `DELETING` is a terminal mutation state and cannot transition back to writable or read-only. Once deletion begins, `IndexResourceOwnership` and queue identity are immutable. Atomic `replacePublishedIndexer(...)` rejects a deleting candidate, previous publisher, or ownership source before changing any participant. This prevents cleanup from reading `OWNER` and deleting a physical index after ownership has concurrently moved. The resource manager remains metadata-independent: orchestration calls it only for `OWNER`, while `ATTACHED` always skips physical index deletion.

Production `finalizeIndexerDeletion(...)` implementations must lock the existing indexer row inside one transaction, treat an absent row as idempotent success, reject a version mismatch with `RetryableStaleStateException`, and reject an existing row outside `DELETING` as a final domain conflict. Publication rows, all manifest rows, and the indexer row are then deleted in that order and committed together. `READ COMMITTED` with an indexer-row lock is sufficient: concurrent finalizers serialize and later callers observe the committed missing row. Any validation or storage failure rolls back all metadata deletion. No lock, claim, or deletion-session fields are added. `DocumentStoreMetadataRepositoryDeletionContract` provides reusable adapter conformance tests for atomic cleanup, rollback behavior, missing-row retries, and concurrent finalization.

Core lifecycle transitions are exposed through an injected `IndexerOperations` port. Its first operation, `markDeleting(MarkIndexerDeletingRequest)`, owns expected-version validation, transitions to `DELETING` and `NON_ACTIVE`, publishes lifecycle invalidation through the metadata-backed implementation, and returns the updated `IndexerRecord`. The port may absorb other cohesive core lifecycle operations later, but this slice does not move unrelated behavior speculatively. `DeleteIndexerCommandHandler` and `AdminServiceImpl` share this operation before submitting cleanup. `IndexerOperations` does not own physical resource cleanup, command chaining, load behavior, or provisioning; those remain in their existing orchestration and provisioning components.

Delete initiation and cleanup are idempotent. `markDeleting(...)` returns an empty result for an absent indexer, returns the current record for an already-deleting indexer regardless of the original requested version, and otherwise requires the expected version before transitioning. `DeleteIndexerCommandHandler` submits versionless `CleanupDeletingIndexerCommand(indexerId)` and requires `CommandService`; cleanup cannot be silently omitted. Every cleanup attempt reloads the current deleting indexer snapshot, uses its immutable resource identities and ownership, and passes that snapshot version to atomic metadata finalization. Missing records succeed and non-deleting records fail. A metadata change between resource cleanup and finalization produces `RetryableStaleStateException`; retrying the same command reloads a fresh snapshot and can make progress without a special restart command.

`CommandFailureClassifier` is the generic command-execution failure boundary for a future durable executor. Explicit `CommandFailure` kinds remain authoritative even when wrapped. Application/provider rules run next and can classify concrete transport, timeout, authentication, configuration, and domain exceptions without coupling generic command infrastructure to those exception packages. `causeType(...)` builds a generic rule that examines the full cause chain. Application composition registers `RetryableStaleStateException` as `RETRYABLE`; core defaults classify argument and state failures as `FINAL` and otherwise unknown failures as `RETRYABLE`. Unknown retries are bounded when the concrete engine has a durable attempt mechanism. `InMemoryCommandEngine` remains inline and returns handler failures directly; it does not schedule retries.

`CommandProcessor` is transport-neutral and never acknowledges, delays, retries, or publishes failure records. It resolves a handler, invokes one attempt, and converts synchronous and asynchronous failures into `CommandExecutionOutcome.Failed(failureKind, originalError)`. Missing handlers and null handler futures are final failures. Resource engines consume this outcome and decide whether to commit, pause/seek, or publish a terminal failure according to their own delivery guarantees.

`CommandEnvelope` is the transport value contract. It owns the stable transport `commandId`, command type, positive schema version, creation timestamp, optional correlation id, and a defensive copy of domain payload JSON. Domain payloads do not own transport identity. Action submission retains correlation through the generic `Command.getCorrelationId()` metadata surface, not inside its payload. `GenericCommand` carries decoded type, correlation, and payload into the existing handler reconstruction flow. `CommandEnvelopeCodec` provides UTF-8 JSON byte encoding without Kafka dependencies. Partition key remains separate transport metadata, and attempts, retry deadlines, leases, and delivery state are not encoded in the envelope.

Command partition routing is owned by the command-service layer and requires no metadata or provider queries. `CommandPartitionKeyRouter` resolves a registered command type to a namespaced `CommandPartitionKey`: target-scoped work uses `target:{id}`, and indexer lifecycle and load lifecycle use `indexer:{id}`. Domain command sets register resolvers explicitly through `RoutingCommandPartitionKeyResolvers`, `CleanupCommandPartitionKeyResolvers`, and `LoadCommandPartitionKeyResolvers`; the generic router has no built-in domain commands. Missing resolvers, missing identities, duplicate registrations, and mixed-resource action batches are final submission failures. Logical action submissions use target name. Concrete action batches use one shared target id when every item carries it, otherwise every item must carry one shared indexer id. This ordering scope coordinates commands for a resource; document/peer ordering inside indexer queues remains the responsibility of those queues.

`CommandRetryPolicy` is a pure application-configured decision model for engines that can track attempts. It accepts maximum attempts, initial and maximum delays, an exponential multiplier, and a jitter ratio; no operational timings are hardcoded in the library. `failedAttempts` counts completed handler executions, so the first failed attempt uses the initial delay and a retryable failure becomes `EXHAUSTED` when `failedAttempts >= maxAttempts`. Decisions are explicit `RETRY`, `FINAL_FAILURE`, or `EXHAUSTED`; only `RETRY` carries a delay. State belongs to the concrete command resource rather than a mandatory core repository. A same-record Kafka engine can pause and seek an uncommitted partition while continuing to poll, but its local delay and attempt count are lost on rebalance; durable maximum attempts and exhaustion therefore require retry-topic metadata or another Kafka-owned state mechanism and are deferred.

The planned Kafka engine disables auto-commit and processes commands sequentially per partition. Handler success is followed by offset commit; commit failure permits redelivery. Retryable failure leaves the offset uncommitted, seeks back to the failed offset, pauses only that partition, continues polling for heartbeats and other partitions, and resumes after a local deadline. Final failures must be published to a durable failure topic before the source offset is committed; Kafka transactions may later make failure publication and offset commit atomic. A generic delivery object does not expose `retry(delay)` because Kafka has no broker-managed delayed redelivery. The engine interprets handler failure and applies its resource-specific retry mechanism. Kafka client implementation is outside the current scope.

Load-owned terminal cleanup uses one `CleanupLoadCommand` rather than publication-specific cleanup. For `PUBLISHED` historical-only loads it deletes only the previously published indexer and retains the former load writer that became the published live writer. For `PUBLISHED` loads with a linked live writer it deletes the previous published indexer and historical load writer while retaining the linked published writer. For `CANCELLED` loads it deletes both load and optional linked live writers. `FAILED` loads remain inspectable until explicitly cancelled. The handler reloads terminal load metadata, submits versioned generic delete commands for every removable indexer, waits only for durable command acceptance, and then deletes the load row with expected-version protection. Missing load/indexer records are idempotent success. Without a durable `CommandService`, the load row remains because cleanup has not been durably accepted.

When `PublishLoadCommandHandler` is wired with a command service, successful publication submits `CleanupLoadCommand`. Cleanup reloads current metadata versions, uses the generic `DeleteIndexerCommand` path for removable writers, and deletes the terminal load row after those commands are accepted.

Timestamp-based live catch-up uses the configured replay window to decide which live actions are copied to the candidate writer. Duplicate/retry safety is assumed only inside the same partition/key ordering scope.

### Lifecycle

- `activate()`: starts the root indexer once. It activates the queue consumer/listener, resumes consumption, and emits `INDEXER_STARTED`. Repeated calls are idempotent.
- `unregister()`: closes the active consumer/listener.
- `openProducer()` / `closeProducer()`: open or close the producer-side queue publisher for this indexer.
- `openConsumer()` / `closeConsumer()`: open or close the consumer-side processor for this indexer.
- `close()`: closes local producer and consumer handles. It does not delete queue resources or drop document-store indexes.
- `delete()`: retained as a local runtime close operation that returns the model. Destructive cleanup belongs to command orchestration.

### Distributed Lifecycle Commands

Indexer lifecycle request/reply operations express desired state and return the resulting metadata view to the caller. Activation and deactivation update `DocumentStoreMetadataRepository` runtime state/version and publish an `IndexerMetadataChanged` wake-up with the indexer id, owning concrete target id, operation type, and resulting version. `IndexerRuntimeState.ACTIVE/NON_ACTIVE` is a consumer-control switch only; it does not change publication state, mutation state, provisioning state, or indexer availability. These operations do not need durable command transport; runtime convergence follows durable metadata plus wake-up and reconciliation mechanisms.

The metadata-change notification is a fan-out wake-up for runtime nodes and local caches, not the source of truth. `IndexerRuntimeReconciler` owns lifecycle subscription, metadata loading, event coalescing, and serialized reconciliation; event callbacks only coalesce the indexer id and highest observed event version before waking its worker. `IndexerRuntime` is repository-independent and remains responsible only for local runtime transport instances and their activate, replace, close, and status operations. Target metadata changes use the same lifecycle event bus for cache invalidation, but do not drive runtime indexer reconciliation by themselves. Runtime construction can use the Verticle-backed constructor so active indexers deploy an `IndexerProcessorVerticle` while `IndexerRuntime` never exposes Vert.x deployment ids.

`IndexerMetadataChanged` delivery is one-way. A publisher never waits for a runtime node to reconcile or reply. `IndexerLifecycleEventBus.publishIndexerWakeUp(...)` schedules the provider publication without exposing its completion to orchestration, so durable metadata mutation success does not depend on event delivery success. The underlying asynchronous `publish(...)` result represents provider acceptance only and remains available to provider implementations and tests. Publish failures are provider-owned operational signals for logs and metrics; startup and safety resynchronization remain the correctness path. Command, provisioning, administration, and load workflows use the one-way API after durable state changes.

`IndexerLifecycleEventBusProvider` owns explicitly selected lifecycle-bus construction from a mandatory deployment namespace. Equal namespaces share one logical event channel and different namespaces are isolated. `VertxIndexerLifecycleEventBusProvider` uses the regular Vert.x EventBus API with `publish`, native `JsonObject` transport, and closeable consumers; the same implementation works locally or across nodes when deployment supplies clustered Vert.x. Cluster creation, discovery, and reconnect monitoring are deployment concerns, and the provider neither adds cluster dependencies nor checks clustered mode. Default node composition uses this provider, while `InMemoryIndexerLifecycleEventBusProvider` remains available for isolated unit tests. The generic `indexer-events` module continues to carry operational event-publishing primitives and is not the lifecycle wake-up transport.

The Vert.x provider wraps each event payload with `published_at_epoch_ms` at transport publication. A receiving handle reconstructs the domain event, compares transport age with `lifecycle_events.max_transport_lag_ms` (30 seconds by default), and emits a local `EXCESSIVE_LAG` signal when the threshold is exceeded. Malformed envelopes and consumer transport exceptions emit local `DELIVERY_LOST`. Signals are throttled independently by type through `lifecycle_events.signal_cooldown_ms` (60 seconds by default). Deployment metrics integrations can report concrete or suspected health conditions through `reportProviderSignal(...)`; the provider applies the same local cooldown. Cross-node timestamp lag assumes reasonably synchronized wall clocks, so production thresholds must include expected clock skew. Publish completion means only that the event was accepted by the local EventBus API, never that subscribers processed it.

Lifecycle subscriptions return an `IndexerLifecycleSubscription` close handle. `IndexerRuntimeReconciler` subscribes once to indexer wake-ups and once to provider signals before startup synchronization, retains both handles, and closes the signal subscription before the indexer subscription during shutdown. Starts are idempotent, and a stopped node cannot reactivate from later wake-ups. Providers can emit `RECONNECTED`, `DELIVERY_LOST`, and `EXCESSIVE_LAG`; every signal clears pending single-indexer work and coalesces into the reconciler's serialized full-synchronization flag. These signals are not durable workflow state. Production delivery fans out wake-ups to runtime nodes, at-least-once delivery is acceptable, global ordering is unnecessary, and duplicate events may be coalesced because reconciliation reloads current repository state. Durable replay may reduce convergence time but is not the runtime correctness boundary.

The accepted node-side reconciliation design uses a bounded dirty-indexer map plus a full-resynchronization flag. `IndexerRuntimeReconcilerOptions.maxDirtyIndexers`, exposed to default node composition as `runtime_reconciler.max_dirty_indexers`, defaults to 10,000 and must be positive. Existing ids continue to coalesce at capacity; when a new distinct id would exceed capacity, the worker discards the individual pending ids and requests one full synchronization. An event callback only records the indexer id and maximum observed version and wakes the worker; it performs no repository or runtime work. Node start, provider reconnect, delivery loss, excessive lag, dirty-map overflow, periodic safety intervals, and detected local tracking inconsistencies request full synchronization. `runtime_reconciler.safety_sync_interval_ms` is mandatory-positive and defaults to five minutes. The reconciler starts its Vert.x periodic timer only after startup convergence, routes ticks through the same coalesced full-sync flag, and cancels the timer before subscription shutdown, so slow scans never overlap and stopped nodes receive no timer work. High CPU cannot by itself prove event loss, so provider signals and periodic repository comparison cover that case. Subscriptions are created once per node start; providers own reconnection and resubscription. Stopping the node closes subscriptions and discards pending transient work because the next start performs a full synchronization.

Metadata-event single-indexer reconciliation reloads repository truth and closes the local runtime when the record is absent, unavailable, deleting, not ready, or non-active. Otherwise it activates a missing runtime, leaves an identical runtime unchanged, or closes and replaces a runtime whose queue name or metadata version changed. When the loaded version is lower than the highest observed event version, the worker reloads immediately once; a still-stale id remains dirty for the next event or safety synchronization. Runtime candidates are registered only after activation succeeds, and a failed candidate is closed best-effort so failed activation cannot remain visible in the runtime map. Unexpected repository, construction, activation, or close errors fail reconciliation.

Full synchronization subscribes before reading metadata, loads the authoritative runtime-eligible indexer set, reconciles desired records sequentially in id order, closes every local runtime absent from that desired set, and then drains events accumulated during the scan. Normal action and runtime services become available only after startup synchronization converges. `listRuntimeActiveIndexers()` excludes deleting records. Metadata-driven reconciliation leaves an identical local runtime in place, while the local-node manual `reconcileIndexer` operation force-closes the selected runtime and recreates it from freshly loaded durable metadata; this provides an explicit broken-consumer recovery primitive without persisting workflow state in `Indexer`. A failed action remains uncommitted at the queue head and leaves its consumer paused. Manual recovery therefore redelivers that action before later items. `ACTION_ITEM_FAILED` must not automatically invoke recovery until a bounded retry, backoff, exhaustion, and operator-visibility policy exists, because an unconditional callback would repeatedly recreate the runtime around a poison item. An unexpected asynchronous reconciliation failure stops the reconciler subscription and all local runtimes before notifying `IndexerNode`, which enters recovery-only mode by undeploying target-action, runtime, REST, and gateway data-plane services while retaining admin deployments, repository access, metadata listeners, and command infrastructure. `IndexerNode.recover()` resubscribes, performs startup full synchronization, and redeploys the configured data plane only after convergence; failed recovery keeps the node in recovery-only mode. Exposing this operation through a restricted recovery-admin endpoint is deferred to the separate services-envelope scope. No durable reconciliation state or event backlog is introduced.

Production lifecycle-event consumers have separate correctness boundaries. Hot target snapshot correctness is backed by `TargetInvalidationRegistry`, so missed metadata events are recovered by registry polling. Invalid-route cache invalidation is a latency optimization and remains bounded by cache TTL. Runtime correctness comes from comparing local runtime state with durable indexer metadata during startup and safety resynchronization, while events only reduce convergence latency.

Runtime reconciliation opens a consumer only when the persisted indexer has catalog state `IndexerStatus.AVAILABLE`, `IndexerProvisioningState.READY`, and `IndexerRuntimeState.ACTIVE`. Otherwise, including `MutationState.DELETING`, it only closes the local runtime indexer. Destructive resource cleanup is performed once through command orchestration rather than independently by every runtime subscriber.

Indexer-scoped queue reset is an orchestration workflow, not an `Indexer` runtime method. Reset is a troubleshooting mechanism whose initial semantics are that future writes move to a clean queue, not that every old in-flight item is synchronously proven dead. `ResetIndexerQueueRequest` carries the expected queue name and metadata version. The queue-management service provisions a deterministic versioned queue, updates metadata with expected-version protection, and recognizes exact request retry when the resulting queue/version is already applied, re-emitting the wake-up without advancing another generation. It publishes the deterministic resulting version directly after mutation instead of reloading metadata that may already contain a later concurrent transition. Negative expected versions and `Long.MAX_VALUE` are rejected before queue provisioning because they cannot produce a valid next generation. A final `-vN` suffix is stripped only when `N` equals the expected metadata version; this prevents a custom old queue name from becoming a later generated queue identity. After metadata advances, reset submits `CleanupResetIndexerQueueCommand` with the exact retired queue name. Cleanup uses the generic command service, deletes only that queue, and relies on the resource-manager contract that missing queues are idempotent success. Cleanup submission failure does not roll metadata back: reset fails for caller retry, and exact retry resubmits the same cleanup without provisioning another queue. For Kafka, prefer advancing a queue generation in metadata and publishing through a new generated topic name over deleting and recreating the same topic name in place. Runtime nodes learn the new queue name through metadata-change fan-out and reconcile onto the new consumer. Strict old-consumer fencing or distributed close acknowledgement can be added later if reset must provide stronger "old items cannot be processed" guarantees.

## Model Construction

Production application code creates every data-bearing model through its builder, regardless of whether the model is implemented as a record, POJO, command, request, result, event, definition, entity, view, persistence model, or Vert.x transport DTO. Builders validate required values and defensively copy mutable input. Framework-required constructors and setters remain available for serialization, code generation, reflection, and persistence, but are not the normal production construction API. Test setup, fixtures, fakes, and test-only objects may use direct construction.
