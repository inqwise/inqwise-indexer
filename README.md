# inqwise-indexer

Vert.x 5.x starter library inspired by `vertx-elastic`, with a modular layout:

- `inqwise-common`: shared data objects and indexing request models.
- `inqwise-indexer-core`: stable indexing action payloads, runtime ports, action/provider/hot-routing contracts, command contracts/execution primitives, provisioning contracts/utilities, operations ports, definitions, metadata contracts/models, and shared error primitives. It has no dependency on deployment services, node wiring, REST, gateway, or local adapter implementations.
- `inqwise-indexer-events`: typed cross-module event publication contracts and local publisher implementations.
- `inqwise-indexer-coordination`: keyed exclusive-flow coordination contracts and the local shared-promise implementation.
- `inqwise-indexer`: command handlers/orchestration, hot routing implementations, provisioning orchestration, operations implementations, runtime implementations, service communication, node wiring, REST/gateway APIs, and default local adapters. It depends on `inqwise-indexer-core`.
- `inqwise-indexer-load`: load/reload orchestration helpers and load-specific metadata around the core indexer primitives.
- `inqwise-client`: client-side wrappers for the indexer service.
- `inqwise`: top-level facade for index actions and load orchestration.

## Indexer Behavior

Core types retain the `com.inqwise.indexer` package while Maven module dependencies enforce ownership: `indexer` may depend on `indexer-core`, while `indexer-core` must not import deployment or adapter code from `indexer`. The current extraction owns stable action payloads, runtime ports, action/provider/hot-routing contracts, command payloads, command engine SPI, command envelope/partition/retry/failure primitives, provisioning contracts/utilities, operations ports, definitions, metadata contracts/models, and shared error primitives. Command handlers, hot-routing services/listeners/local caches, provisioning orchestration, metadata-backed provider composition, operations implementations, node wiring, service facades, and concrete runtime/local implementations remain in `indexer`; those move only in later cycle-free slices.

`inqwise-indexer` provides a controlled transport pipeline for gently moving structured actions into a targeted document store:

- `Indexer`: front object for one internal indexer. It owns producer-side submission into the indexer queue, validates concrete action identity, delegates action-specific document writes to `IndexerAction`, and delegates consumer lifecycle to an `IndexerProcessor` when one is provided.
- `IndexerRole`: declares the indexer responsibility. `LIVE_WRITER` handles ongoing action streams. `LOAD_WRITER` handles finite historical loads.
- `IndexResourceOwnership`: declares whether an indexer owns the physical document index resource. Cleanup deletes a document index only for an `OWNER`; `ATTACHED` writers may share the same `indexName` without owning deletion.
- `IndexerProcessor`: consumer-side runtime abstraction. `VerticleIndexerProcessor` deploys an `IndexerProcessorVerticle` and hides the Vert.x deployment id.
- `IndexerProcessorVerticle`: owns queue consumption for one indexer, including pause, process, commit, and resume. It receives only an `ActionItemProcessHandler`, not the whole `Indexer`.
- `IndexerQueueClient`: buffer client abstraction for publisher and consumer handles. Production implementations can use Kafka or another durable transport. `InMemoryIndexerQueue` is a simple local/test implementation.
- `IndexerQueueResourceManager`: admin-side abstraction for ensuring and deleting queue resources. Queue provisioning and deletion are not part of the shared runtime queue client surface. Provisioning may receive provider-owned `QueueDefinition` settings; implementations should make `ensure` idempotent for compatible existing resources and fail when an existing resource is incompatible. `delete(queueName)` acts only on the exact queue identity, treats missing or already-deleting resources as successful cleanup misses, and completes after the provider has durably accepted deletion; physical disappearance may remain asynchronous. Provider authorization, connectivity, timeout, and rejection failures propagate for command retry. Runtime clients must not auto-create missing queues because stale producers must not recreate a deleted queue. Every indexer owns its queue; `IndexResourceOwnership` controls document-index cleanup only. `IndexerQueueResourceManagerContract` provides shared missing, repeated, and exact-name deletion checks. Immediate recreation after delete remains an in-memory/provider-specific test because production deletion may settle asynchronously.
- `IndexerQueueConsumer`: consumer side of the queue. It owns bulk/portion delivery policy, exposes `pause`, `resume`, `commit`, and `close`, and calls the configured item handler.
- `IndexerActionItem`: abstract action payload. Logical `PutDocumentActionItem` and `RemoveDocumentActionItem` values contain document data only; `targetName` and timestamp belong to the submission envelope. Routing creates concrete queue payloads with mandatory `targetId`, `indexerId`, and `indexName`. Runtime indexers reject logical or partially routed document actions. `CompleteIndexActionItem` is an internal marker for historical load completion; `CatchUpBarrierActionItem` is an internal marker proving a live writer consumed earlier queued catch-up actions.
- `IndexerActionProvider`: action-type extension point for processing and route normalization. Document action providers create concrete queue payloads through `IndexerActionItems`.
- `IndexerProvider`: indexer-type extension point for loading and composing indexer views. The default metadata-backed provider exposes hot routing capability only for eligible live writers.
- `IndexerDocumentStore`: target document-store abstraction. The default document store is in-memory and also implements `IndexerDocumentIndexResourceManager` for test/local provisioning. Document-index `ensure` is idempotent for the same `IndexDefinition`, and fails when an existing index has a different definition. Resource deletion accepts only one concrete physical index identity; wildcard, `_all`, and comma-separated identities are rejected. Missing and repeated deletion are idempotent success, while real provider failures propagate for command retry. Production document clients must not auto-create missing indexes. `IndexerDocumentIndexResourceManagerContract` supplies shared deletion checks; immediate recreation remains provider-specific because durable deletion may settle asynchronously.
- `DocumentStoreMetadataRepository`: id-first metadata abstraction for targets, indexers, publications, manifests, and mutation state. The default repository is in-memory.
- `CommandService`: narrow producer-facing command submission API.
- `CommandEngine`: pluggable runtime SPI that combines command submission, handler registration, and engine lifecycle. Concrete engines own transport-specific consumption, acknowledgement, and retry mechanics. `CommandHandlerRegistry` resolves handlers independently of transport. `CommandProcessor` executes exactly one handler attempt and returns an explicit succeeded or classified failed outcome while preserving the original throwable. `InMemoryCommandEngine` maps that outcome back to its inline `Future<Void>` contract for local composition and tests.
- `DocumentStoreCommandHandlers`: assembly helper for registering the standard document-store lifecycle and provisioning command handlers with any `CommandEngine` while keeping repository, provider, resource-manager, and event-bus dependencies explicit.
- `CreateTargetCommand`: generic command for creating a concrete target from provider-owned `TargetDefinition` data. It can optionally compose indexer provisioning through a nested `createIndexer` object and marks the target `READY` only after requested indexer readiness or publication succeeds.
- `CreateIndexerCommand`: generic command for provisioning an indexer from `IndexerDefinitionProvider`. It inserts durable indexer metadata as `PROVISIONING`, ensures document-index and queue resources, inserts manifest/publication metadata, and marks the indexer `READY` or `FAILED`.
- `RecoverTargetProvisioningCommand`: admin command for reopening an `ACTIVE` concrete target whose provisioning state is `FAILED`. It moves the target back to `READY` with expected-version protection so normal explicit indexer creation or cold first-writer provisioning can be retried.
- `ReplacePublishedIndexer`: metadata primitive for atomically retiring the old published indexer for a target and publishing a replacement indexer.

### Node Envelope And Service Facades

The node envelope is the local Vert.x composition layer for one running indexer node. It owns service deployment, dependency assembly, and local runtime lifecycle, while keeping durable workflow decisions inside command handlers and metadata/repository layers.

- `IndexerNode`: programmatic composition root. It receives `IndexerNodeOptions`, builds or receives `IndexerNodeComponents`, and deploys enabled internal service verticles.
- `IndexerNodeVerticle`: Vert.x parent verticle wrapper for deploying a node through normal Vert.x deployment APIs. Child service verticles are deployed under this parent deployment scope.
- `IndexerNodeOptions`: declares which internal services, service-level REST APIs, and external gateway are enabled and how many verticle instances each service should deploy. Instance counts must be at least one when a service is enabled. Runtime service, REST APIs, and the gateway are intentionally singleton per node. REST APIs and the gateway are disabled by default and must be enabled explicitly with service options plus their host/port option blocks.
- `IndexerNodeComponents`: explicit dependency container for node-local runtime services. Production bootstraps can replace in-memory repositories, queues, stores, event buses, command service wiring, invalid-route cache wiring, and definition providers without changing service APIs.

Plugin-enabled workflows are composed at the application/component layer, not through `IndexerNodeOptions` JSON. A load-enabled application should construct the shared core metadata repository, load repository, `LoadIndexerPlugin`, `IndexerPlugins`, and `SubmitIndexActionsCommandHandler` in the same bootstrap scope, then pass the resulting services through `IndexerNodeComponents`. Production lazy-live composition should pass the shared `CommandService` and application `EventPublisher` to `LoadIndexerPlugin`; its simpler constructor intentionally uses no cleanup command service and a no-op event publisher. Both constructors create a local exclusive-flow coordinator by default, while the full constructor accepts an application-provided coordinator. This keeps core node configuration free of module-specific class names and prevents plugins from accidentally using a different repository instance than the command path.

`CommandEngine` and `IndexerOperations` are application-scoped dependencies exposed through `IndexerNodeComponents`. Composition creates one metadata-backed operations instance and one command engine, registers cleanup before delete initiation, registers remaining core and plugin handlers, and injects the engine's `CommandService` surface into admin paths. `IndexerNode` starts the command engine before listeners and service deployments and stops it after service undeployment. `DocumentStoreCommandHandlers.register(commandEngine, config)` is the canonical core registration helper; the command-unaware `create(config)` helper is removed because it cannot compose complete chained workflows. `IndexerOperations` is the core indexer-entity lifecycle port; `MetadataIndexerOperations` is the default metadata/event implementation. It is distinct from runtime `Indexer`, provisioning operations, `IndexerDocumentIndexResourceManager`, and `IndexerQueueResourceManager`; no general physical `IndexOperations` abstraction is introduced.

- `ServiceProxyVerticle`: shared base for Vert.x Service Proxy service verticles. It centralizes start/stop registration lifecycle while concrete services create their generated proxy handlers explicitly.
- `AdminService`: internal administration facade for metadata inspection and narrow management operations. The first slices expose target/indexer list/get operations, target creation, standalone indexer creation, failed target-provisioning recovery, indexer activation/deactivation, metadata indexer delete, and indexer queue reset through admin DTOs that hide repository-only fields such as metadata prefixes.
- `TargetActionService`: internal target/action service facade. It accepts target-envelope document mutation submissions through typed data objects and delegates execution to `HotIndexActionsService`. Command durability and concrete results remain subject to command/API review.
- `RuntimeService`: local-node runtime facade. `status()` reports only in-memory runtime indexers on this node, and `reconcileIndexer(...)` is an internal/manual repair hook for reconciling one indexer from metadata.
- `AdminRestVerticle`: OpenAPI-backed REST API over `AdminService`. It exposes target/indexer administration endpoints through Vert.x Web while calling the internal service proxy instead of the service implementation directly. It can run standalone or be deployed by `IndexerNode` when the `adminRest` node service is enabled.
- `TargetActionRestVerticle`: OpenAPI-backed REST API over `TargetActionService`. It exposes target-envelope document mutation submission for internal/manual HTTP access.
- `RuntimeRestVerticle`: OpenAPI-backed REST API over `RuntimeService`. It exposes local-node runtime status and a manual reconcile hook for one indexer.
- `GatewayRestVerticle`: external gateway boundary. It is deployed separately from service-level REST APIs and is the planned owner for authentication, authorization, rate limits, external audit logging, and proxying selected public routes to REST APIs. It is OpenAPI-backed, runs gateway request hooks around each operation, supports optional static API-key authentication plus optional in-memory rate limiting, and the first proxy slice forwards selected admin read traffic to the configured internal admin REST base URI.

Service APIs use Vert.x Service Proxy over the event bus, with typed data objects rather than raw `JsonObject` in concrete contracts. REST APIs provide direct HTTP access for internal callers and tools such as Postman or Insomnia. The gateway is a separate external REST proxy layer in front of those REST APIs. Mutating admin operations will be added one use case at a time after deciding whether each operation should return a concrete result or durable command acceptance.

The first admin REST contract is stored under `openapi/admin.yaml` and currently exposes:

- `GET /admin/targets`
- `POST /admin/targets`
- `GET /admin/targets/{id}`
- `POST /admin/targets/{id}/recover-provisioning`
- `GET /admin/indexers`
- `POST /admin/indexers`
- `GET /admin/indexers/{id}`
- `DELETE /admin/indexers/{id}`
- `POST /admin/indexers/{id}/activate`
- `POST /admin/indexers/{id}/deactivate`
- `POST /admin/indexers/{id}/reset-queue`

REST handlers translate HTTP path/query parameters into existing admin data objects and normalize service-boundary failures into JSON error tickets at the HTTP boundary. Mutating endpoints are added only when the service already returns a concrete result or after the command/result contract is reviewed. Operational endpoints such as queue reset must remain internal/admin-only unless deliberately exposed through a gateway policy.

Creation endpoints stay definition-driven at the REST boundary. Target creation accepts `target_name`, date-level external time input, and optional `create_indexer` intent. Standalone indexer creation accepts only `target_id`; it loads the target name from metadata instead of accepting redundant target identity fields. `AdminCreateRequestResolver` prepares existing admin create DTOs from these smaller intents, and `IndexerResourceNameGenerator` centralizes generated metadata prefixes plus generated index/queue names so REST handlers do not duplicate durable naming rules.

The first target/action REST contract is stored under `indexer/src/main/resources/openapi/target-action.yaml` and exposes `POST /targets/{target_name}/actions`. This API is internal/service-level only for now, not a gateway route. The target identity is carried by the path, not duplicated in the body. The body accepts optional `submission_id`, optional ISO timestamp, and logical document mutation action items (`PUT_DOCUMENT`, `REMOVE_DOCUMENT`) with only `type`, `uid`, and put `document` payload fields. Concrete `target_id`, `indexer_id`, and `index_name` fields are rejected at the service boundary and appear only after hot or cold routing expands the actions. The REST verticle maps this request into `TargetActionSubmitRequest` and calls the `TargetActionService` service proxy.

The first runtime REST contract is stored under `openapi/runtime.yaml` and exposes `GET /runtime/status` plus `POST /runtime/indexers/{id}/reconcile`. Runtime status is local-node only; broader node-management and cluster status remain separate future infrastructure.

The gateway contract is stored under `openapi/gateway.yaml` and currently exposes `GET /gateway/status`, `GET /gateway/admin/targets`, and `GET /gateway/admin/indexers`. The admin read routes proxy to internal admin REST, preserve the query string, forward the upstream status/body/content type, and use the configured admin REST base URI plus request timeout. `GatewayProxyOperations` keeps upstream validation and response forwarding separate from gateway verticle lifecycle. `GatewayRequestHooks` provides extension points for authentication, authorization, rate limiting, and success/failure audit callbacks; hook implementations can fail with `ErrorTicket` to return typed public errors. When `GatewayRestOptions.apiKey` is configured, `GatewayBuiltInRequestHooks` requires the matching API key header, defaulting to `x-api-key`; the secret is read from JSON config but intentionally omitted from `toJson()`. When `rateLimitRequests` is greater than zero, the same built-in hooks apply a per-operation/per-remote-address fixed-window in-memory rate limit using `rateLimitWindowMs`, returning a typed `RateLimited` error when exceeded. Gateway-owned failures are normalized through the shared `ErrorTicket` JSON contract so raw internal exception messages are not returned to callers. Real authorization and audit sink implementations are still pending. Target/action submission is not planned for gateway exposure unless a concrete external use case is approved.

### Document Store Publishing Model

Document-store publishing separates public target routing from physical index execution:

- `TargetDefinition` is provider-owned application/static data, not repository metadata. It is resolved by `targetName` and controls whether public writes may auto-create/provision concrete targets through `autoProvisionOnWrite`.
- `TargetRecord` is the concrete target used internally for one period bucket, or the single concrete target when the period strategy is `NONE`.
- `targetName` is the public route identity and logical business target name, such as `customers`.
- concrete period target names are encoded as `{baseTargetName}--{periodKey}`, such as `customers--2026-05`.
- supported period strategies are `NONE`, `MONTHLY`, `HALF_YEARLY`, and `YEARLY`.
- period routing uses UTC.
- `indexName` is the concrete physical document-store index, such as `customers-2024-01J...`.
- the indexer id or uid identifies one durable physical index version.
- `PUBLISHED` means queryable; it does not mean immutable.
- publication state and mutation state are separate, so a valid physical index can be `PUBLISHED` and `WRITABLE`.
- multiple indexers may share one physical `indexName` when their roles and ownership make that relationship explicit, for example a `LOAD_WRITER` owner plus an attached `LIVE_WRITER`.

Repository access for document-store metadata is id-first. Identity lookup uses concrete metadata `id` or `uid`, and relationship lookup uses foreign ids such as concrete `targetId` and `indexerId`. Target definitions are resolved through `TargetDefinitionProvider`, so the repository stores concrete targets by `targetName` plus `periodKey` rather than a target-definition foreign key.

Public write requests route by `targetName` plus a timestamp when the target definition uses period routing. Command orchestration resolves the target definition from `TargetDefinitionProvider`, resolves the UTC period, loads the concrete `TargetRecord`, resolves or provisions a writable indexer for that concrete target, expands logical mutations to concrete `IndexerActionItem` payloads, and publishes those concrete actions to each resolved indexer queue. Runtime action items execute by concrete `targetId`, `indexerId`, and `indexName`.

If `autoProvisionOnWrite` is disabled and the concrete target or writable indexer is missing, the cold command fails as a stable invalid route and does not create resources. If it is enabled and the concrete target is missing, the command creates the concrete target for the resolved period. If the concrete target has no writable indexer, the command path attempts to provision the first writable indexer through `IndexerProvisioningService`. The cold path generates the physical index/queue names, resolves index and queue definitions from `IndexerDefinitionProvider`, ensures document-index and queue resources, inserts manifest/publication metadata, and moves the concrete target through `PROVISIONING` and back to `READY`. Provisioning failure marks the target `FAILED`, so later writes fail fast instead of repeatedly creating indexers. Explicit target creation uses `CreateTargetCommand`; when a nested indexer is requested, the nested `initialPublicationMode` is mandatory and can prepare the indexer publication as `READY` or publish it immediately.

Query routing resolves the published indexer by `targetId` and queries only the resulting concrete `indexName`. A target may have zero published indexes during first build and multiple writable indexes during rebuild, but the first supported query contract allows at most one `PUBLISHED` indexer per target. More than one published indexer is an invariant failure.

Hot routing keeps an in-memory view of operational targets and indexers for the action-item flow. `HotMetadataView` loads a full immutable `HotTarget` snapshot from repository target records and `IndexerProvider` results, indexes it by target name, target uid, concrete target id, and indexer id, and invalidates the whole snapshot rather than patching child indexers in place. The default view uses only active, ready concrete targets and hot-capable live writers.

`HotTarget` owns target-level routing. It resolves the request timestamp to the configured UTC target period, selects the concrete target snapshot, and routes each action to every hot live writer under that concrete target. Hot routing is batch-atomic: either every action is accepted by at least one hot indexer and grouped into `RoutedIndexActions`, or the original request falls back unchanged to `SubmitIndexActionsCommand`.

`HotIndexer` owns final per-indexer acceptance and concrete action expansion. `MetadataHotIndexer` delegates action-specific normalization to `IndexerActionProvider.router()`. Candidate routing skips non-matching indexers; direct routing throws on conflicting concrete fields. This keeps action-specific rules out of the target cache and lets future providers add indexer-specific composition without changing the cache.

`HotIndexActionsService` is the hot-path entry point. It first tries a target-envelope route by `targetName` plus timestamp, then tries direct concrete routing for actions that carry an `indexerId`, and otherwise submits the original request to the command service. `RoutedIndexActionPublisher` is shared by hot routing and the cold command path for queue publication.

Hot routing support also includes two guard components. `InvalidRouteCache` stores expiring invalid route signatures for stable cold failures such as missing target definitions, missing concrete targets/indexers, or missing writable indexers. `HotIndexActionsService` checks this cache before falling back to `SubmitIndexActionsCommand`; cached invalid routes fail fast instead of repeatedly entering cold submit. Retryable provisioning states and operator-recovery failures are not cached. Successful cold submission invalidates matching route signatures, so a route that becomes valid through explicit command submission or auto provisioning can clear stale cache entries before the TTL expires. `InvalidRouteMetadataChangeListener` subscribes to indexer and target metadata events. Indexer events invalidate direct target-id and indexer-id cache entries from the event, then reload the changed indexer only for target-envelope cache invalidation. Target events carry their target envelope and invalidate matching target-envelope and target-id cache entries without repository lookup, which covers explicit target creation and target-provisioning recovery.

`TargetInvalidationRegistry` is the missed-event recovery path for hot target snapshots. Its API is asynchronous so a distributed provider does not block Vert.x event loops. In current local composition, `TargetInvalidationMetadataChangeListener` immediately invalidates the local hot snapshot for indexer and target metadata events and marks the owning concrete target in the registry from the event target id. `TargetInvalidationPoller` performs an initial read during node startup, then non-overlapping periodic reads. It compares the full observed entry (`version` and `expiresAt`), which detects both normal increments and version reset after an expired entry is recreated. Changed entries invalidate the owning `HotTarget`; entries no longer returned are removed from local observation state. A truncated registry result invalidates the entire hot view and clears local observations because the omitted target identities are unknown. Registry TTL is derived from poll interval times a retention factor of at least two, and the configured maximum target count must be positive.

`TargetInvalidationRegistryProvider` owns registry construction from `TargetInvalidationRegistryConfig`. The common configuration supplies a mandatory deployment namespace and the polling/retention options; backend endpoints, credentials, clients, and lifecycle remain application/provider concerns. Repeated construction for one namespace must observe the same logical registry, while different namespaces must be isolated. A distributed implementation must atomically increment one concrete target version while refreshing its TTL, may restart the version after expiry, and must set `truncated` whenever `listInvalidations(maxTargets)` omits entries. Provider selection is explicit in production composition rather than discovered through `ServiceLoader`. The default local node uses `InMemoryTargetInvalidationRegistryProvider`; a concrete distributed adapter remains pending.

Production composition should expose the existing `TargetInvalidationRegistry` contract as an internal request/reply microservice rather than introduce another domain interface. Local/test composition injects the registry directly; production metadata workflows use a remote proxy and await `markInvalidated(targetId)` until the backing provider confirms the version/TTL update, while pollers call bounded `listInvalidations(maxTargets)`. The reply confirms registry mutation, not that every node has reloaded. Registry writes move from event listeners to metadata mutation workflows so one change produces one confirmed mark; metadata event listeners then perform local cache invalidation only. Repeated marks remain safe, and retrying a metadata workflow must resubmit invalidation even when the metadata mutation was already applied. Multiple service replicas are valid when the distributed provider supplies atomic updates. Service envelope and proxy implementation remain deferred to the separate services scope.

Broader metadata inspection belongs to an administration layer that can load targets and indexers with wider status/state filters. Repository query-object methods such as `listTargets(TargetMetadataQuery)` and `listIndexers(IndexerMetadataQuery)` and the generic `IndexerProvider` read APIs support both hot routing and administration without baking hot-routing filters into the repository itself.

### Index Flow

Indexing uses two paths:

- Hot path: callers submit a `HotIndexActionsRequest` to `HotIndexActionsService`. A normal live-write request carries `targetName`, a timestamp, and logical document mutation items. If the cached target/indexer snapshot proves the route, the service expands the items to concrete `targetId`, `indexerId`, and `indexName` payloads and publishes them through `RoutedIndexActionPublisher`.
- Cold/unknown path: callers submit `SubmitIndexActionsCommand`, either directly or through hot-path fallback. The command supports only two routing schemas. Target-envelope mode carries `targetName`, optional timestamp, and logical document mutation actions with no concrete destination fields. Concrete mode carries no target envelope or timestamp, and every action must include a concrete `targetId` or `indexerId`; internal actions such as complete and catch-up barrier require `indexerId`. The command handler resolves writable metadata indexers by concrete `targetId`, verifies each destination, expands logical actions to concrete `indexerId`/`indexName` payloads, publishes metadata-change wake-ups only for real metadata changes such as auto-provisioned indexers, then publishes the concrete actions through the shared `RoutedIndexActionPublisher`.

Cold routing supports indexer preparation through `IndexerActionReceiveCapability`. Core asks capabilities whether a non-live candidate can receive an action with `YES`, `REQUIRES_PREPARE`, or `NO`. `YES` means the candidate is a receiver, `REQUIRES_PREPARE` lets the plugin prepare and return actual receiver indexers, and `NO` skips the candidate. Core remains responsible for forwarding the original action items to the prepared receivers.

`IndexerPlugin` is the core SPI for peer indexer functionality. The initial plugin surface exposes action-receive capabilities through `IndexerPlugins`; application composition constructs plugins explicitly because implementations may need repositories or other runtime dependencies.

Applications that enable load behavior should pass their plugin aggregator into `SubmitIndexActionsCommandHandler`, for example `new IndexerPlugins(List.of(new LoadIndexerPlugin(metadataRepository, loadRepository)))`. Core defaults use `IndexerPlugins.empty()`.

Command completion means that the submitted actions were handed to the indexer queue, not that the documents were already indexed. Runtime processing remains asynchronous.

The cold path fails closed. If the command sees an unexpected indexer state or action mismatch, it must not publish actions. Expected/idempotent cases include resolving a writable, available, provisioned, runtime-active metadata indexer and waking runtime consumers that may not be hot yet.

Cold command failures use typed `CommandFailure` classification where the command layer needs retry decisions. Concurrent provisioning states, including target provisioning already in progress and target provisioning lock/version conflicts, are `RETRYABLE`. Stable invalid routes, including missing target definitions, missing concrete targets/indexers, and missing writable indexers, are `STABLE_INVALID` and may be written to `InvalidRouteCache`. Target provisioning marked `FAILED` is final for the submit command and requires explicit `RecoverTargetProvisioningCommand` before the same route should be retried.

The current fail-closed guards are:

- an unavailable or deleting indexer cannot receive new actions;
- an indexer whose provisioning state is not `READY` cannot receive new actions;
- a runtime-`NON_ACTIVE` indexer cannot receive new actions;
- cold concrete-target routing requires either target-envelope document mutations or concrete route fields so writable live writers can be resolved; load writers are not live-submit destinations;
- concrete actions with `indexerId` and `indexName` must match the resolved metadata indexer.

Routing identity fields are immutable by definition for normal lifecycle: `targetId`, `targetName`, `indexName`, `queueName`, `role`, and `type`. If these values are wrong, create a replacement indexer instead of mutating the existing record. `ResetIndexerQueueCommand` remains a narrow troubleshooting exception in the current codebase and must not be used as a normal reload/live-writer swap mechanism.

### Load And Reload Workflow

Durable load/reload orchestration is split between the core `indexer` module and the `indexer-load` module. Core owns indexer roles, resource ownership, runtime marker processing hooks, and generic indexer commands. `indexer-load` owns load workflow metadata, external loader contracts, and marker handlers.

- `LOAD_WRITER`: finite historical load writer for a target and physical `indexName`.
- `LIVE_WRITER`: ongoing writer. During reload, a new live writer may be linked to the load workflow and write to the same `indexName` as the load writer.
- `IndexerLoadRecord`: load-plugin metadata keyed by the core `indexerId` of the load writer. It tracks target id, load state, optional linked live writer id, persisted live-writer policy, timestamp replay window, review requirement and approval, barrier progress, and failure details. The load repository enforces one active load per target.
- `LiveWriterPolicy`: live writer creation is explicit and durable. A load may create no live writer, create one immediately, or create one lazily on the first live action when the policy allows it.

`CompleteIndexActionItem` and `CatchUpBarrierActionItem` are internal actions. External loaders should use loader-facing helpers such as `LoadWriter.submit(...)` and `LoadWriter.complete(...)` rather than constructing marker items directly. `QueueLoadWriter.submit(...)` accepts document mutations, normalizes them to the load writer's concrete `targetId`, `indexerId`, and `indexName`, and rejects mismatched concrete identities. `QueueLoadWriter.complete(...)` publishes the internal completion marker only while the load is `HISTORICAL_LOADING`; duplicate or late completion callbacks after completion, cancellation, failure, or publication are ignored. `LoadIndexerMarkerHandler` requires `CommandService` because barrier dispatch and publication are durable orchestration and must not be silently omitted.

After provider start is accepted, provider-owned source/load failures should be reported through `LoadWriter.fail(...)`. The queue-backed writer marks active loads `FAILED` with the reported reason. Late failures after the load is already `CANCELLED`, `PUBLISHED`, or `FAILED` are ignored so provider callbacks cannot overwrite terminal workflow decisions.

`CreateLoadCommand` is the first load orchestration command. It ensures the target, creates the core `LOAD_WRITER`, optionally creates an immediate linked `LIVE_WRITER`, stores the provider id and load source fields (`sourceFrom`, `sourceTo`, `sourceQuery`, `sourcePlaybookId`) in `IndexerLoadRecord`, publishes metadata-change wake-ups, and persists the load as `CREATED`. When wired with a command service, it submits `StartLoadCommand`; otherwise the load remains at the durable `CREATED` recovery point until an external orchestrator submits start.

`StartLoadCommand` owns provider acceptance. It moves `CREATED` to `STARTING`, resolves the application-level `LoadProvider` from `LoadProviderRegistry`, builds `LoadRequest` from durable target/load/indexer metadata, calls `LoadProvider.start(...)`, and moves the load to `HISTORICAL_LOADING` only after the provider accepts the asynchronous job. The `LoadRequest` includes both source fields and concrete callback identities such as `targetId`, `indexerId`, optional `liveIndexerId`, `providerId`, `indexName`, and `queueName`. `LoadProvider.start(...)` must mean accepted asynchronous work, not historical load completion. Retrying `StartLoadCommand` for a load already in `STARTING` is allowed; providers must treat `LoadRequest.indexerId` as the start idempotency key and accept/resume repeated start calls for that same load.

`LoadWriterActionReceiveCapability` is the cold-submit integration for lazy live writers. A `LOAD_WRITER` returns `REQUIRES_PREPARE` for live document actions only while an active load has `LiveWriterPolicy.CREATE_ON_FIRST_LIVE_ACTION` and no linked live writer. `prepareToReceive(...)` is the lazy-live preparation workflow boundary: it creates or reuses the linked `LIVE_WRITER`, attaches it to the load, returns that writer as the actual receiver, and the core submit command publishes the original live action items to it. The durable safety primitive for production is an atomic attach-if-absent operation on the load record's existing `liveIndexerId` and version; no extra lock, claim, or session field belongs in load metadata. After the live writer is linked, the same `LOAD_WRITER` returns `NO` for live actions and is never a live action receiver.

When a lazy-live candidate loses atomic attachment or is abandoned after a stale-version retry, load orchestration submits the generic `DeleteIndexerCommand` with the candidate version and emits `LAZY_LIVE_WRITER_PREPARATION_CONFLICT` through `indexer-events`. Cleanup is best-effort and never blocks routing to a valid winner or changes the stale-state retry result. `cleanupSubmitted=true` means the command transport accepted cleanup and `cleanupSucceeded` remains null because distributed deletion has not completed. Rejected cleanup submission emits `CLEANUP_FAILED` with `cleanupSubmitted=false` and `cleanupSucceeded=false`. The cold command id is propagated as the event correlation id.

`LoadIndexerPlugin` exposes load-module peer behavior through the core `IndexerPlugin` SPI. It contributes `LoadWriterActionReceiveCapability` and model-scoped runtime marker handling for `LOAD_WRITER` and `LIVE_WRITER` roles while keeping load metadata and workflow dependencies in `indexer-load`. `IndexerRuntime` resolves marker handling through application-supplied `IndexerPlugins`; zero matching plugins retain the explicit failing handler, and multiple matching handlers are rejected as ambiguous.

Load-enabled applications assemble the module explicitly. `LoadCommandHandlers.register(...)` registers create, start, publish, approve, cancel, and cleanup handlers against a shared `CommandEngine` from a `Config` containing the core metadata repository, load repository, queue client, provider registry, and lifecycle event bus. The same repositories, command service, and event bus are supplied to `LoadIndexerPlugin`, and that plugin is passed to the runtime and cold-submit composition through `IndexerPlugins`. Core node JSON options and default node wiring remain load-free.

Historical-only loads publish the `LOAD_WRITER` after successful completion unless review is required; publication converts that indexer role to `LIVE_WRITER` while preserving physical index ownership. Reviewed historical-only loads move to `WAITING_FOR_REVIEW`. For a load with a linked live writer, completion atomically persists a generated barrier id and timestamp with `CATCH_UP_BARRIER_REQUESTED` before submitting a concrete `CatchUpBarrierActionItem` through the generic action command. A completion-command retry reloads and resubmits the same persisted marker identity. The live writer's ordered queue makes consuming that marker proof that earlier catch-up items were consumed; the timestamp is informational and does not depend on synchronized node clocks. Repository barrier completion accepts only the requested id and timestamp, then moves to `CATCH_UP_READY` or `WAITING_FOR_REVIEW`. Missing active load metadata for a late duplicate marker is an idempotent cleanup miss.

Loads with live support publish the linked `LIVE_WRITER` after historical completion, catch-up barrier processing, and optional review. `PublishLoadCommand` validates the load state, candidate writer state, optional approval, and catch-up barrier before calling the atomic metadata replace primitive. When a linked live writer is published, ownership moves from the load writer to the linked live writer and the old published writer is retired.

`ApproveLoadPublicationCommand` is accepted only for a review-required load in `WAITING_FOR_REVIEW`. It records `approvedAt`, `approvedBy`, and `approvalReason`, moves the load to `APPROVED`, and submits `PublishLoadCommand`. This prevents early approval from replacing historical or catch-up progress state. Marker handling auto-publishes non-reviewed loads when a command service is supplied: historical-only loads publish after the completion marker, and linked live loads publish after the catch-up barrier marker.

`CancelLoadCommand` marks the load `CANCELLED` and, when wired with a command service, submits generic delete commands for the load writer and optional linked live writer. A `CREATED` load has not been accepted by a provider yet, so cancel skips provider stop. `STARTING` and later active states resolve the stored provider id from `IndexerLoadRecord` and stop that provider before cancellation. Published loads are not cancellable through this command.

`LoadAwareIndexerEventPublisher` is the load-side runtime failure bridge. It observes `ACTION_ITEM_FAILED` events, finds an active load for the failing indexer id, marks the load `FAILED`, attempts to stop the stored provider, and then delegates the original event. Runtime processing stays generic; load workflow state remains in `indexer-load`.

Cross-module event publication uses the separate `indexer-events` module under `com.inqwise.events`. Its initial API consists of typed `EventChannel<T>` metadata (`name` and `payloadType`), `EventEnvelope<T>` (`eventId`, `eventType`, `occurredAt`, `source`, optional `correlationId`, and payload), and an `EventPublisher` whose generic `publish(channel, envelope)` returns `Future<Void>`. Publisher completion means that the configured transport accepted the event; it does not mean consumers processed it. Event ids and timestamps are assigned before publication so retries can reuse the same identity. The initial module supplies no-op and recording in-memory publishers; subscriber APIs and distributed transport implementations are added only with concrete consumers. Domain modules continue to own payloads, channel constants, consumers, and channel-specific delivery requirements. Lifecycle invalidation, runtime processing events, and load operational conflicts may therefore share transport infrastructure without becoming one event stream or adopting the same reliability policy. Load operational conflicts are the first consumer; migration of the existing lifecycle event bus is a separate follow-up scope.

Shared exclusive-flow coordination is implemented in the separate `indexer-coordination` module under `com.inqwise.coordination`. Its generic execution API accepts a flow key, concrete result `Class<T>`, and `Handler<Promise<T>>`; `LocalExclusiveFlowCoordinator` creates one shared promise, invokes only the first caller's handler for an active key, and returns that promise's future to the owner and local waiters. Success values and the original `Throwable` failure are shared, the key is released after either outcome, different keys remain independent, and an active-key call with a different result class fails immediately. Lazy-live integration wraps only `prepareToReceive(...)` under `load-live-writer:{indexerId}` and shares `PreparedIndexers`; action publication remains outside coordination so every cold submit forwards its own action items exactly once. A distributed implementation will encode successful results through a general extensible value-codec registry. At the current stage, the concrete result class is the codec identity and only one codec is allowed per concrete type; raw generic result types are unsupported. Explicit codec ids, format versions, and portable failure encoding are deferred until a distributed provider is implemented. Coordination reduces duplicate work but never replaces atomic repository correctness or abandoned-candidate cleanup for cross-node races.

Final indexer deletion is generic command orchestration, not runtime-node or load-plugin resource ownership. `DeleteIndexerCommand` first persists `DELETING` and `NON_ACTIVE`, publishes metadata invalidation, and asynchronously submits `CleanupDeletingIndexerCommand`. Runtime reconciliation closes only its local producer and consumer handles. The cleanup command reloads and validates the deleting indexer, idempotently deletes its queue, and deletes the document index only for `IndexResourceOwnership.OWNER`. After physical cleanup, one atomic repository `finalizeIndexerDeletion(indexerId, expectedVersion)` operation verifies `DELETING`, deletes publication and all manifest metadata for the indexer, and deletes the core indexer record in one metadata transaction. Repeating finalization after the record is absent succeeds idempotently. Publication and manifest rows are operational metadata; durable history belongs in audit/operational events. Missing resources and records are successful cleanup misses, while real storage failures fail for command retry. The initial workflow fences routing but does not wait for closure acknowledgement from every runtime node; strict in-flight consumer acknowledgement is deferred. Plugin-owned load metadata is finalized separately.

Document-index ownership transfer must complete before deletion starts. `DELETING` is a terminal mutation state and cannot transition back to writable or read-only. Once deletion begins, `IndexResourceOwnership` and queue identity are immutable. Atomic `replacePublishedIndexer(...)` rejects a deleting candidate, previous publisher, or ownership source before changing any participant. This prevents cleanup from reading `OWNER` and deleting a physical index after ownership has concurrently moved. The resource manager remains metadata-independent: orchestration calls it only for `OWNER`, while `ATTACHED` always skips physical index deletion.

Production `finalizeIndexerDeletion(...)` implementations must lock the existing indexer row inside one transaction, treat an absent row as idempotent success, reject a version mismatch with `RetryableStaleStateException`, and reject an existing row outside `DELETING` as a final domain conflict. Publication rows, all manifest rows, and the indexer row are then deleted in that order and committed together. `READ COMMITTED` with an indexer-row lock is sufficient: concurrent finalizers serialize and later callers observe the committed missing row. Any validation or storage failure rolls back all metadata deletion. No lock, claim, or deletion-session fields are added. `DocumentStoreMetadataRepositoryDeletionContract` provides reusable adapter conformance tests for atomic cleanup, rollback behavior, missing-row retries, and concurrent finalization.

Core lifecycle transitions are exposed through an injected `IndexerOperations` port. Its first operation, `markDeleting(MarkIndexerDeletingRequest)`, owns expected-version validation, transitions to `DELETING` and `NON_ACTIVE`, publishes lifecycle invalidation through the metadata-backed implementation, and returns the updated `IndexerRecord`. The port may absorb other cohesive core lifecycle operations later, but this slice does not move unrelated behavior speculatively. `DeleteIndexerCommandHandler` and `AdminServiceImpl` share this operation before submitting cleanup. `IndexerOperations` does not own physical resource cleanup, command chaining, load behavior, or provisioning; those remain in their existing orchestration and provisioning components.

Delete initiation and cleanup are idempotent. `markDeleting(...)` returns an empty result for an absent indexer, returns the current record for an already-deleting indexer regardless of the original requested version, and otherwise requires the expected version before transitioning. `DeleteIndexerCommandHandler` submits versionless `CleanupDeletingIndexerCommand(indexerId)` and requires `CommandService`; cleanup cannot be silently omitted. Every cleanup attempt reloads the current deleting indexer snapshot, uses its immutable resource identities and ownership, and passes that snapshot version to atomic metadata finalization. Missing records succeed and non-deleting records fail. A metadata change between resource cleanup and finalization produces `RetryableStaleStateException`; retrying the same command reloads a fresh snapshot and can make progress without a special restart command.

`CommandFailureClassifier` is the generic command-execution failure boundary for a future durable executor. Explicit `CommandFailure` kinds remain authoritative even when wrapped. Application/provider rules run next and can classify concrete transport, timeout, authentication, and configuration exceptions without coupling resource interfaces to command types. Core defaults classify `RetryableStaleStateException` as `RETRYABLE`, argument and domain-state failures as `FINAL`, and otherwise unknown failures as `RETRYABLE`. Unknown retries are bounded when the concrete engine has a durable attempt mechanism. `InMemoryCommandEngine` remains inline and returns handler failures directly; it does not schedule retries.

`CommandProcessor` is transport-neutral and never acknowledges, delays, retries, or publishes failure records. It resolves a handler, invokes one attempt, and converts synchronous and asynchronous failures into `CommandExecutionOutcome.Failed(failureKind, originalError)`. Missing handlers and null handler futures are final failures. Resource engines consume this outcome and decide whether to commit, pause/seek, or publish a terminal failure according to their own delivery guarantees.

`CommandEnvelope` is the transport value contract. It owns the stable transport `commandId`, command type, positive schema version, creation timestamp, optional correlation id, and a defensive copy of domain payload JSON. Domain payloads do not own transport identity; unused embedded ids were removed from target creation and index publication commands. Action submission retains correlation through the generic `Command.getCorrelationId()` metadata surface, not inside its payload. `GenericCommand` carries decoded type, correlation, and payload into the existing handler reconstruction flow. `CommandEnvelopeCodec` provides UTF-8 JSON byte encoding without Kafka dependencies. Partition key remains separate transport metadata, and attempts, retry deadlines, leases, and delivery state are not encoded in the envelope.

Command partition routing is owned by the command-service layer and requires no metadata or provider queries. `CommandPartitionKeyRouter` resolves a registered command type to a namespaced `CommandPartitionKey`: target creation and load creation use `target-name:{name}`, target-scoped work uses `target:{id}`, indexer lifecycle and load lifecycle use `indexer:{id}`, and publication readiness uses `publication:{id}`. Core resolver registration is built in; extension modules register only their command-type resolvers, as `indexer-load` does through `LoadCommandPartitionKeyResolvers`. Missing resolvers, missing identities, duplicate registrations, and mixed-resource action batches are final submission failures. Logical action submissions use target name. Concrete action batches use one shared target id when every item carries it, otherwise every item must carry one shared indexer id. This ordering scope coordinates commands for a resource; document/peer ordering inside indexer queues remains the responsibility of those queues.

`CommandRetryPolicy` is a pure application-configured decision model for engines that can track attempts. It accepts maximum attempts, initial and maximum delays, an exponential multiplier, and a jitter ratio; no operational timings are hardcoded in the library. `failedAttempts` counts completed handler executions, so the first failed attempt uses the initial delay and a retryable failure becomes `EXHAUSTED` when `failedAttempts >= maxAttempts`. Decisions are explicit `RETRY`, `FINAL_FAILURE`, or `EXHAUSTED`; only `RETRY` carries a delay. State belongs to the concrete command resource rather than a mandatory core repository. A same-record Kafka engine can pause and seek an uncommitted partition while continuing to poll, but its local delay and attempt count are lost on rebalance; durable maximum attempts and exhaustion therefore require retry-topic metadata or another Kafka-owned state mechanism and are deferred.

The planned Kafka engine disables auto-commit and processes commands sequentially per partition. Handler success is followed by offset commit; commit failure permits redelivery. Retryable failure leaves the offset uncommitted, seeks back to the failed offset, pauses only that partition, continues polling for heartbeats and other partitions, and resumes after a local deadline. Final failures must be published to a durable failure topic before the source offset is committed; Kafka transactions may later make failure publication and offset commit atomic. A generic delivery object does not expose `retry(delay)` because Kafka has no broker-managed delayed redelivery. The engine interprets handler failure and applies its resource-specific retry mechanism. Kafka client implementation is outside the current scope.

Load-owned terminal cleanup uses one `CleanupLoadCommand` rather than publication-specific cleanup. For `PUBLISHED` historical-only loads it deletes only the previously published indexer and retains the former load writer that became the published live writer. For `PUBLISHED` loads with a linked live writer it deletes the previous published indexer and historical load writer while retaining the linked published writer. For `CANCELLED` loads it deletes both load and optional linked live writers. `FAILED` loads remain inspectable until explicitly cancelled. The handler reloads terminal load metadata, submits versioned generic delete commands for every removable indexer, waits only for durable command acceptance, and then deletes the load row with expected-version protection. Missing load/indexer records are idempotent success. Without a durable `CommandService`, the load row remains because cleanup has not been durably accepted.

When `PublishLoadCommandHandler` is wired with a command service, successful publication submits `CleanupLoadCommand`. Cleanup reloads current metadata versions, uses the generic `DeleteIndexerCommand` path for removable writers, and deletes the terminal load row after those commands are accepted.

Timestamp-based live catch-up uses the configured replay window to decide which live actions are copied to the candidate writer. Duplicate/retry safety is assumed only inside the same partition/key ordering scope.

### Lifecycle

- `activate()`: starts the root indexer once. It activates the queue consumer/listener, resumes consumption, and emits `INDEXER_STARTED`. Repeated calls are idempotent.
- `unregister()`: closes the active consumer/listener.
- `openProducer()` / `closeProducer()`: open or close the producer-side queue publisher for this indexer.
- `openConsumer()` / `closeConsumer()`: open or close the consumer-side processor for this indexer.
- `close()`: closes local producer and consumer handles. It does not delete queue resources or drop document-store indexes.
- `delete()`: retained as a local runtime close operation that returns the model. Destructive cleanup belongs to command orchestration.

### Distributed Lifecycle Commands

Lifecycle commands express durable desired state. `ActivateIndexerCommand` and `DeactivateIndexerCommand` are handled through the generic `CommandService` layer. Their handlers update `DocumentStoreMetadataRepository` runtime state/version and publish an `IndexerMetadataChanged` notification with the indexer id, owning concrete target id, command type, and resulting version. `IndexerRuntimeState.ACTIVE/NON_ACTIVE` is a consumer-control switch only; it does not change publication state, mutation state, provisioning state, or indexer availability.

The metadata-change notification is a fan-out wake-up for runtime nodes and local caches, not the source of truth. The current `IndexerRuntime` implementation subscribes to indexer metadata changes, reloads the latest metadata indexer identified by the event, maps it to an `IndexerModel` for runtime transport, and reconciles local resources directly from the subscription callback. Target metadata changes use the same lifecycle event bus for cache invalidation, but do not drive runtime indexer reconciliation by themselves. Runtime construction can use the Verticle-backed constructor so active indexers deploy an `IndexerProcessorVerticle` while `IndexerRuntime` only tracks `Indexer` instances and never exposes Vert.x deployment ids.

`IndexerMetadataChanged` delivery is one-way. A publisher never waits for a runtime node to reconcile or reply. `IndexerLifecycleEventBus.publishIndexerWakeUp(...)` schedules the provider publication without exposing its completion to orchestration, so durable metadata mutation success does not depend on event delivery success. The underlying asynchronous `publish(...)` result represents provider acceptance only and remains available to provider implementations and tests. Publish failures are provider-owned operational signals for logs and metrics; startup and safety resynchronization remain the correctness path. Command, provisioning, administration, and load workflows use the one-way API after durable state changes.

`IndexerLifecycleEventBusProvider` owns explicitly selected lifecycle-bus construction from a mandatory deployment namespace. Equal namespaces share one logical event channel and different namespaces are isolated. Backend clients, credentials, lag thresholds, and transport lifecycle remain application/provider concerns. `InMemoryIndexerLifecycleEventBusProvider` supplies local and test composition; a production adapter remains pending. The generic `indexer-events` module continues to carry operational event-publishing primitives and is not the lifecycle wake-up transport.

Lifecycle subscriptions return an `IndexerLifecycleSubscription` close handle. Runtime and metadata-cache listeners retain their handles, starts are idempotent, and node shutdown closes subscriptions in reverse startup order so a stopped node cannot reactivate from later wake-ups. Providers can emit `RECONNECTED`, `DELIVERY_LOST`, and `EXCESSIVE_LAG` signals through a separate closeable subscription. These signals request node-side safety resynchronization; they are not durable workflow state. Production delivery fans out wake-ups to runtime nodes, at-least-once delivery is acceptable, global ordering is unnecessary, and duplicate events may be coalesced because reconciliation reloads current repository state. Durable replay may reduce convergence time but is not the runtime correctness boundary.

The accepted node-side reconciliation design uses a bounded dirty-indexer set plus a full-resynchronization flag. An event callback only marks the indexer dirty and wakes a reconciliation worker; it performs no repository or runtime work. Node start, provider reconnect or delivery-loss signals, dirty-set overflow, periodic safety intervals, and detected local tracking inconsistencies mark full resynchronization required. High CPU cannot by itself prove event loss, so provider lag/connection signals and periodic repository comparison cover that case. The worker and its synchronization mechanics remain a separate implementation scope.

Production lifecycle-event consumers have separate correctness boundaries. Hot target snapshot correctness is backed by `TargetInvalidationRegistry`, so missed metadata events are recovered by registry polling. Invalid-route cache invalidation is a latency optimization and remains bounded by cache TTL. Runtime correctness comes from comparing local runtime state with durable indexer metadata during startup and safety resynchronization, while events only reduce convergence latency.

Runtime reconciliation opens a consumer only when the metadata indexer is `IndexerStatus.AVAILABLE`, `IndexerProvisioningState.READY`, and `IndexerRuntimeState.ACTIVE`. Otherwise, including `MutationState.DELETING`, it only closes the local runtime indexer. Destructive resource cleanup is performed once through command orchestration rather than independently by every runtime subscriber.

Indexer-scoped queue reset is an orchestration workflow, not an `Indexer` runtime method. Reset is a troubleshooting mechanism whose initial semantics are that future writes move to a clean queue, not that every old in-flight item is synchronously proven dead. `ResetIndexerQueueCommand` carries the expected queue name and metadata version. The handler provisions a deterministic versioned queue, updates metadata with expected-version protection, and recognizes exact redelivery when the resulting queue/version is already applied, re-emitting the wake-up without advancing another generation. A final `-vN` suffix is stripped only when `N` equals the expected metadata version; this prevents a custom old queue name from becoming a later generated queue identity. After metadata advances, reset submits `CleanupResetIndexerQueueCommand` with the exact retired queue name. Cleanup uses the generic command service, deletes only that queue, and relies on the resource-manager contract that missing queues are idempotent success. Cleanup submission failure does not roll metadata back: reset fails for retry, and exact redelivery resubmits the same cleanup without provisioning another queue. For Kafka, prefer advancing a queue generation in metadata and publishing through a new generated topic name over deleting and recreating the same topic name in place. Runtime nodes learn the new queue name through metadata-change fan-out and reconcile onto the new consumer. Strict old-consumer fencing or distributed close acknowledgement can be added later if reset must provide stronger "old items cannot be processed" guarantees.
