# Roadmap

## Module Layout

- Discuss and design a module split that moves core indexing primitives out of the current `indexer` module and leaves `indexer` focused on deployment, service communication, node wiring, and external/internal APIs. The likely direction is a core module for runtime/actions/metadata/commands/provisioning primitives plus a deployment-facing module for Vert.x service proxies, service verticles, node container, gateway APIs, internal REST APIs, and OpenAPI wiring.
- Consider extracting default local/in-memory node composition from `IndexerNode.defaultComponents(...)` into a dedicated factory or bootstrap class. `IndexerNodeComponents` is intentionally explicit, but the default wiring now spans repository, definitions, queue resources, document-index resources, command routing, hot view, invalid-route cache/listener, runtime, and lifecycle event bus.

## Index Flow

- Add public API error mapping so internal ids, index names, queue names, and storage details are not exposed directly to external callers.
- Add authorization, ownership checks, and rate limits before exposing auto-provision-on-write to public API traffic.
- Design the concrete queue/resource provisioning contract for indexer creation. In particular, decide whether `queueName` is always derived from `indexName`, stored explicitly on `IndexerModel`, or versioned for replacement/load flows.
- Add durable command state storage for `SubmitIndexActionsCommand` when the command service moves beyond the in-memory implementation. The intended states are received, ensuring indexer, publish-ready, publishing, published, retryable failure, and final failure.
- Define command retry policy for the planned queue-backed command engine. Failed commands may be redelivered and processed by another consumer, so the command layer needs maximum retry count, retry/backoff timing, poison-command handling, final failure state, and operator visibility. Queue reset retry behavior should follow this generic command retry policy rather than embedding reset-specific retry loops.
- Add a separate `CommandStateRepository` for queue-backed command execution state. It should track command payload, status, attempts, maximum attempts, worker lease, retry timing, last error, timestamps, and optimistic version, and stay separate from `DocumentStoreMetadataRepository`.
- Extend typed command failure classification beyond `SubmitIndexActionsCommandHandler`. The current submit path classifies retryable provisioning conflicts, stable invalid routes, and final provisioning failures while keeping the existing `Future<Void>` handler style. Other command handlers still need classification before the queue-backed command engine can make consistent retry/final decisions.
- Defer action-level deduplication for publish retries. The planned queue-backed command engine retries the whole command, and current document actions should remain idempotent where practical. Add stable `actionId`, `batchId`, or persistent action dedupe only when non-idempotent action effects or operational duplicate suppression require it.
- Treat publish-readiness as a command/provisioning concern, not an `Indexer` runtime concern. Metadata checks remain first, and production readiness should additionally verify or ensure external queue/topic and document-index resources before publishing. Missing resources should fail closed or trigger provisioning/recovery commands rather than publishing blindly.
- Add cleanup/retry admin commands for failed concrete indexers left by provisioning failures. Target-level reopening is handled by `RecoverTargetProvisioningCommand`; failed physical indexer retry/replacement still needs ownership-aware cleanup rules.
- Finish high-level publication orchestration for load/reload workflows. The core pieces now exist: `LOAD_WRITER` plus optional linked `LIVE_WRITER`, internal completion/barrier markers, load metadata keyed by the core load-writer `indexerId`, source metadata fields, create-load orchestration, and an atomic metadata publish/replace primitive.
- Add production repository support for atomic `finalizeIndexerDeletion(...)` and production queue/document resource managers for `CleanupDeletingIndexerCommandHandler`.
- Consider wrapping external queue/topic and document-index provisioning calls with Vert.x Circuit Breaker. Do not encode circuit-breaker behavior in the metadata model.

## Document Store Publishing

- Add query API support for resolving `targetName` plus a time range into published physical `indexName` values. Queries should skip missing period targets and return empty results when no published indexes exist.
- Wire hot routing into the service-level action submission surface. The core components now exist: `HotIndexActionsService`, `HotMetadataView`, immutable `HotTarget` snapshots, hot-capable indexer providers, shared `RoutedIndexActionPublisher`, `InvalidRouteCache`, and `TargetInvalidationRegistry`.
- Add background invalidation wiring for `TargetInvalidationRegistry`. Polling nodes should compare entry versions with locally seen versions, invalidate affected hot targets, and invalidate all local hot targets when registry results are truncated.
- Extend invalid-route cache invalidation to target-definition policy changes. Cold submit now clears matching invalid-route entries after a successful publish, and `InvalidRouteMetadataChangeListener` clears entries for indexer and target metadata events.
- Extend the first `AdminService` slices into a broader administration layer. Target/indexer list/get over flexible repository queries, target creation, standalone indexer creation, failed target-provisioning recovery, indexer activation/deactivation, metadata indexer delete, and indexer queue reset now exist. The first OpenAPI-backed admin REST read endpoints, target creation, standalone indexer creation, target provisioning recovery, indexer activate/deactivate, indexer delete, and indexer queue reset endpoints can now be deployed through the node envelope; future admin work should focus on command-result review, gateway exposure policy, and production wiring.
- Keep REST create preparation narrow and definition-driven. Target REST create accepts `target_name`, date-level time input, and optional create-indexer intent. Standalone indexer REST create accepts only `target_id`, loads the target record internally, generates names through `IndexerResourceNameGenerator`, and returns concrete admin result objects unless command-result review changes that contract.
- Extend target/action REST beyond the first `POST /targets/{target_name}/actions` slice when needed. The first slice supports internal/service-level target-envelope document mutations through `TargetActionService`; target/action submission should remain outside the external gateway unless a concrete external use case is approved.
- Extend runtime REST beyond the first `GET /runtime/status` and `POST /runtime/indexers/{id}/reconcile` slice when node-management infrastructure is designed. Current runtime REST is local-node only.
- Extend the external `GatewayRestVerticle` proxy layer. It is now a separate OpenAPI-backed deployable node service with upstream admin REST base URI configuration, optional static API-key authentication, optional in-memory rate limiting, request hooks for authorization/audit, typed public gateway errors, and approved admin read proxy routes for target and indexer lists. Next work should add real authorization and audit sink implementations plus deliberate approval for each additional public route.
- Add repository-backed mutation tracking only for the blend window where historical reload data is mixed with live stream mutations.
- Add production-backed enforcement of the target publication invariant. The in-memory repository now atomically replaces the published indexer for a target; production storage must preserve the same at-most-one-published-indexer rule without a transient no-published-indexer state.
- Add full load plugin orchestration around external `LoadProvider` implementations, including application-owned composition examples for `LoadIndexerPlugin` and final removal/tombstone handling after cancel or post-publish cleanup marks indexers deleting. Core node JSON options should remain plugin-free; load-enabled applications own the shared repository and plugin instances they pass through `IndexerNodeComponents`.
- Make lazy live-writer `prepareToReceive(...)` concurrency-safe as the workflow boundary. Production `attachLiveWriterIfAbsent(...)` must be an atomic correctness boundary on existing load metadata (`liveIndexerId` plus version), without adding lock/claim/session fields to the load record. Missing records, null requested live writer ids, and terminal loads fail. If a live writer is already linked, the operation returns that winner without requiring the expected version to match. If no live writer is linked, the operation requires the expected version, atomically sets `liveIndexerId`, increments version, and returns the attached writer. A version mismatch with no linked writer is a conflict: `prepareToReceive(...)` must reload load metadata and re-evaluate eligibility before retrying because another workflow may have changed approval, barrier, state, or other load metadata. Retry once inside the same prepare call after reload; do not loop indefinitely. If the second attempt conflicts again, fail the prepare path with a generic `RetryableStaleStateException` and let the outer command retry policy retry the submit command later. `RetryableStaleStateException` means the operation should retry from a fresh read snapshot, is not a terminal business failure, and should later map to command retry/backoff and service-level temporary error normalization. If reload finds a linked live writer, return that winner. If reload shows the load is no longer eligible, do not attach. If a candidate live writer was already created before a conflict or loser result and will not be used, mark/delete it through normal idempotent cleanup and emit `LAZY_LIVE_WRITER_PREPARATION_CONFLICT` for operational visibility. The event is not emitted for normal exclusive-flow waiting; it is emitted when a candidate is created but not used, or cleanup cannot be submitted/completed. Payload should include `targetId`, `loadIndexerId`, nullable `candidateLiveIndexerId`, nullable `winnerLiveIndexerId`, `reason`, `cleanupSubmitted`, nullable `cleanupSucceeded`, and `timestamp`. Reasons are `ATTACH_LOST`, `VERSION_CONFLICT`, `LOAD_NOT_ELIGIBLE_AFTER_RELOAD`, and `CLEANUP_FAILED`. Abandoned candidate cleanup is best-effort by default: a valid winner should still be returned and the live submit should continue when cleanup fails; cleanup failure must be operationally visible and retryable by normal cleanup/reconciliation. Strict cleanup mode is deferred and optional. A production storage adapter can implement attach-if-absent as conditional update where `liveIndexerId IS NULL`, version matches, and state is non-terminal, followed by a deterministic row read when no row was updated.
- Extend the implemented `indexer-events` module with subscriber APIs, serialization codecs, and distributed provider-backed transports only when concrete consumers require them. Event payloads, channel constants, consumers, and delivery guarantees remain domain-owned. Migrate `IndexerLifecycleEventBus` only in a later explicit scope, preserving lifecycle invalidation reliability and replay semantics rather than merging lifecycle and operational events into one channel.
- Add a distributed/provider-backed implementation of the existing `indexer-coordination` API. It must transport successful results through a general value-codec registry. For the current design, concrete `Class<T>` is the codec identity, one codec is registered per concrete type, and raw generic result types are unsupported; explicit codec ids and versions are deferred. The implemented local coordinator already shares lazy-live `PreparedIndexers` under `load-live-writer:{indexerId}` while each submit command publishes its own actions afterward. Atomic repository operations and abandoned-candidate cleanup remain the correctness boundary across nodes.
- When a distributed `indexer-coordination` provider is implemented, define its portable failure encoding. The current local stage shares the original `Throwable` through the in-memory promise and does not add a normalized failure model.
- Defer a standalone load-fail command until failures must be reported by a separate process that does not hold a `LoadWriter`. Provider-owned asynchronous failures should use `LoadWriter.fail(...)`.
- Define future partition/lane support for catch-up barriers. The first design assumes a single ordered catch-up queue; partitioned catch-up needs one barrier per ordered lane.
- Deferred: back the id-first `DocumentStoreMetadataRepository` with the production storage engine and preserve the insert/update/delete model split used by the in-memory implementation.

## Runtime Resources

- Treat `queueName` as immutable routing identity for normal lifecycle. `ResetIndexerQueueCommand` is a troubleshooting exception and should not be used for live/load swap. Revisit whether reset should instead create a replacement indexer and retire the old one when stricter immutability is required.
- Add an indexer-scoped hard reset mechanism for one or more indexers. Initial queue cleanup should not support item-by-item drain semantics. For Kafka, reset means advance a queue generation, update the durable queue name, create/use a new topic for future writes, and asynchronously clean the old topic. Treat missing old topics as successful idempotent cleanup misses.
- Store the initial reset generation in the concrete `IndexerRecord.queueName` only. A separate `queueGeneration` metadata field is deferred until generation-aware queries, stale item fencing, or stricter reset semantics require it. Queue names should use a deterministic suffix convention so old topics can be identified and cleaned asynchronously.
- Use the resulting `IndexerRecord.version` as the reset queue-name suffix, for example `{baseQueueName}-v{version}`. This keeps reset queue naming deterministic without adding a separate reset counter.
- Use the same queue-name composition rule for initial queue creation and reset re-creation. Reset derives the base queue name from the current durable `IndexerRecord.queueName` by stripping only a final reset suffix matching `-v[0-9]+`, then appending `-v{resultingVersion}`. Custom queue names remain supported.
- Make queue reset orchestration responsible for provisioning the new queue topic before publishing the metadata-change event that wakes runtime consumers. Runtime `Indexer` components should open consumers and publishers against resolved queue names, but must not own topic creation.
- Replace the legacy queue cleanup-only abstraction with a queue resource manager/admin abstraction that owns queue topic provisioning and deletion, for example `ensure(queueName)` and `delete(queueName)`. No backward compatibility shim is required; reset orchestration should use the renamed/replaced abstraction directly, while `IndexerQueueClient` remains runtime publish/consume only.
- Implement queue reset as a generic `CommandService` workflow, not as an `Indexer` method. The reset command should update durable metadata to the new queue name, provision the new topic through the queue resource manager, publish metadata-change fan-out, and delegate old topic cleanup.
- Keep the initial queue reset command scoped to one indexer per command. Bulk reset is deferred and can later be implemented as orchestration over multiple single-indexer reset commands.
- Require `expectedVersion` for queue reset and perform external provisioning before metadata update. The reset handler should load and validate the indexer version, compute the candidate queue name from the resulting version, ensure the new queue topic, then update metadata with the new queue name using the expected version. If queue creation fails, metadata remains unchanged and the runtime keeps using the old queue. If metadata update fails after topic creation, the new topic is unused and may be cleaned up or reused by retry when the deterministic name still matches.
- Publish metadata-change fan-out only after new topic provisioning and metadata queue-name update both succeed. Runtime nodes should switch queues by normal metadata reload/reconcile from the metadata-change event. If event publish fails after metadata update, durable metadata remains the source of truth and a retry or later runtime resync should republish/reconcile the current queue name.
- Treat old queue/topic cleanup as asynchronous best-effort after reset succeeds. Reset success is defined by new topic provisioning, metadata update, and metadata-change fan-out. Old topic deletion failure should not roll back or fail a completed reset; it should be retried by cleanup.
- Make runtime reconciliation replace stale local indexers when durable metadata version or queue name differs from the local runtime model. For active indexers, a stale local instance should be closed and recreated from latest metadata so queue reset by generated queue name takes effect.
- Make runtime reconciliation close local indexers whose durable runtime state is `NON_ACTIVE`. Deactivation should stop local consumers; this is a lifecycle correctness fix independent of queue reset.
- Add an explicit expected-version metadata operation for changing an indexer queue name, for example `UpdateIndexerQueueName`. Queue reset should use this operation after new topic provisioning succeeds rather than replacing the whole indexer record.
- Allow queue reset for `AVAILABLE` indexers that are not `MutationState.DELETING`, including runtime-`ACTIVE` and runtime-`NON_ACTIVE` indexers. Resetting a runtime-`NON_ACTIVE` indexer updates/provisions the queue but does not activate consumers; activation remains a separate lifecycle command.
- Keep the initial queue reset command in the existing `CommandService` `Future<Void>` style. The durable result is the updated `IndexerRecord`; callers reload metadata to inspect the new queue name and version. A typed reset result can be added later if command infrastructure supports it.
- Fail the reset command if metadata-change fan-out fails after metadata update. Metadata remains the source of truth, and retry should be idempotent: if the durable queue name is already advanced, the handler should avoid creating another queue unnecessarily and republish/reconcile the current metadata state.
- Defer distributed consumer-close acknowledgement and stale-generation item fencing until reset needs strict "old queued items cannot still be processed" semantics. The initial reset workflow is a troubleshooting mechanism that provides a clean queue for future writes, not a synchronous proof that every old in-flight item is dead.
- Add a smart consumer recovery mechanism for broken or unhealthy runtime consumers. Candidate indicators include stale lifecycle version, no progress while assigned to an active queue, repeated processing failures, excessive event-loop delay, high CPU pressure, low memory pressure, or missed heartbeat windows. Recovery should stop the local consumer, reload the latest metadata model, and reconcile from durable desired state rather than trusting stale local runtime state.
- Implement production-backed `IndexerQueueResourceManager` behavior for idempotent Kafka topic ensure/delete, using provider-owned `QueueDefinition` settings.
- Implement production-backed `IndexerDocumentIndexResourceManager` behavior for idempotent document-index ensure/delete, using provider-owned `IndexDefinition` settings and mappings.
- Define production document-index cleanup behavior through `CleanupDeletingIndexerCommandHandler` and `IndexerDocumentIndexResourceManager`, preserving idempotent missing-resource semantics.
