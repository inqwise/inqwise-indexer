# Roadmap

## Module Layout

- Keep the implemented `indexer-core` extraction stable. Current cycle-free slices own stable action payloads, runtime transport/processing/event/configuration contracts, document data-plane ports, action/provider/hot-routing contracts, command engine SPI, command envelope/partition/retry/failure primitives, durable cleanup command payloads, provisioning contracts/utilities, catalog ports, shared error primitives, definitions, and metadata contracts/models. Queue and document-index resource manager ports live under provisioning ownership. Local/in-memory implementations, metadata-backed providers, hot-routing services/listeners/local caches, provisioning orchestration, metadata-backed catalog implementations, cleanup handlers, command infrastructure, `IndexerRuntime`, `IndexerRuntimeReconciler`, service proxies, service verticles, node wiring, gateway/internal REST APIs, and OpenAPI wiring remain deployment-facing in `indexer`.
- Treat current services and service verticles as implementation/API candidates rather than final domain boundaries. Domain boundaries are accepted function-first: Target Catalog, Indexer Catalog, Publication, Action Routing, Indexer Runtime, Resource Provisioning, Deletion/Cleanup Workflow, Load/Reload, and Command Transport/Workflow Engine as infrastructure. Future refactors should group code by durable state ownership, invariants, and external-resource coordination before creating more Maven modules.
- Keep the current repository together while the approved domain boundaries stabilize. Reorganize packages inside `indexer` around those boundaries before splitting Maven modules or repositories. `indexer-load` remains the strongest future standalone domain-repository candidate because it already owns a cohesive load/reload workflow and metadata model.
- Do not preserve an empty `indexer-common` as a planned shared bucket. Shared indexer contracts continue to belong in `indexer-core`; introduce a common module only when a concrete non-indexer shared contract exists.
- Keep reusable build infrastructure in separate POM modules: `indexer-dependencies` as a dependency-management BOM and `indexer-parent` as the reusable build parent. The repository root is now the local aggregator rather than the parent external repositories inherit from.
- Defer repository splitting until release cadence and dependency direction justify it. Candidate future repository groups are build infrastructure, core contracts/support, load/reload, provider adapters, and deployable app/service composition. `indexer-load` is now source-separable from deployment-facing `indexer` for production code, but tests still share local adapters and in-memory composition. Runtime, control-plane, and routing should remain in the same repository until their contracts stop co-evolving heavily.
- Start package reorganization with ownership clarity rather than service names. Local adapters, runtime implementation, action-routing implementation, target/indexer catalog packages, cleanup workflow packages, and lifecycle wake-up infrastructure have been separated from root/package-generic command and management areas. Publication and provisioning names remain acceptable for their current ownership.
- The local-adapter package pass is complete for in-memory queue, document-store, lifecycle event-bus, metadata repository, target-invalidation registry, invalid-route cache, and static definition providers under `com.inqwise.indexer.adapters.local`. Core invalid-route matching is exposed through `InvalidRouteInvalidation.matches(...)`, keeping hot-routing contracts in `indexer-core.hot` while local in-memory storage remains an adapter.
- The runtime package pass is complete for `Indexer`, `IndexerRuntime`, `IndexerRuntimeReconciler`, `IndexerRuntimeReconcilerOptions`, `IndexerProcessorVerticle`, and `VerticleIndexerProcessor` under `com.inqwise.indexer.runtime`. `IndexerSnapshot` now has a public constructor because runtime status is a cross-package core contract.
- The core runtime-port pass moved queue transport ports, processor ports, and runtime event contracts under `com.inqwise.indexer.runtime` in `indexer-core`. Queue resource administration remains under provisioning ownership.
- The runtime contract pass moved `IndexerOptions`, `IndexerSnapshot`, and `IndexerMarkerHandler` under `com.inqwise.indexer.runtime` in `indexer-core`.
- The catalog model pass moved `IndexerModel`, `IndexerRole`, `IndexerRuntimeState`, `IndexerType`, and `IndexResourceOwnership` under `com.inqwise.indexer.catalog.indexers` in `indexer-core`. The core root package no longer owns generated model contracts.
- The document data-plane port pass moved `IndexerDocumentStore` under `com.inqwise.indexer.documents` in `indexer-core`. Metadata repositories stay under metadata ownership, and document-index ensure/delete capabilities stay under provisioning ownership.
- The action-routing package pass is complete for `SubmitIndexActionsCommandHandler`, `MetadataSubmitIndexActionRouter`, and `RoutedIndexActionPublisher` under `com.inqwise.indexer.routing`. The action-provider service-loader registry `Actions` now lives under `com.inqwise.indexer.actions`. Core action payload contracts also live under `com.inqwise.indexer.actions`, including `IndexerActionItem`, document actions, completion markers, and `IndexerActionType`. Command payload/shared routing DTOs remain in `indexer-core.commands` as transport/shared contracts.
- The catalog package pass is complete for target catalog contracts/implementation under `com.inqwise.indexer.catalog.targets` and indexer catalog contracts/implementation under `com.inqwise.indexer.catalog.indexers`. `CreateIndexerOperation` moved to indexer catalog because it is metadata-only. `IndexerProvisioningService` stays in provisioning because it coordinates catalog metadata with document-index and queue resource ensure.
- The repository-split readiness pass moved the shared `Actions` service-loader helper and metadata-only `CreateIndexerOperation` into `indexer-core`, allowing `indexer-load` production code to compile without depending on the deployment-facing `indexer` module. `indexer-load` now depends on `indexer` only for tests that use local adapters, in-memory command/runtime implementations, and integration composition helpers.
- The provider boundary exposes `IndexerModel` through both action-receive preparation and `ResolvedIndexer`; metadata records are validated, filtered, and converted inside metadata routing/provider adapters. `IndexerProviderQuery` intentionally retains lifecycle-state filters because eligibility selection is part of provider resolution, but resolved consumers do not receive persistence records.
- The `indexer-load` package pass is complete for API contracts, repository contracts, catalog ports, workflow implementation, runtime/plugin integration, durable command integration, operational events, metadata/local adapters, and test support. Metadata-backed implementations of creation/start, lazy live-writer, publication, and cleanup ports now live together under `com.inqwise.indexer.load.adapters.metadata`; catalog and repository packages are contract-only. `LoadPackageDependencyDirectionTest` enforces the accepted main-source package arrows, rejects wildcard load-slice imports, keeps load production code out of deployment-facing `indexer` adapter/gateway/node/REST/service packages, limits non-load `com.inqwise.indexer` imports to an exact accepted set of contract/support types, confines pre-split metadata imports to the metadata-adapter slice, and keeps load tests under accepted root composition/architecture exceptions or known slice/test-support packages. Runtime no longer imports workflow and may import only the publication command handoff helper from command integration; it must not import command payloads, handlers, handler registration, or partition-routing helpers directly. The shared publication handoff helper lives in command integration because it only decides whether to submit the durable publish command. Workflow may import durable command payload/handoff types, but not command handlers, handler registration, or partition-routing helpers. Keep those slices in one Maven module until external consumers require a smaller API or repository artifact. If a split becomes justified, start with provider-facing contracts and keep workflow implementation, command handlers, and repository mutation models together unless a production adapter SPI needs its own artifact.
- Accepted: replace the tolerated `indexer-load` direct metadata/catalog creation surface with load-facing catalog/repository ports before external repository separation. The current call sites need four groups of functions: resolve an active/ready target and create load/live writer metadata for load creation; reload target/load-writer/live-writer details to start the provider; lazily create, attach, resolve, and abandon live writers during cold action preparation; and validate/publish/replace the candidate indexer plus look up old/load writers for cleanup. Keep these ports narrow and load-owned at first, with implementations over the existing metadata repository/catalog helpers in the current repository. Do not move them to `indexer-core` or publish them as stable cross-repository APIs until the method names and DTOs survive implementation slices. Implemented slices: `LoadWriterActionReceiveCapability` now depends on `LazyLiveWriterCatalog`, backed by `MetadataLazyLiveWriterCatalog`, instead of constructing indexer metadata directly, and `LoadIndexerPlugin` receives that port from application composition rather than constructing its metadata adapter; the core action-receive SPI and lazy catalog now exchange existing `IndexerModel` views, with metadata-record conversion confined to metadata routing/adapters; `DefaultLoadManagementService` receives `LoadCreationCatalog` from application composition for target readiness, load/live writer creation, and provider-start metadata reload, while `MetadataLoadCreationCatalog` remains the adapter and creation orchestration exchanges load-owned target/indexer views rather than core metadata records; publication replacement and cleanup lookup now sit behind `LoadPublicationRepository` and `LoadCleanupRepository`, backed by `MetadataLoadPublicationRepository`, so command handlers no longer orchestrate direct metadata replacement/read logic or consume metadata indexer records, and `LoadCommandHandlers` receives both ports from application composition rather than constructing the metadata adapter.
- The load-port stabilization review is complete. Every field in the creation/start views is consumed by workflow creation, provider startup, or lifecycle wake-ups. Publication and cleanup use the narrower `LoadIndexerReference` containing only indexer id, target id, and optimistic version; the unused physical index name was removed rather than preserving a metadata-record-shaped transfer object.
- The operational queue-reset package pass moved `IndexerQueueManagementService`, `ResetIndexerQueueRequest`, and `MetadataIndexerQueueManagementService` under `com.inqwise.indexer.operations.queues`. Queue reset remains an operational troubleshooting boundary, separate from indexer catalog lifecycle and provisioning resource-manager capability code.
- The resource-provisioning contract pass moved `IndexerQueueResourceManager` into `com.inqwise.indexer.provisioning`, alongside `IndexerDocumentIndexResourceManager`. Runtime queue transport contracts remain separate from queue resource administration.
- The cleanup package pass is complete for durable delete and cleanup command payloads plus handlers under `com.inqwise.indexer.cleanup`. The generic `commands` package retains command engine, dispatch, retry/failure, partition routing, and shared action-routing command contracts.
- Domain-service tests for publication, target catalog, indexer catalog, provisioning, and operational queue reset now live under the matching domain test packages. Command test packages are reserved for command engine, transport, retry, partitioning, envelope, and shared command-contract tests.
- Runtime lifecycle, queue-flow, and reconciliation tests now live under `com.inqwise.indexer.runtime` with the runtime implementation tests.
- Action registry/provider tests, in-memory lifecycle provider tests, and local resource-manager adapter tests now live under their matching action, lifecycle, and local-adapter test packages. Remaining root-package tests should be kept only when they are intentionally shared contracts or cross-boundary helpers.
- Metadata-backed submit-action command handler tests now live under `com.inqwise.indexer.routing`, matching the cold action-routing implementation. Deployment-module root tests should stay limited to shared helpers or deliberately accepted composition tests.
- Shared deployment-module test helpers now live under `com.inqwise.indexer.testing`. The deployment root test package is empty and should stay that way unless a deliberate root-level test support reason is accepted.
- Core lifecycle event/config contract tests now live under `com.inqwise.indexer.lifecycle` in `indexer-core`. Core root tests should stay empty unless a deliberate cross-boundary core helper is introduced.
- The lifecycle package pass is complete for `MetadataChangeNotifier`, the Vert.x lifecycle event-bus provider, transport implementation, lifecycle event-bus options, and core lifecycle wake-up contracts under `com.inqwise.indexer.lifecycle`. Runtime, catalog, routing, cleanup, load, adapter, and node code import those contracts explicitly.
- Vert.x codegen package metadata is explicit for packages containing `@DataObject`, `@ProxyGen`, or `@VertxGen` types. Clean builds should not depend on stale package-info artifacts from earlier package layouts.
- Keep API/deployment packages (`service`, `rest`, `gateway`, `node`) as outer envelopes. They may depend inward on domain implementations, but domain implementation packages must not depend on REST, gateway, or node composition.

## Index Flow

- Keep the completed command classification enforced. The former request/reply command groups are migrated out of command registration; remaining command models are the intentional durable set: action transport (`SubmitIndexActionsCommand`), internal workflows (`DeleteIndexerCommand`, `PublishLoadCommand`), and cleanup (`CleanupDeletingIndexerCommand`, `CleanupResetIndexerQueueCommand`, `CleanupLoadCommand`). Core lifecycle/management operations, publication mark-ready/publish/retire, and load create/start/approve/cancel now execute through typed services while preserving confirmed durable submission of follow-up commands where required. Do not add creation idempotency metadata unless a future durable creation workflow introduces a concrete need.
- The current provider-neutral `IndexPublicationService` boundary is accepted for now: readiness, publish, retire, resource verification, exact-version replay, and provider-definition resolution stay together. Its service name, method names, and remote envelope remain provisional before external exposure. Target creation stays in the separate draft target-management service, delegating only optional publication steps to publication.
- The current `TargetManagementService` grouping is accepted for now: target-definition resolution, period resolution, concrete target creation, target READY/FAILED transitions, and failed-provisioning recovery stay in Target Catalog. Nested indexer creation and publication remain delegated to provisioning/publication services. Its service name, method names, and remote envelope remain provisional before external exposure.
- The current `IndexerManagementService` grouping is accepted for now: activate/deactivate owns desired runtime-state metadata, deletion fencing, exact-version replay, and lifecycle wake-ups. Standalone physical creation stays in `IndexerProvisioningService` because it resolves provider definitions, ensures document-index and queue resources, inserts manifest/publication metadata, and marks provisioning READY/FAILED. `CreateIndexerOperation` remains a catalog helper for metadata-only insertion. Service names, method names, and remote envelopes remain provisional before external exposure.
- The current `IndexerQueueManagementService` grouping is accepted for now: queue reset is operational troubleshooting orchestration, not indexer catalog lifecycle, runtime execution, generic provisioning, or generic command transport. It validates expected queue/version, provisions the deterministic replacement queue, advances queue metadata, emits lifecycle wake-up, and submits durable retired-queue cleanup through `CleanupResetIndexerQueueCommand`. Service name, method name, and remote envelope remain provisional before external exposure.
- Review the completed draft `LoadManagementService` migration in `indexer-load`; keep its name, method grouping, and placement provisional. Typed creation, explicit start, exact-version recovery, approval, and cancellation are implemented; create and start no longer use command transport, while approval and cancellation keep confirmed durable publish/cleanup handoff. Approval and cancellation recognize only their exact result at the requested version plus one before resubmitting the durable follow-up. Keep `PublishLoadCommand` and `CleanupLoadCommand` durable. Load creation now requires a concrete pre-existing active, ready target id and does not auto-provision targets; name generation for load writer prefix, index, queue, and immediate linked live queue is service-owned rather than caller-provided. Any optional target-management/provisioning orchestration before load creation remains a separate caller/service-envelope scope.
- Implement production persistence and retention policy for `IndexerLoadCompletion`. The accepted contract atomically replaces a cleanup-ready load record with a minimal terminal-state/version tombstone; exact completed cancellation retries succeed from that identity while unknown ids still fail. Keep operational completion identity separate from general audit history.
- Add public API error mapping so internal ids, index names, queue names, and storage details are not exposed directly to external callers.
- Add authorization, ownership checks, and rate limits before exposing auto-provision-on-write to public API traffic.
- Implement a Kafka-backed `CommandEngine` using the transport-neutral `CommandEnvelope`, `CommandEnvelopeCodec`, and command-service-owned `CommandPartitionKeyRouter`, with the resolved partition key supplied separately as Kafka record metadata. Kafka records and committed offsets are the first engine's durable state: commit only after handler success, leave retryable failures uncommitted, pause/seek the failed partition for local backoff while continuing to poll, and publish final failures durably before committing their source offsets. Kafka client implementation remains a separate scope.
- Integrate the implemented `CommandProcessor`, `CommandRetryPolicy`, and `CommandFailureClassifier` into resource-backed command engines. The processor already supplies one classified handler outcome without transport behavior. Same-record Kafka retry cannot durably preserve delay, attempt count, or exhaustion across rebalance; durable maximum attempts require retry-topic headers or another Kafka-owned state mechanism. Queue reset retry behavior should use the generic engine rather than handler-local loops. Deleting-indexer cleanup is already safe for generic redelivery.
- Integrate the implemented `CommandFailureClassifier` into the future queue-backed command executor and register concrete provider rules for transport/timeouts versus authentication/configuration failures. Explicit `CommandFailure`, retryable stale state, domain failures, and unknown defaults are already classified without handler-local retry loops.
- Defer action-level deduplication for publish retries. The planned queue-backed command engine retries the whole command, and current document actions should remain idempotent where practical. Add stable `actionId`, `batchId`, or persistent action dedupe only when non-idempotent action effects or operational duplicate suppression require it.
- Finish production composition for load/reload workflows. The provider-neutral orchestration now includes `LOAD_WRITER` plus optional linked `LIVE_WRITER`, external provider start, internal completion markers, atomic persisted catch-up barrier requests with retry-stable identity, review gating, automatic publish command submission, atomic metadata publish/replace, and terminal cleanup. Remaining work belongs to application/plugin assembly and production repository, queue, event, and command-engine adapters.
- Implement the selected production repository adapter against the accepted atomic `finalizeIndexerDeletion(...)` transaction contract and its conformance tests. Also add production queue/document resource managers for `CleanupDeletingIndexerCommandHandler`.
- Consider wrapping external queue/topic and document-index provisioning calls with Vert.x Circuit Breaker. Do not encode circuit-breaker behavior in the metadata model.

## Document Store Publishing

- Configure production deployments to select the implemented target-invalidation backend and namespace-isolated service placement. Node workflows and pollers always use the service proxy; one local service is enabled by default and can be disabled for remote-service consumers. The node configuration and startup wiring are implemented; deployment manifests, cluster-manager selection, credentials, and operational sizing remain application concerns. Confirmed `markInvalidated(targetId)` ownership belongs to metadata mutation workflows through `MetadataChangeNotifier`; listeners invalidate only local caches, already-applied retry paths re-mark without another metadata mutation, and both indexer and target metadata events are one-way wake-ups after the confirmed mark.
- Integrate `PublishedIndexResolver` when a concrete document-query execution contract or query API is introduced. Do not expose physical index resolution as a standalone service before a consumer exists; the implemented resolver remains the metadata boundary for target-name/time-range routing.
- Extend the first `AdminService` slices into a broader administration layer. Target/indexer list/get over flexible repository queries, target creation, standalone indexer creation, failed target-provisioning recovery, indexer activation/deactivation, metadata indexer delete, and indexer queue reset now exist. The first OpenAPI-backed admin REST read endpoints, target creation, standalone indexer creation, target provisioning recovery, indexer activate/deactivate, indexer delete, and indexer queue reset endpoints can now be deployed through the node envelope; future admin work should focus on command-result review, gateway exposure policy, and production wiring.
- Keep REST create preparation narrow and definition-driven. Target REST create accepts `target_name`, date-level time input, and optional create-indexer intent. Standalone indexer REST create accepts only `target_id`, loads the target record internally, generates names through `IndexerResourceNameGenerator`, and returns concrete admin result objects unless command-result review changes that contract.
- Extend target/action REST beyond the first `POST /targets/{target_name}/actions` slice when needed. The first slice supports internal/service-level target-envelope document mutations through `TargetActionService`; target/action submission should remain outside the external gateway unless a concrete external use case is approved.
- Extend runtime REST beyond the first `GET /runtime/status` and `POST /runtime/indexers/{id}/reconcile` slice when node-management infrastructure is designed. Current runtime REST is local-node only.
- Extend the external `GatewayRestVerticle` proxy layer. It is now a separate OpenAPI-backed deployable node service with upstream admin REST base URI configuration, optional static API-key authentication, optional in-memory rate limiting, request hooks for authorization/audit, typed public gateway errors, and approved admin read proxy routes for target and indexer lists. Next work should add real authorization and audit sink implementations plus deliberate approval for each additional public route.
- Add repository-backed mutation tracking only for the blend window where historical reload data is mixed with live stream mutations.
- Add production-backed enforcement of the target publication invariant. The in-memory repository now atomically replaces the published indexer for a target; production storage must preserve the same at-most-one-published-indexer rule without a transient no-published-indexer state.
- Extend production load application composition when concrete adapters are selected. Provider-neutral assembly now supplies `LoadCommandHandlers`, `LoadIndexerPlugin` cold-routing and runtime-marker contributions, shared repository/provider dependencies, and an end-to-end local composition test. Core node JSON options and default node wiring remain plugin-free. Production applications still own adapter construction, final audit/tombstone policy, and the plugin instances passed to their runtime and cold-submit composition.
- Implement production `attachLiveWriterIfAbsent(...)` with the atomic conditional-update contract already exercised by the in-memory repository and load workflow tests. Local retry, winner selection, abandoned-candidate cleanup, and conflict events are implemented; production storage must preserve the same behavior.
- Configure clustered Vert.x and deployment metrics outside this module when lifecycle wake-ups must cross nodes. The regular-EventBus `VertxIndexerLifecycleEventBusProvider`, namespace configuration, JSON transport envelopes, timestamp-lag detection, throttled local provider signals, closeable consumers, default node wiring, and an explicit deployment-metrics signal hook are implemented. Cluster creation, discovery, and reconnect monitoring remain cloud deployment concerns. Keep this lifecycle wake-up transport separate from the generic operational `indexer-events` publisher.
- Expose the implemented `IndexerNode.recover()` operation later through the restricted recovery-admin contract from the separate services-envelope scope. Runtime reconciliation itself is complete: startup and periodic full synchronization, serialized/coalesced indexer work, bounded dirty-map overflow, provider-signal synchronization, stale-version handling, local runtime convergence, and recovery-only data-plane supervision are implemented without durable reconciliation state or a stopped-node event backlog.
- Add a distributed/provider-backed implementation of the existing `indexer-coordination` API. It must transport successful results through a general value-codec registry. For the current design, concrete `Class<T>` is the codec identity, one codec is registered per concrete type, and raw generic result types are unsupported; explicit codec ids and versions are deferred. The implemented local coordinator already shares lazy-live `PreparedIndexers` under `load-live-writer:{indexerId}` while each submit command publishes its own actions afterward. Atomic repository operations and abandoned-candidate cleanup remain the correctness boundary across nodes.
- When a distributed `indexer-coordination` provider is implemented, define its portable failure encoding. The current local stage shares the original `Throwable` through the in-memory promise and does not add a normalized failure model.
- Defer a standalone load-fail command until failures must be reported by a separate process that does not hold a `LoadWriter`. Provider-owned asynchronous failures should use `LoadWriter.fail(...)`.
- Define future partition/lane support for catch-up barriers. The first design assumes a single ordered catch-up queue; partitioned catch-up needs one barrier per ordered lane.
- Deferred: select and implement the production storage engine behind the id-first `DocumentStoreMetadataRepository`, preserve the insert/update/delete model split, and run repository conformance suites against that adapter.

## Runtime Resources

- Keep `queueName` immutable for normal lifecycle and retain reset as an internal troubleshooting exception. If stricter routing immutability is required, replace reset with creation of a replacement indexer followed by normal retirement of the old indexer.
- Keep bulk queue reset deferred; implement it, if needed, as orchestration over existing single-indexer reset commands.
- Defer distributed consumer-close acknowledgement and stale-generation action fencing until reset needs strict proof that old queued or in-flight items cannot be processed. The current reset guarantees only that future writes use the new queue.
- Add a smart consumer recovery mechanism for broken or unhealthy runtime consumers. Candidate indicators include stale lifecycle version, no progress while assigned to an active queue, repeated processing failures, excessive event-loop delay, high CPU pressure, low memory pressure, or missed heartbeat windows. Recovery should stop the local consumer, reload the latest metadata model, and reconcile from durable desired state rather than trusting stale local runtime state.
- Implement production-backed `IndexerQueueResourceManager` behavior for idempotent Kafka topic ensure/delete, using provider-owned `QueueDefinition` settings and the accepted queue-resource conformance contract. Kafka client implementation is outside the current provider-neutral scope.
- Implement production-backed `IndexerDocumentIndexResourceManager` behavior against the accepted exact-identity, idempotent deletion contract, using provider-owned `IndexDefinition` settings and mappings. Production clients must disable implicit index creation and must not expand aliases or wildcard identities for cleanup.
