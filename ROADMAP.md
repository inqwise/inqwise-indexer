# Roadmap

## Index Flow

- Add public API error mapping so internal ids, index names, queue names, and storage details are not exposed directly to external callers.
- Add authorization, ownership checks, and rate limits before exposing auto-provision-on-write to public API traffic.
- Design the concrete queue/resource provisioning contract for indexer creation. In particular, decide whether `queueName` is always derived from `indexName`, stored explicitly on `IndexerModel`, or versioned for replacement/preload flows.
- Add durable command state storage for `SubmitIndexActionsCommand` when the command service moves beyond the in-memory implementation. The intended states are received, ensuring indexer, publish-ready, publishing, published, retryable failure, and final failure.
- Define command retry policy for the planned queue-backed command engine. Failed commands may be redelivered and processed by another consumer, so the command layer needs maximum retry count, retry/backoff timing, poison-command handling, final failure state, and operator visibility. Queue reset retry behavior should follow this generic command retry policy rather than embedding reset-specific retry loops.
- Add a separate `CommandStateRepository` for queue-backed command execution state. It should track command payload, status, attempts, maximum attempts, worker lease, retry timing, last error, timestamps, and optimistic version, and stay separate from `DocumentStoreMetadataRepository`.
- Add typed command failure classification while keeping the existing `Future<Void>` handler style. Command handlers should use a `CommandFailure`-style exception to distinguish retryable external failures from final validation/version/state failures. The queue-backed command engine should treat unknown failures as retryable until maximum attempts are exhausted.
- Defer action-level deduplication for publish retries. The planned queue-backed command engine retries the whole command, and current document actions should remain idempotent where practical. Add stable `actionId`, `batchId`, or persistent action dedupe only when non-idempotent action effects or operational duplicate suppression require it.
- Treat publish-readiness as a command/provisioning concern, not an `Indexer` runtime concern. Metadata checks remain first, and production readiness should additionally verify or ensure external queue/topic and document-index resources before publishing. Missing resources should fail closed or trigger provisioning/recovery commands rather than publishing blindly.
- Add an explicit retry/recovery command for concrete targets whose first writable indexer provisioning failed.
- Add a target creation command for creating public target definitions and, when requested, initial concrete targets through the generic `CommandService` layer instead of direct repository calls.
- Add an indexer creation/provisioning command that resolves static definitions, ensures document index and queue resources, inserts `IndexerRecord` and `ManifestRecord`, and marks the concrete target ready after resources are usable.
- Implement the `CompleteIndexActionItem` workflow. The flow must be command-orchestrated and target-aware, define exactly which indexer states it changes, and must not silently mark action streams complete until the durable completion semantics are implemented.
- Finish the indexer delete workflow after cleanup ownership is finalized. The current command marks the metadata indexer `DELETING` and runtime `NON_ACTIVE` so runtime nodes can clean resources from durable metadata; final repository removal or tombstone handling remains deferred.
- Consider wrapping external queue/topic and document-index provisioning calls with Vert.x Circuit Breaker. Do not encode circuit-breaker behavior in the metadata model.

## Document Store Publishing

- Add query API support for resolving `targetUid` or `targetName` plus a time range into published physical `indexName` values. Queries should skip missing period targets and return empty results when no published indexes exist.
- Add target-definition-level control for concrete target auto-creation. The current behavior auto-creates concrete targets on first write.
- Add a hot metadata layer for the action-item flow. It should keep an in-memory target/indexer structure filtered to operational routing records and decide whether actions can be forwarded to a hot target or must fall back to `SubmitIndexActionsCommand`.
- Add an administration metadata loading layer for broader target/indexer inspection and management. Unlike the hot layer, it must support wider status/state scopes and flexible repository queries.
- Add repository-backed mutation tracking only for the blend window where historical reload data is mixed with live stream mutations.
- Decide the query-side contract for resolving multiple published indexers by `targetId`, including ordering and conflict behavior when a target has more than one published physical index.
- Enforce the target publication invariant atomically: at most one indexer may be `PUBLISHED` for a target. Publishing a replacement indexer must not allow either two published indexers under the same target or a transient no-published-indexer state when a previous published indexer exists.
- Define `ReloadIndexer` blend mode for concurrent historical snapshot load plus live stream. This includes stale-write protection, a hot-path mutation-state store or document-store conditional writes, and indexer-scoped mutation-state cleanup after the blend window closes.
- Deferred: back the id-first `DocumentStoreMetadataRepository` with the production storage engine and preserve the insert/update/delete model split used by the in-memory implementation.

## Runtime Resources

- Make queue implementations isolate messages by resolved `queueName`. The in-memory queue must model per-queue publisher, consumer, and delete behavior so tests catch cross-indexer routing bugs before a production transport is introduced.
- Add an indexer-scoped hard reset mechanism for one or more indexers. Initial queue cleanup should not support item-by-item drain semantics. For Kafka, reset means advance a queue generation, update the durable queue name, create/use a new topic for future writes, and asynchronously clean the old topic. Treat missing old topics as successful idempotent cleanup misses.
- Store the initial reset generation in the concrete `IndexerRecord.queueName` only. A separate `queueGeneration` metadata field is deferred until generation-aware queries, stale item fencing, or stricter reset semantics require it. Queue names should use a deterministic suffix convention so old topics can be identified and cleaned asynchronously.
- Use the resulting `IndexerRecord.version` as the reset queue-name suffix, for example `{baseQueueName}-v{version}`. This keeps reset queue naming deterministic without adding a separate reset counter.
- Use the same queue-name composition rule for initial queue creation and reset re-creation. Reset derives the base queue name from the current durable `IndexerRecord.queueName` by stripping only a final reset suffix matching `-v[0-9]+`, then appending `-v{resultingVersion}`. Custom queue names remain supported.
- Make queue reset orchestration responsible for provisioning the new queue topic before publishing the metadata-change event that wakes runtime consumers. Runtime `Indexer` components should open consumers and publishers against resolved queue names, but must not own topic creation.
- Replace the legacy queue cleanup-only abstraction with a queue resource manager/admin abstraction that owns queue topic provisioning and deletion, for example `ensure(queueName)` and `delete(queueName)`. No backward compatibility shim is required; reset orchestration should use the renamed/replaced abstraction directly, while `IndexerQueueClient` remains runtime publish/consume only.
- Implement queue reset as a generic `CommandService` workflow, not as an `Indexer` method. The reset command should update durable metadata to the new queue name, provision the new topic through the queue resource manager, publish metadata-change fan-out, and delegate old topic cleanup.
- Keep the initial queue reset command scoped to one indexer per command. Bulk reset is deferred and can later be implemented as orchestration over multiple single-indexer reset commands.
- Require `expectedVersion` for queue reset and perform external provisioning before metadata update. The reset handler should load and validate the indexer version, compute the candidate queue name from the resulting version, ensure the new queue topic, then update metadata with the new queue name using the expected version. If queue creation fails, metadata remains unchanged and the runtime keeps using the old queue. If metadata update fails after topic creation, the new topic is unused and may be cleaned up or reused by retry when the deterministic name still matches.
- Publish metadata-change fan-out only after new topic provisioning and metadata queue-name update both succeed. Runtime nodes should switch queues by normal metadata reload/reconcile from the metadata-change event. If event publish fails after metadata update, durable metadata remains the source of truth and a retry or later runtime resync should republish/reconcile the current queue name.
- Treat old queue/topic cleanup as asynchronous best-effort after reset succeeds. Reset success is defined by new topic provisioning, metadata update, and metadata-change fan-out. Old topic deletion failure should not roll back or fail a completed reset; it should be retried by cleanup.
- Make runtime reconciliation replace stale local indexers when durable metadata version or queue name differs from the local runtime model. For active indexers, a stale local instance should be closed and recreated from latest metadata so queue reset by generated queue name takes effect.
- Make runtime reconciliation close local indexers whose durable runtime state is `NON_ACTIVE`. Deactivation should stop local consumers; this is a lifecycle correctness fix independent of queue reset.
- Add an explicit expected-version metadata operation for changing an indexer queue name, for example `UpdateIndexerQueueName`. Queue reset should use this operation after new topic provisioning succeeds rather than replacing the whole indexer record.
- Allow queue reset for `AVAILABLE` indexers that are not `MutationState.DELETING`, including runtime-`ACTIVE` and runtime-`NON_ACTIVE` indexers. Resetting a runtime-`NON_ACTIVE` indexer updates/provisions the queue but does not activate consumers; activation remains a separate lifecycle command.
- Keep the initial queue reset command in the existing `CommandService` `Future<Void>` style. The durable result is the updated `IndexerRecord`; callers reload metadata to inspect the new queue name and version. A typed reset result can be added later if command infrastructure supports it.
- Fail the reset command if metadata-change fan-out fails after metadata update. Metadata remains the source of truth, and retry should be idempotent: if the durable queue name is already advanced, the handler should avoid creating another queue unnecessarily and republish/reconcile the current metadata state.
- Defer distributed consumer-close acknowledgement and stale-generation item fencing until reset needs strict "old queued items cannot still be processed" semantics. The initial reset workflow is a troubleshooting mechanism that provides a clean queue for future writes, not a synchronous proof that every old in-flight item is dead.
- Add a smart consumer recovery mechanism for broken or unhealthy runtime consumers. Candidate indicators include stale lifecycle version, no progress while assigned to an active queue, repeated processing failures, excessive event-loop delay, high CPU pressure, low memory pressure, or missed heartbeat windows. Recovery should stop the local consumer, reload the latest metadata model, and reconcile from durable desired state rather than trusting stale local runtime state.
- Define production `IndexerQueueResourceManager` behavior for idempotent Kafka topic ensure/delete.
- Define production document-index cleanup behavior through `IndexerResourceCleaner`.
