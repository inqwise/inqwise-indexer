# Roadmap

## Scope

- Current project completion covers provider-neutral domain contracts, workflows, local/in-memory adapters, application composition boundaries, and conformance tests.
- Production repository implementations and durable/Kafka-backed `CommandEngine` implementations are external integration concerns. Keep their required atomicity, ordering, retry, and compatibility contracts documented, but do not treat implementation of those adapters as unfinished work in this repository.
- The concrete report-consumer requirement established the provider-neutral `indexer-query` boundary: generic report dispatch, trusted-scope enforcement, Publication-backed multi-index selection, schema-compatible execution grouping, typed report helpers, and the document-query provider port are accepted repository scope. `ReportExecutionRequest` contains only report identity and user parameters; deployment composition injects `ReportCaller` into the server implementation, and the server-owned consumer context resolver selects maximum scope without coupling consumer identity to target ownership. Physical indexes are visible only to provider execution, not consumer report decoding. The separate `indexer-example-hacker-news-reports` module validates both document-shaped and aggregate result flows with typed story-search and grouped story-author reports, codecs, facade methods, in-memory capability dispatch, and consumer-owned OpenAPI adapters. Story search owns stateless keyset pagination ordered by score/time/id; its versioned cursor is criteria-bound, is never trusted scope, and does not establish a frozen read snapshot. The author summary deduplicates multi-index story identities before grouping and supports bounded deterministic aggregate ordering. Keep pagination semantics in the concrete consumer/provider unless multiple real providers establish a neutral common contract. Keeping this module separate prevents node/report composition from importing the HN polling launcher and logging resources. Query-provider implementation in this scope ends at `InMemoryIndexerDocumentStore`. Elasticsearch, OpenSearch, and every other external store adapter must be planned and implemented independently in provider-specific threads; do not introduce a speculative common external-search layer here. Public exposure and authentication/context construction remain external composition work.
- Keep the consumer stored-document contract independent from ingestion, action transport, and reports. `indexer-example-hacker-news-model` owns `HackerNewsDocument`, its builder validation, and its JSON codec; ingestion and the consumer action preparer validate and encode before routing PUT actions, while the in-memory query provider decodes through the same contract. Report projections remain report-owned. Provider-specific appended fields may wrap the base codec and are tolerated during base decoding, but external-store enrichment remains part of each future provider-specific thread.
- Keep the public gateway read-only until deployment authorization, ownership, and audit contracts are selected. Current administration mutations, target-action submission, runtime reconcile, and node recovery operations remain internal even though some have internal REST envelopes.
- Keep `indexer-web` as an internal operator console over existing HTTP envelopes. Its accepted current-stage shape is a separate logical Maven module packaged by `indexer-node-application`: Vite owns hot reload only, while `IndexerWebVerticle` serves the compiled SPA and forwards the same-origin `/api/{service}` paths to the internal REST ports. The wrapper remains a delivery adapter with no Indexer domain/runtime or Gateway dependency. Admin, Runtime, and neutral Reports response/error schemas are concrete OpenAPI contracts, and the frontend generates its typed `openapi-fetch` clients from them. Reports are represented in the console only by a bounded read-only activity view: neutral discovery supplies stable names/titles, while a fixed Prometheus projection supplies process-lifetime succeeded/invalid/failed counts, active executions, and duration totals. The console does not submit report parameters or render report results. Report monitoring remains a provider-neutral `indexer-query` port, and deployment-owned adapters must bound report-name labels to the registered catalog with one shared unknown-name bucket. Consumer fields, trusted scope, logical targets, physical indexes, and arbitrary metric series remain hidden. Read-only catalog filtering, deterministic sorting, bounded pagination, and entity details remain client-side projections over those responses. Explicit stable-ID navigation links Indexer/Target/Runtime relationships through the already-loaded catalogs, preserves mutually exclusive shareable entity selection, and exposes broken references; physical names and arbitrary report fields are not inferred as identities. Live monitoring uses serialized, visibility-aware polling with operator-selectable intervals, last-success stale-data reporting, runtime attachment drift, and URL-persisted view state. Readiness, target catalog, indexer catalog, and runtime envelopes are monitored independently so partial failure retains last-good data and does not mask healthy service results. Catalog sort, row-limit, page, and filter state are URL-persisted. A read-only same-origin Prometheus proxy feeds a compact bounded projection of action intake, indexing outcomes, runtime convergence, lifecycle operations, and report activity; the frontend does not accept arbitrary metric names or labels. A bounded read-only attention queue derives active conditions from those loaded service, catalog, runtime, and metrics projections, caps rendered issue cards, and navigates to existing diagnostic/entity views. Cumulative rejected, failed, and retrying counters remain explicitly labeled observations rather than active incidents. Node Diagnostics consumes the existing node-status, infrastructure-status, invalid-route, and target-invalidation Admin contracts as four independently monitored last-good envelopes. It caps all rendered collections/text, restricts infrastructure details to bounded non-sensitive scalars, and links routing identities only by explicit catalog ids or one unambiguous target-name/period match. It must remain read-only and must not become a second health probe or expose arbitrary nested configuration. Bounded operation slices now include version-aware indexer activate/deactivate, failed target-provisioning recovery, node-local manual runtime reconciliation, explicitly confirmed single-indexer queue reset, and typed-name-confirmed single-indexer deletion, with pending/error feedback and a durable-state refresh after every attempt. Catalog mutations use exact `expected_version`; reconciliation does not mutate the desired catalog state. Queue reset advances to a new versioned queue and schedules durable retired-queue cleanup without claiming synchronous old-item fencing. Deletion fences the indexer and accepts durable cleanup before physical cleanup completes. Keep bulk destructive operations outside this scope. Public exposure, identity, and authorization remain deployment decisions outside this scope.
- Organize new internal admin REST paths by architecture ownership rather than implementation class. The accepted top-level groups are `/admin/catalog`, `/admin/definitions`, `/admin/routing`, `/admin/node`, `/admin/loads`, and `/admin/infrastructure`. Health checks must remain small availability probes and must not duplicate infrastructure diagnostics. Existing flat `/admin/targets` and `/admin/indexers` paths are compatibility aliases; new callers should use `/admin/catalog`.
- The `/admin/definitions` group is read-only and exposes node-loaded provider snapshots, not repository catalog state. Target definitions are listed and fetched by `target_name`. The current indexer-definition provider has one effective physical definition, exposed as `default`; richer selector keys require a future provider contract change rather than synthetic API names.
- The `/admin/routing` group is read-only diagnostics over current node routing memory. `invalid-routes` exposes bounded cached stable route failures, `target-invalidations` exposes bounded pending target invalidation entries from the node's target invalidation registry, and `hot-targets` exposes the actual node-local concrete targets plus explicit hot indexer ids from `HotRoutingDiagnostics`. Target and per-target indexer results are capped and carry truncation flags. The console treats absent, empty, populated, and unavailable results distinctly and must not infer hot membership from catalog fields. These are not health checks, not durable repositories, and not public gateway routes.
- The `/admin/node/status` endpoint exposes node-local lifecycle and composition facts: started/ready/recovery-only/stopping booleans, clustered mode, deployment counts by control/data/infrastructure group, configured service instances versus deployed instances, lifecycle-event namespace, and target-invalidation provider identity. It is diagnostic state and must not replace the health endpoints or runtime indexer status.
- The `/admin/loads` group is implemented in the load-owned REST contract as aliases over `LoadService`, not as core `AdminService` methods. The existing `/loads` paths remain internal compatibility aliases. Keep load creation/start/recovery/review/cancel workflow state inside `indexer-load`.
- Load workflow visibility uses a separate load-owned query service and `GET /admin/loads` contract rather than extending core Admin or enabling mutations in the console. The repository query is bounded and newest-first; its read model exposes workflow state/version, explicit target/load-writer/live-writer ids, review/barrier/failure facts, and timestamps while omitting source-query payloads. The local node composes this read side over its local load repository, and the console requests 50 records, renders at most 25, retains last-good data independently, and links only explicit catalog ids. Load create/start/recover/approve/cancel controls remain deferred until visibility and production authorization exist.
- The `/admin/infrastructure/status` endpoint exposes node-local infrastructure implementation and safe configuration facts as generic diagnostic items. It includes provider/adapter identities, service-proxy addresses, REST bind options, lifecycle namespace/cluster mode, target-invalidation provider configuration, and command-engine implementation details available from the selected engine. It is not a health endpoint and must not grow into availability probing.
- Keep `IndexerNodeApplicationVerticle` as the consumer-neutral root execution verticle. `DefaultIndexerApplicationProvider` owns node construction and its private repository/runtime/document resources, exposes only lifecycle plus narrow load/report services, and automatically loads every packaged `ReportsProviderFactory` and `TargetActionPreparationProvider` with duplicate identity/report/target rejection. Configuration must not select concrete reports. The generic node artifact contains no HN dependency. A distribution opts into concrete capabilities only by packaging provider artifacts; generic report discovery/execution lifecycle remains root-owned and participates in rollback/reverse shutdown. The current report provider context exposes in-memory snapshots only. External document stores require separate provider-specific composition in later scopes rather than widening this local adapter.
- The node image includes the Hazelcast cluster manager but launches standalone by default. `INDEXER_CLUSTERED=true` adds the deployment-owned Compose cluster override, explicit TCP discovery configuration, and independently configurable bind, advertised, and Docker-forwarded Hazelcast/EventBus addresses without adding a custom `main()` method. The local launchers detect the address selected by the host's default route and accept `INDEXER_PUBLIC_HOST` plus endpoint-specific overrides; raw Compose defaults remain loopback-only. This validates cluster-capable delivery and remote EventBus participation; it does not authorize multiple state-owning Indexer replicas while persistence, queue, document, and command adapters remain local/in-memory.
- The first concrete data project is `indexer-example-hacker-news`. Keep its source polling, in-memory fingerprints, and HN projection in the outer example module. It runs as a separate clustered Vert.x application, obtains the generated Target Action EventBus proxy, and never constructs `IndexerNode` or accesses node-local repositories, queues, runtimes, or document adapters. The accepted slice consumes only the current `/v0/updates` window, uses stable item ids for idempotent PUT/REMOVE actions, bounds request concurrency and action batches, and intentionally performs no archive or historical backfill. In the separated-process profile, deploy the Indexer node independently in the same cluster with a matching `hacker-news` target definition; the optional combined deployment remains an outer wrapper around these two applications.
- Keep `indexer-example-hacker-news-node-application` as an optional combined distribution, not the only topology. Its dependencies package the standalone source plus HN action/report providers; Maven Shade merges their service descriptors. The wrapper starts the unchanged generic root before HN ingestion and rolls it back when ingestion startup fails. The same distribution may instead launch `IndexerNodeApplicationVerticle` alone—with HN providers auto-loaded—while `indexer-example-hacker-news` runs as a separate clustered process. A bare generic node has no HN reports. Because the current document store is process-local, an HN report provider must be packaged with the state-owning node; placing it in an independent container cannot query that node until a real remote document-store adapter is introduced.

## Query And Report Follow-ups

- The consumer-neutral report delivery slice is accepted. Optional
  `ReportPresentation` metadata contains only a stable name, title,
  description, and draft 2020-12 object schemas for user parameters and encoded
  results; `ReportDiscoveryService` is read-only and remains separate from
  execution. `indexer-query-rest` provides neutral discovery/execution HTTP
  delivery, and `indexer-web` renders only the accepted bounded schema subset.
  Do not expand schema support without a concrete consumer need, resolve remote
  references, or import a consumer module or consumer-owned OpenAPI contract
  into the operator console.

- The internal console Definitions & Capabilities view consumes target and indexer definition snapshots independently, bounds collections and displayed top-level configuration keys, omits credential-like keys and nested values, and links a target definition only when one loaded catalog target matches its logical name. Definitions remain read-only provider configuration; the UI must not infer indexer-definition identity from schema or physical names.
- Keep the current query provider contract capability-based and typed. Do not select a universal user-facing query language yet. Revisit query-language design only after concrete external-store adapters establish the required OpenSearch, Elasticsearch, or other engine semantics; provider-specific expressive query objects must remain behind trusted report definitions and must never be accepted directly from a generic report request.
- Implement each external document-store query adapter as an independently scoped provider integration. Its thread must decide client ownership, physical request construction, schema/version behavior, error classification, pagination consistency, and any store-specific document enrichment. The current in-memory provider is complete for this thread and is not a placeholder adapter for those engines.
- Add further concrete reports in consumer-specific threads. Promote cursor, aggregation, projection, or query-language concepts into `indexer-query` only after multiple real reports/providers demonstrate a stable shared abstraction.
- Add authenticated principal resolution and construction of trusted report context at the gateway or deployment boundary before public report exposure. `indexer-query` continues to enforce the supplied maximum scope without authenticating the caller or creating a consumer-target ownership relationship.
- Add durable idempotent follow-up commands or an approved outbox only when a concrete required post-action side effect exists. Runtime after-commit observers remain best-effort notifications and cannot supply cross-system atomicity.

## Module Layout

- Keep the implemented `indexer-core` extraction stable. Current cycle-free slices own stable action payloads, runtime transport/processing/event/configuration contracts, document data-plane ports, action/provider/hot-routing contracts, command engine SPI, command envelope/partition/retry/failure primitives, durable cleanup command payloads, provisioning contracts/resource definitions/utilities, catalog ports, shared error primitives, and metadata contracts/models. Queue/document resource managers and physical indexer definition contracts live under provisioning ownership. Local/in-memory implementations, metadata-backed providers, hot-routing services/listeners/local caches, provisioning orchestration, metadata-backed catalog implementations, cleanup handlers, command infrastructure, `IndexerRuntime`, `IndexerRuntimeReconciler`, service proxies, service verticles, node wiring, gateway/internal REST APIs, and OpenAPI wiring remain deployment-facing in `indexer`.
- Treat current services and service verticles as implementation/API candidates rather than final domain boundaries. Domain boundaries are accepted function-first: Target Catalog, Indexer Catalog, Publication, Action Routing, Indexer Runtime, Resource Provisioning, Deletion/Cleanup Workflow, Load/Reload, and Command Transport/Workflow Engine as infrastructure. Future refactors should group code by durable state ownership, invariants, and external-resource coordination before creating more Maven modules.
- Keep the current repository together while the approved domain boundaries stabilize. Reorganize packages inside `indexer` around those boundaries before splitting Maven modules or repositories. `indexer-load` remains the strongest future standalone domain-repository candidate because it already owns a cohesive load/reload workflow and metadata model.
- Do not preserve an empty `indexer-common` as a planned shared bucket. Shared indexer contracts continue to belong in `indexer-core`; introduce a common module only when a concrete non-indexer shared contract exists.
- Keep reusable build infrastructure in separate POM modules: `indexer-dependencies` as a dependency-management BOM and `indexer-parent` as the reusable build parent. The repository root is now the local aggregator rather than the parent external repositories inherit from.
- Keep `indexer-query` as a separate provider-neutral report/query module depending only on `indexer-core` plus Vert.x/service support. It owns `ReportsService`, server-injected caller/context resolution, report catalog/definition contracts, trusted scope composition, effective query planning, Publication resolver integration, schema-compatible execution grouping, the query-provider port, and typed report helpers. Caller construction and authentication remain deployment concerns; caller identity must never enter the report request transport. Physical identities remain provider-input-only. One provider per facade is the current composition invariant; mixed-provider resolution requires explicit provider/strategy identity before implementation. It must not depend on deployment-facing `indexer`, load/reload, runtime workers, node/application modules, consumers, or concrete provider clients.
- Keep consumer action preparation outside `indexer-query` and separate from `IndexerActionProvider`. `TargetActionService` may invoke one deployment-selected `TargetActionPreparer` before hot routing; unregistered targets pass through, preparation is batch-atomic, and count/type preservation is enforced. The initial HN implementation validates ids and canonicalizes shared-model JSON. Runtime document hooks are a separate injected capability with immutable context: pre-action failures prevent writes, post-write/pre-commit failures leave work uncommitted for recovery/redelivery, and after-commit failures are reported without rollback or blocking resume. Marker actions remain outside document hooks. Required durable side effects and cross-system atomic handoff remain deferred until a concrete command/outbox use case exists; provider-specific enrichment remains part of its store-adapter scope.
- Defer repository splitting until release cadence and dependency direction justify it. Candidate future repository groups are build infrastructure, core contracts/support, load/reload, provider adapters, and deployable app/service composition. `indexer-load` is now source-separable from deployment-facing `indexer` for production code, but tests still share local adapters and in-memory composition. Runtime, control-plane, and routing should remain in the same repository until their contracts stop co-evolving heavily.
- Start package reorganization with ownership clarity rather than service names. Local adapters, runtime implementation, action-routing implementation, target/indexer catalog packages, cleanup workflow packages, and lifecycle wake-up infrastructure have been separated from root/package-generic command and management areas. Publication and provisioning names remain acceptable for their current ownership.
- The local-adapter package pass is complete for the in-memory command engine, queue, document-store, lifecycle event-bus, metadata repository, target-invalidation registry, invalid-route cache, and static definition providers under `com.inqwise.indexer.adapters.local`. Core invalid-route cache/signature/invalidation contracts and cold-command signature construction live in `indexer-core.routing`; hot-request signature construction stays in `indexer-core.hot`. Keep the dependency one-way from the hot fast path to Action Routing. Concrete resource-backed command engines should be sibling adapters over the core `CommandEngine` and processing contracts.
- The runtime package pass is complete for `Indexer`, `IndexerRuntime`, `IndexerRuntimeReconciler`, `IndexerRuntimeReconcilerOptions`, `IndexerProcessorVerticle`, and `VerticleIndexerProcessor` under `com.inqwise.indexer.runtime`. `IndexerSnapshot` is a cross-package core status contract with validated public builder construction and a private constructor.
- The core runtime-port pass moved queue transport ports, processor ports, and runtime event contracts under `com.inqwise.indexer.runtime` in `indexer-core`. Queue resource administration remains under provisioning ownership.
- The runtime contract pass keeps `IndexerOptions` and `IndexerSnapshot` under `com.inqwise.indexer.runtime` in `indexer-core`. `IndexerMarkerHandler` is provider-owned because plugins select it per model; runtime consumes the selected capability, and providers must not depend back on runtime implementation or hot routing.
- The catalog model pass moved `IndexerModel`, `IndexerRole`, `IndexerRuntimeState`, `IndexerType`, `IndexResourceOwnership`, `IndexerStatus`, `IndexerProvisioningState`, and `MutationState` under `com.inqwise.indexer.catalog.indexers` in `indexer-core`. Metadata records and mutation DTOs consume these catalog states. `IndexerMetadataQuery` remains in metadata because it combines Indexer Catalog and Publication filters.
- Resource Provisioning owns `ManifestStatus`, which marks the active persisted snapshot of the physical index and queue definitions used during provisioning. Manifest records and repository mutation DTOs remain under metadata persistence. Do not introduce a separate manifest/configuration domain until promotion, supersession, or version-selection workflows establish an independent behavioral boundary.
- `IndexerProvisioningService` returns the minimal provisioning-owned `ProvisionedIndexer` identity/version result rather than exposing `metadata.IndexerRecord`. Consumers reload a persistence record through their own repository dependency when needed. Keep core provisioning contracts free of metadata imports; the deployment architecture guard enforces this direction.
- `IndexPublicationService` returns publication-owned `PublicationReadinessResult` and `IndexPublicationResult` operation outcomes rather than metadata persistence records. Keep core Publication contracts free of metadata imports; persistence-rich views stay inside metadata adapters and outer API facades.
- `TargetManagementService` returns the catalog-owned `TargetManagementResult` rather than `metadata.TargetRecord`. Outer API facades reload persistence-rich target views through their repository dependency. Keep core Target Catalog contracts free of metadata imports; the architecture guard enforces this direction.
- `IndexerManagementService` returns `IndexerRuntimeStateResult` rather than `metadata.IndexerRecord` for activate/deactivate outcomes. Outer API facades reload persistence-rich views through their repository dependency. Core Indexer Catalog is now entirely free of metadata imports; a package-wide architecture guard enforces this direction.
- `IndexerOperations.markDeleting(...)` returns optional `IndexerDeletionResult` rather than `metadata.IndexerRecord`. The result carries the `DELETING`/`NON_ACTIVE` fence and optimistic version required by cleanup handoff. Admin reloads its response view before submitting cleanup because local command execution may finalize deletion synchronously. Keep the deletion operation, request, and result contracts free of metadata imports.
- The document data-plane port pass moved `IndexerDocumentStore` under `com.inqwise.indexer.documents` in `indexer-core`. Metadata repositories stay under metadata ownership, and document-index ensure/delete capabilities stay under provisioning ownership.
- The action-routing package pass is complete for `SubmitIndexActionsCommand`, `ActionDestination`, `RoutedIndexActions`, `RoutingCommandPartitionKeyResolvers`, `SubmitIndexActionsCommandHandler`, `MetadataSubmitIndexActionRouter`, and the publishing boundary under `com.inqwise.indexer.routing`. `IndexerPublishingService` is the accepted service-shaped contract for publishing concrete routed action groups from hot routing, cold routing, and load writers. Default node composition uses the strict local `RuntimeIndexerPublishingService`, which publishes only through active runtime-owned indexers and validates route identity/version before delegating to the indexer producer path. `QueueIndexerPublishingService` remains an explicit raw-queue adapter for tests and deliberately non-runtime compositions. An EventBus service proxy remains deferred until the usage requires cross-verticle or cross-node routing through that boundary. The reusable routing contracts remain in `indexer-core`, but generic `commands` no longer owns or registers action-specific behavior. The action-provider contract `IndexerActionProvider` and its service-loader registry `Actions` live under `com.inqwise.indexer.actions`; the former generic `spi` package is removed. Core action payload contracts also live under `com.inqwise.indexer.actions`, including `IndexerActionItem`, document actions, completion markers, and `IndexerActionType`. Action JSON constructors are package-private; application code must use logical/concrete factories, marker builders, or the central parser. `SubmitIndexActionsCommand` exposes builder/parser construction only.
- The catalog package pass is complete for target catalog contracts/implementation under `com.inqwise.indexer.catalog.targets` and indexer catalog contracts/implementation under `com.inqwise.indexer.catalog.indexers`. Target naming validation/encoding, concrete target keys, UTC period strategy/resolution, status, provisioning state, catalog query criteria, auto-provision policy, and target-definition lookup are owned by Target Catalog; metadata persistence contracts consume these catalog values. Target records and repository mutation DTOs remain in `metadata` until shared UID formatting and repository/entity ownership are deliberately redesigned. Physical index, queue, and combined indexer resource definitions plus their provider contract live under `provisioning.definitions`; Catalog must not depend directly on them. `CreateIndexerOperation` is persistence-owned under `metadata` because it directly accepts repository mutations and returns records. The core `IndexerProvisioningService` contract and deployment-module `MetadataIndexerProvisioningService` implementation stay in provisioning because they coordinate catalog metadata with document-index and queue resource ensure.
- Target Catalog uses `TargetDefinitionNotFoundException` for missing configured definitions and remains independent of generic command failure/retry semantics. Service envelopes map this to their public not-found contract; Action Routing owns separate command classification for the same environmental condition.
- Target creation validates canonical target names in `CreateTargetRequest` before definition lookup or persistence, keeping malformed input distinct from a genuinely missing configured definition.
- The repository-split readiness pass moved the shared `Actions` service-loader helper and metadata-only `metadata.CreateIndexerOperation` into `indexer-core`, allowing `indexer-load` production code to compile without depending on the deployment-facing `indexer` module. `indexer-load` now depends on `indexer` only for tests that use local adapters, in-memory command/runtime implementations, and integration composition helpers.
- The provider boundary exposes `IndexerModel` through both action-receive preparation and `ResolvedIndexer`; metadata records are validated, filtered, and converted inside metadata routing/provider adapters. `IndexerProviderQuery` intentionally retains lifecycle-state filters because eligibility selection is part of provider resolution, but resolved consumers do not receive persistence records.
- Publication lifecycle and readiness states live under `com.inqwise.indexer.publication`. The nested target-creation `InitialPublicationMode` option is Target Catalog-owned because only that workflow consumes it; Publication Lifecycle remains a service dependency of the deployment implementation, not part of the core Target Catalog contract. Metadata `IndexerRecord`, `PublicationRecord`, mixed query criteria, and insert/update DTOs consume publication domain states while remaining persistence-owned. Publication records stay in metadata until shared UID formatting and repository/entity ownership are deliberately redesigned.
- `autoPublishOnWrite` is Target Catalog policy attached to `TargetDefinition`, while the actual publish transition remains owned by `IndexPublicationService`. When the option is omitted, it follows `autoProvisionOnWrite`; explicit `false` supports write-only auto-provisioning without making the generated writer queryable.
- `ResolvedIndexer` exposes optional provider-owned `HotIndexerCapability`; `MetadataHotIndexer` lives with the metadata-backed provider implementation. `IndexerPlugin` also exposes provider-owned model-scoped `IndexerMarkerHandler` selection. Hot views and runtime consume provider capabilities, while provider packages must not import hot view/cache or runtime types.
- The `indexer-load` package pass is complete for API contracts, repository contracts, catalog ports, workflow implementation, runtime/plugin integration, durable command integration, operational events, metadata/local adapters, and test support. Metadata-backed implementations of creation/start, lazy live-writer, publication, and cleanup ports now live together under `com.inqwise.indexer.load.adapters.metadata`; catalog and repository packages are contract-only. `LoadPackageDependencyDirectionTest` enforces the accepted main-source package arrows, rejects wildcard load-slice imports, keeps load production code out of deployment-facing `indexer` adapter/gateway/node/REST/service packages, limits non-load `com.inqwise.indexer` imports to an exact accepted set of contract/support types, confines pre-split metadata imports to the metadata-adapter slice, and keeps load tests under accepted root composition/architecture exceptions or known slice/test-support packages. Runtime no longer imports workflow and may import only the publication command handoff helper from command integration; it must not import command payloads, handlers, handler registration, or partition-routing helpers directly. The shared publication handoff helper lives in command integration because it only decides whether to submit the durable publish command. Workflow may import durable command payload/handoff types, but not command handlers, handler registration, or partition-routing helpers. Keep those slices in one Maven module until external consumers require a smaller API or repository artifact. If a split becomes justified, start with provider-facing contracts and keep workflow implementation, command handlers, and repository mutation models together unless a production adapter SPI needs its own artifact.
- Accepted: replace the tolerated `indexer-load` direct metadata/catalog creation surface with load-facing catalog/repository ports before external repository separation. The current call sites need four groups of functions: resolve an active/ready target and create load/live writer metadata for load creation; reload target/load-writer/live-writer details to start the provider; lazily create, attach, resolve, and abandon live writers during cold action preparation; and validate/publish/replace the candidate indexer plus look up old/load writers for cleanup. Keep these ports narrow and load-owned at first, with implementations over the existing metadata repository/catalog helpers in the current repository. Do not move them to `indexer-core` or publish them as stable cross-repository APIs until the method names and DTOs survive implementation slices. Implemented slices: `LoadWriterActionReceiveCapability` now depends on `LazyLiveWriterCatalog`, backed by `MetadataLazyLiveWriterCatalog`, instead of constructing indexer metadata directly, and `LoadIndexerPlugin` receives that port from application composition rather than constructing its metadata adapter; the core action-receive SPI and lazy catalog now exchange existing `IndexerModel` views, with metadata-record conversion confined to metadata routing/adapters; `DefaultLoadManagementService` receives `LoadCreationCatalog` from application composition for target readiness, load/live writer creation, and provider-start metadata reload, while `MetadataLoadCreationCatalog` remains the adapter and creation orchestration exchanges load-owned target/indexer views rather than core metadata records; publication replacement and cleanup lookup now sit behind `LoadPublicationRepository` and `LoadCleanupRepository`, backed by `MetadataLoadPublicationRepository`, so command handlers no longer orchestrate direct metadata replacement/read logic or consume metadata indexer records, and `LoadCommandHandlers` receives both ports from application composition rather than constructing the metadata adapter.
- The load-port stabilization review is complete. Every field in the creation/start views is consumed by workflow creation, provider startup, or lifecycle wake-ups. Publication and cleanup use the narrower `LoadIndexerReference` containing only indexer id, target id, and optimistic version; the unused physical index name was removed rather than preserving a metadata-record-shaped transfer object.
- The operational queue-reset package pass moved `IndexerQueueManagementService`, `ResetIndexerQueueRequest`, and `MetadataIndexerQueueManagementService` under `com.inqwise.indexer.operations.queues`. Queue reset remains an operational troubleshooting boundary, separate from indexer catalog lifecycle and provisioning resource-manager capability code.
- The resource-provisioning contract pass moved `IndexerQueueResourceManager` into `com.inqwise.indexer.provisioning`, alongside `IndexerDocumentIndexResourceManager`. Runtime queue transport contracts remain separate from queue resource administration.
- Indexer provisioning establishes one invariant baseline: type `INDEX`, mutation state `WRITABLE`, catalog publication state `UNPUBLISHED`, and publication readiness `PENDING`. Creation requests no longer accept caller-selected type, mutation state, or publication state. `IndexerType` remains persisted catalog metadata for provider selection and querying; provisioning should expose type selection only after another concrete type and its creation policy exist. Mutation transitions belong to Indexer Catalog lifecycle and readiness/publish/retire transitions belong to Publication Lifecycle. Core provisioning contracts are publication-independent and an architecture guard enforces this direction.
- Target Catalog and standalone admin indexer creation derive `LIVE_WRITER`, `OWNER`, and `NON_ACTIVE`; those outer request contracts no longer expose role, resource ownership, or runtime state. The lower provisioning request requires these dimensions explicitly because Action Routing and Load Workflow use different valid combinations; it must not default missing workflow policy to standalone-admin behavior. Add future combinations through their owning workflow rather than widening generic administration.
- `InsertIndexer` requires explicit type, role, and resource ownership, and repository adapters must not supply classification defaults. Keep classification policy in the owning workflow/provisioning layer before persistence.
- Provisioning uses `targetId` as the sole target identity and reloads the canonical target before definition resolution or insertion. Do not reintroduce caller-supplied target names into provisioning or standalone admin creation; persisted indexer, manifest, and publication target names derive from the repository target record.
- New provisioning requires explicit index and queue names and never derives queue identity from index identity. Keep nullable queue fallbacks limited to compatibility reads of historical runtime metadata; new creation paths must establish both physical resource identities.
- Provisioning contracts reject blank resource identities and use `DocumentIndexNameValidator` to reject wildcard, multi-index, and `_all` destinations before metadata insertion. Keep queue-provider syntax in transport adapters; the shared provisioning contract should enforce only provider-neutral queue identity rules.

## Runtime Resources

- Keep `queueName` immutable for normal lifecycle and retain reset as an internal troubleshooting exception. If stricter routing immutability is required, replace reset with creation of a replacement indexer followed by normal retirement of the old indexer.

- Defer distributed consumer-close acknowledgement and stale-generation action fencing until reset needs strict proof that old queued or in-flight items cannot be processed. The current reset guarantees only that future writes use the new queue.
- The local-node manual runtime reconcile operation is the first broken-consumer recovery primitive: it reloads durable metadata, closes the selected local runtime even when its model is unchanged, and recreates it only when the durable record remains eligible. A failed action remains uncommitted and leaves its consumer paused, so `ACTION_ITEM_FAILED` cannot directly trigger recovery: recreating the runtime redelivers the same head item and an unconditional trigger would form an unbounded poison-item retry loop. Automated failure recovery requires an explicit bounded retry/backoff/exhaustion policy plus operator visibility; other provider-neutral signal candidates include no progress while assigned to an active queue, excessive event-loop delay, resource pressure, or missed provider heartbeat windows. Do not add queue-provider health assumptions to core merely to trigger the existing recovery operation.

Jib defaults to `amd64` and selects `arm64` on AArch64 build hosts for local daemon compatibility; registry CI must build on or explicitly select the intended target architecture. The approved Temurin Java 21 Alpine base is pinned by its multi-platform OCI index digest so both architectures share one immutable source identity; upgrades require an explicit reviewed digest change. Keep custom process entry points and environment-specific target definitions out of Java code.
