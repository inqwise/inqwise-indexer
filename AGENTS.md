# Repository Instructions

- Use tabs for hierarchy indentation in Java and XML files. Do not use leading spaces for indentation in those files.
- Use `vertx-junit5` library tools for tests that exercise Vert.x asynchronous code.
- Treat the project as distributed-oriented. Keep runtime components, persistence, queue/buffer transport, and command orchestration separate.
- Do not put distributed workflow state into `Indexer` unless explicitly requested. Prefer durable commands and idempotent handlers for cross-resource operations.
- Design destructive cleanup as idempotent: missing queue/topic, document index, or repository record should be handled as an expected cleanup miss unless the storage client reports a real failure.
- Keep `Indexer` focused on runtime transport for one model: activate listeners/consumers, pause/resume/commit portions, process action items, emit events, and clean up its own resources.
- Keep command orchestration generic where possible. Use the generic `CommandService` layer for lifecycle/workflow commands instead of indexer-specific command infrastructure unless the domain requires it.
- Do not blindly create new models for new logic. First inspect the actual flow for existing command, repository, definition, request, and result models that already carry the needed data.
- Create every data-bearing model through a builder in production application code. This applies regardless of implementation style or annotation, including records, POJOs, commands, requests, results, events, definitions, entities, views, persistence models, and transport DTOs. Builders must validate required values and defensively copy mutable input. Direct construction is allowed inside the model's builder, in test code for test setup and test-only objects, or where a serialization, code-generation, reflection, or persistence framework demonstrably requires a constructor; framework-required constructors and setters must not become the normal production application construction API.
- Prefer simplicity over compatibility-preserving complexity. If a change requires deep function chains, excessive adapter layers, or model-to-model mutation mostly to preserve an old shape, bring that tradeoff up for discussion; in most cases the simpler design is preferred.
- Catch and normalize unexpected errors only at service implementation boundaries. Lower-level operations should fail naturally with typed/domain errors where possible and should not wrap broad `Throwable` unless they are the service boundary responsible for returning a normalized error contract.
- Document important accepted modules, designs, and solutions in `README.md` as part of the change that introduces or approves them.
- Add important uncovered flows, deferred design questions, and known follow-up decisions to the roadmap instead of leaving them only in conversation or code comments.
- Periodically refactor `README.md` and the roadmap so they form coherent, complete documents rather than scattered accumulated notes.
- For scoped multi-step work, create or update a local progress checklist file such as `PROGRESS.md`. Record accepted decisions, implementation tasks, deferred items, and verification status, and keep checklist item statuses current as the work progresses. Treat progress checklist files as local working artifacts; keep them git-ignored rather than committed.
- After meaningful design or implementation changes, periodically review the implementation shape before committing or starting the next scope. Look for ownership mismatches, lifecycle gaps, distributed-state leakage, unclear boundaries, and missing tests.

# Indexer Query Instructions

- Use `indexer-query` as the provider-neutral query and report-execution module. It may depend on `indexer-core`, but it must not depend on `indexer`, `indexer-load`, `indexer-node-application`, a concrete consumer, or a concrete document-store client.
- Keep querying independent from indexing transport. `ReportsService`, report execution, query planning, published-index resolution integration, and document-store query-provider contracts must not call queues, load orchestration, runtime workers, or `Indexer`.
- Keep `ReportsService` as the generic report-dispatch service name. A report request identifies the report and carries only user-controlled parameters; it must not accept physical index names, mandatory consumer filters, or document-store query objects.
- Model user-level query options and trusted consumer-level scope separately. Construct consumer scope from trusted execution context, never through the user request codec, and combine report scope, consumer scope, and user filters by intersection/conjunction so user input cannot widen the allowed scope.
- Keep caller identity out of `ReportExecutionRequest` and its transport codec. Inject `ReportCaller` or a resolved trusted context when composing the server-side `ReportsService`; typed clients and direct EventBus request payloads must not select their own consumer identity or trusted attributes.
- Let each report definition declare its logical target and effective time requirements. Do not create a bidirectional consumer-target association, consumer ownership registry, or consumer-target validation layer. Target and publication lifecycles remain independently managed.
- Resolve physical indexes through Publication-owned `PublishedIndexResolver` using the report's logical target and effective period. Consumers and reports must not generate, parse, accept, or expose physical index names.
- Include enough schema/provider identity in resolved query inputs to detect multi-index compatibility. Execute one multi-index provider query when selected indexes are compatible; otherwise group by compatible schema/provider strategy, use version-appropriate codecs, or return a controlled unsupported-combination error.
- A `ReportsFacade` composed with one `DocumentQueryProvider` may treat provider identity as implicit only when its resolver is guaranteed to return indexes owned by that provider. Mixed-provider resolution requires explicit provider/strategy identity before it is implemented.
- Keep physical index identities in `DocumentQueryExecution` for provider adapters only. Report-facing group results may expose compatibility/schema identity and the provider result, but must not expose physical index names, indexer ids, or target ids to report definitions.
- Keep report definitions typed internally. A definition owns its request codec, request validation, query planning, result decoding, result codec, and report-specific transformation. Do not force document hits, aggregations, and calculated reports into one generic result model.
- Support concrete typed report facades in addition to `ReportsService`. A facade may group reports by consumer or any other useful domain grouping and should delegate through a reusable typed executor and shared typed report bindings rather than duplicate query behavior. Keep the generic service as the primary stable remote contract unless a concrete typed remote service is explicitly required.
- Keep consumer report API artifacts separate from runtime implementations where useful: request/result models, codecs, typed bindings, and facade interfaces may be shared without pulling in provider clients, query planners, deployment code, or consumer runtime dependencies.
- Allow report definitions to reuse consumer document codecs for full-document results, but do not require that reuse. Projection, aggregation, and calculated reports may use specialized result codecs.
- Preserve dependency direction: consumers and concrete provider adapters may depend on `indexer-query` and `indexer-core`; deployment modules may compose selected consumers and adapters; `indexer-query` and `indexer` must never depend on a concrete consumer; report definitions must never depend on queue, runtime, load, node, or physical-index naming implementation details.

## Decisions Outside `indexer-query` Scope

- Consumer document ingestion is outside `indexer-query`. Treat `PutDocumentActionItem.document` as an untrusted JSON transport value and let a consumer-owned document definition decode it to a typed model, validate required values and domain invariants, normalize or enrich it, and encode the logical stored representation before durable acceptance whenever possible.
- Consumer document models, validators, projectors, and concrete codecs remain in the consumer module. `indexer-query` may expose neutral codec contracts or consume an injected codec through a report definition, but it must not own consumer document schemas or write preparation.
- Document-store write encoding and query-provider execution adapters are outside `indexer-query` orchestration. The consumer owns domain validation and logical projection; the concrete store adapter owns provider requests and provider-specific error classification. `indexer-query` depends only on the provider-neutral query port.
- Target and Publication lifecycle management are outside `indexer-query`. Reports declare logical targets and consume `PublishedIndexResolver`; they do not create targets, publish indexes, mutate catalog state, or validate a consumer-target ownership relationship.
- Authentication, principal resolution, authorization policy, and construction of trusted report execution context are deployment or gateway responsibilities. `indexer-query` consumes the trusted context and enforces its scope but does not authenticate callers.
- Concrete typed report facade interfaces and implementations belong to the consumer or another chosen grouping module. `indexer-query` supplies reusable typed bindings/execution helpers and `ReportsService`, but it does not own a concrete consumer's facade surface.
- Report presentation and export workflows such as PDF, spreadsheet, HTML, or file delivery are outside the core query execution boundary unless a separate approved module composes them from a completed typed report result.
- Action lifecycle extension is outside `indexer-query`. Keep `IndexerActionProvider` responsible for generic action-type behavior and coordinate target-specific preparation or optional hooks through separately injected action/runtime capabilities rather than through report definitions.
- Distinguish submission preparation, runtime pre-action hooks, post-write/pre-commit hooks, and after-commit observers in the action/runtime boundary. Submission preparation rejects invalid input before durable acceptance; pre-action failures prevent writes; post-write/pre-commit failures cause redelivery and require idempotent writes and hooks; after-commit observer failures must not roll back committed actions.
- Runtime hooks must not mutate target identity, indexer identity, physical index name, document uid, or routing destination. Document transformation belongs to submission preparation, and runtime hooks receive immutable execution context.
- Required post-action side effects use durable idempotent follow-up commands. When atomic handoff across different durable systems is required, use an approved outbox or equivalent design rather than assuming a document write and command submission are atomic.
- Queue transport, command orchestration, load/reload workflows, `Indexer` runtime behavior, node composition, web delivery, and concrete provider deployment remain outside `indexer-query`; do not introduce dependencies on them to implement report execution.
